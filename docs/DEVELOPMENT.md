# Разработка и проверка

Этот раздел для разработчика. Для установки готового агента используйте
[эксплуатацию](OPERATIONS.md).

## Сборка пакета

Собирайте на той же версии Debian, для которой предназначен агент. На Debian13
установите инструменты сборки:

```bash
sudo apt install dpkg-dev gcc make python3 python3-yaml poppler-utils
```

Из корня проекта:

```bash
make test
make build
./scripts/build-deb.sh
```

`make test` выполняет тесты Python. Привилегированные тесты и SQLCipher требуют
своего окружения; пропуски не считайте успешными проверками этих механизмов.
`make build` собирает native-компоненты. Сборка DEB также выполняет тесты.
Результат — `build/dlp-lab_0.2.23_amd64.deb`. Сборка не устанавливает агент.
Для Debian12 нужен нативный пакет с суффиксом `~deb12u1`, для сборки используется проверенный SQLCipher4 DEB как входной артефакт; [проверенный опыт сборки](research/debian12_port_2026-10-30.md).
Остальные зависимости выполнения перечислены в `Depends` файла `debian/control`.
Сборка с пропущенными специальными тестами не подтверждает работу этих функций.

## Проверка и ручной запуск

Ручной анализ из исходников:

```bash
./scripts/dlp analyze --text 'Обычная встреча'
./scripts/dlp analyze --text 'коммерческая тайна'
```

Файловый монитор из исходников не запускайте одновременно с установленной
службой. Для ручного запуска установленного файлового контроля:

```bash
sudo systemctl stop dlp-lab-files.service
sudo dlp-lab-run-files
# После Ctrl+C верните системную службу:
sudo systemctl start dlp-lab-files.service
```

Проверка Docker в отдельном временном проекте:

```bash
sudo python3 scripts/test-docker.py
```

Она создаёт тестовые контейнеры и данные, проверяет HTTPS, аутентификацию,
приём события и сохранение состояния; рабочий сервер не переносит.

Карта исходников: `native/` — файловый перехват; `src/dlp/` — анализ,
адаптеры, сервер; `src/dlp/ml_assets/` — модель; `tests/` — тесты;
`packaging/` и `debian/` — пакет и службы; `docker/` — серверный контейнер;
`data/ml/` — наборы и отчёты ML. Результаты экспериментов находятся в
`docs/research/`, журнал решений и проверок — в `docs/PROJECT_CONTEXT.md`.

## Приватный SQLCipher в пакете Debian 12

Сборка с `deb12` в версии включает библиотеку в
`/usr/lib/dlp-lab/lib/libsqlcipher.so.1`, а её лицензию — в
`/usr/share/doc/dlp-lab/copyright.sqlcipher`. Она не регистрируется через ldconfig
и не заменяет системные SQLCipher/SQLite. Читатель Signal выбирает её при
стандартном имени библиотеки; явный путь `--sqlcipher-library` остаётся доступен.
На Debian13 используется штатная зависимость `libsqlcipher1 (>=4)`.

На Debian12 amd64 перед сборкой задайте абсолютный путь:

```bash
export DLP_SQLCIPHER_DEB="$HOME/dlp-build-input/libsqlcipher1_4.6.1-2~dlplab12.1_amd64.deb"
./scripts/build-deb.sh
```

Версия в `debian/changelog` должна иметь суффикс `~deb12u1`.
Входной DEB нужен только сборщику, клиенту передаётся один DEB DLP.
`packaging/sqlcipher_bundle.py` проверяет SHA-256, имя, версию и архитектуру;
неизвестный файл останавливает сборку. Происхождение backport описано в
[опыте Debian12](research/debian12_port_2026-10-30.md). Зафиксированный SHA-256:
`1be243f9b4e36186990e93e951aec966ff67ed436ee0a05032349826a255670b`.

Этот бинарный артефакт не хранится в Git; его предоставляет сопровождающий сборки.
Повторная сборка upstream может дать другой хеш. При обновлении зависимости
сопровождающий проверяет новый артефакт и обновляет pin вместе с испытаниями.
Зависимости ELF (в том числе OpenSSL) вычисляет dpkg-shlibdeps на Debian12.
Обновления встроенной SQLCipher распространяются новым пакетом DLP.

Изолированная проверка без системной SQLCipher:

```bash
DLP_TEST_NO_SYSTEM_SQLCIPHER=1 DLP_TEST_DEP_DIR=/путь/тестовые-зависимости \
  bash scripts/test-deb-lifecycle.sh build/dlp-lab_0.2.23~deb12u1_amd64.deb /путь/python3-yaml.deb
```

Каталог тестовых зависимостей содержит PyCryptodome, но не SQLCipher. Скрипт
удаляет регистрацию SQLCipher только в одноразовом chroot, проверяет загрузку
приватной библиотеки, чтение синтетической зашифрованной базы и удаление пакета.
Это не проверка GUI или systemd на чистой виртуальной машине.
