# Telegram Desktop: локальное хранилище

Исследование: **2026-10-06**. Объект: собственный профиль roman,
`/home/roman/.local/share/TelegramDesktop/tdata`.

## Итог для проекта

Доступна read-only инвентаризация файлов и ограниченное распознавание контейнеров.
Прямой reader переписки из tdata **не реализован и не подтверждён**. По изученному
коду Telegram карта локального хранилища и черновики используют шифрование.
В рамках проекта ключи не извлекаются, расшифровка не выполняется.

Штатный JSON-экспорт — возможный отдельный источник нормализованных сообщений.
Он не заменяет прямой мониторинг локальной базы и не обеспечивает наблюдение
в реальном времени. Один реальный экспорт тестового чата успешно проверен
2026-10-06; подробности в [протоколе экспорта](telegram_export.md).

## Методика и границы

1. Проверены расположение профиля, пакет и ссылка executable.
2. Проведён обход с лимитом 10 000 записей и глубиной 5. Собраны только агрегаты
   файловой системы; непрозрачные имена файлов/аккаунтов в отчёт не включены.
3. Только для allowlist `settingss`, `maps`, `configs` прочитано по 8 байтов:
   сигнатура и число версии записи. Другие файлы не открывались на чтение.
4. Изучены первичные источники Telegram, закреплённые на теге v7.2.8.

Инструмент: `scripts/inspect-telegram-storage.py`. Он использует O_NOFOLLOW,
проверяет владельца и идентичность inode, пропускает симлинки/специальные файлы,
применяет O_NOATIME. Ключи, логи, JSON shortcut-файлы, кэш и медиа не читаются.
Не выполнялись запросы SQLite, копирование профиля, запуск/остановка Telegram,
создание сообщений, извлечение ключей или изменение настроек клиента.

Это наблюдение живого дерева, **не согласованный snapshot**. Стабильность трёх
заголовков проверена по size/mtime/ctime до и после чтения. Статистика в разных
запусках может различаться из-за работы Telegram.

Повторение без root из корня проекта:

```bash
python3 scripts/inspect-telegram-storage.py
```

Верхний уровень включает каталоги `audio_cache`, `user_data`, `dumps`, `fonts`,

и непрозрачно именованные файлы. Наличие имён не доказывает смысл содержимого.
Пакет: telegram-desktop-local 0+local.20260911142732.
Executable: `/usr/bin/telegram-desktop` → `/opt/telegram-desktop/Telegram`.
Версия/commit самого установленного бинарника по-прежнему не подтверждены.

| Проверенный файл | Заголовок | Число версии записи, little-endian | Размер |
|---|---|---|---|
| settingss | TDF$ | 7002008 | 2976 |
| configs в каталоге аккаунта | TDF$ | 7002008 | 1084 |
| maps в каталоге аккаунта | TDF$ | 7002008 | 340 |

TDF$ — собственная сигнатура контейнера Telegram, а не SQLite signature.
Нельзя утверждать, что весь профиль не содержит SQLite: полная проверка сигнатур
не проводилась. Отсутствие расширений — только отрицательное наблюдение по именам.
Число из заголовка относится к записавшей файл версии, не удостоверяет текущий
бинарник; файл мог пережить обновление. Сам TDF$ не доказывает шифрование payload.

## Что подтверждается исходниками

В качестве фиксированной ссылки использован тег v7.2.8. Соответствие локальной
сборке целиком не доказано; выводы о внутренней схеме относятся к этому исходному коду.

- `WriteManager::writeHeader` пишет TDF$ и AppVersion. Суффиксы s/0/1 используются
  файловыми утилитами; `FileWriteDescriptor::writeEncrypted` передаёт данные
  подготовке шифрования. Это объясняет контейнер, но не делает его открытой БД.
  [storage_file_utilities.cpp](https://raw.githubusercontent.com/telegramdesktop/tdesktop/v7.2.8/Telegram/SourceFiles/storage/details/storage_file_utilities.cpp)
- `Account::readMapWith` обрабатывает зашифрованную карту; `writeDrafts` сохраняет
  сериализованный черновик через writeEncrypted. Кэши имеют собственную абстракцию
  Cache::Database, пути cache/media_cache и ключ. Термин Database здесь сам по себе
  не означает SQLite или полную историю чата.
  [storage_account.cpp](https://raw.githubusercontent.com/telegramdesktop/tdesktop/v7.2.8/Telegram/SourceFiles/storage/storage_account.cpp)
- `Domain::startModern` использует зашифрованные данные для восстановления
  локальных сведений об аккаунтах. Эти операции нашим инструментом не повторяются.
  [storage_domain.cpp](https://raw.githubusercontent.com/telegramdesktop/tdesktop/v7.2.8/Telegram/SourceFiles/storage/storage_domain.cpp)

Не установлено, какие именно сообщения и насколько полно присутствуют в текущем
кэше. Нельзя выдавать кэш за полную историю. Факт локальной защиты не зависит от
нашего знания, включён ли пользовательский passcode; его наличие не выяснялось.

## Какие данные доступны агенту без обхода защиты

| Данные | Статус |
|---|---|
| Существование/тип файлов, размер и файловые timestamps | Доступны stat; timestamps не являются временем отправки |
| Сигнатура и версия контейнера для allowlist | Проверены |
| Отправитель, адресат, чат, время сообщения из tdata | Не извлечены, доступность без расшифровки не подтверждена |
| Текст сообщений/черновиков из tdata | Не извлечён; прямой reader не реализуется в рамках текущего подхода |
| Ключи/сессии | Не читаются и не нормализуются |
| Штатно экспортированные сообщения | Адаптер проверен на синтетике и одном предоставленном реальном тестовом экспорте |

Файловые метаданные нельзя превращать в фиктивный NormalizedMessage. Для них
нужен отдельный тип inventory event. Профиль исследован только для определения
технических возможностей; содержимое сообщений в docs/build не сохранялось.

## Альтернатива: явный экспорт и нормализация

Telegram официально описывает экспорт отдельных чатов и данных в JSON/HTML.
[Официальное описание экспорта](https://telegram.org/blog/export-and-more).
Это работа самого клиента с доступными пользователю данными; DLP не получает ключи.
Доступность пункта меню и формат результата конкретной локальной сборки ещё надо
подтвердить на собственном тестовом чате. Нельзя автоматически экспортировать
весь пользовательский аккаунт ради проверки.

В исходнике JSON writer текст может быть строкой или массивом фрагментов с
форматированием. Поэтому нельзя искать секретные слова в сыром JSON: необходима
нормализация текста, иначе разбиение фразы тегами вызовет пропуски.
[export_output_json.cpp](https://raw.githubusercontent.com/telegramdesktop/tdesktop/v7.2.8/Telegram/SourceFiles/export/output/export_output_json.cpp)

Адаптер реализован 2026-10-06, проверен на синтетике и одном реальном экспорте:

```text
Явно выбранный JSON тестового экспорта → проверка размера/схемы
  → NormalizedMessage(source=telegram_json_export) → общий ContentAnalyzer → аудит
```

Схема проверена по upstream; совместимость с одним реальным образцом подтверждена.
Отсутствующие account/recipient неизвестны; получатель не выводится из отправителя.
Для text-array фрагменты соединяются в исходном порядке без добавления разделителей.
Пути вложений не открываются, текст в журнале не сохраняется. Экспорт — исторический
аудит, не предотвращение отправки. Детали: [telegram_export.md](telegram_export.md).

## Проверки инструмента

Добавлены 5 тестов: чтение только allowlist-заголовков без вывода payload,
пропуск симлинков/FIFO, явные лимиты, неизвестная сигнатура и сохранение atime.
На этапе одной инвентаризации `make test`: 39 тестов, 37 пройдены, 2 opt-in пропущены.
После добавления экспортного адаптера: **51 тест, 49 пройдены, 2 opt-in пропущены**
(2026-10-06).
Привилегированные файловые тесты не запускались: этот этап не изменяет fanotify.

## Продолжение 2026-10-09

Руководитель подтвердил обязательность локальной базы; экспорт не заменяет её.
Повторная инвентаризация и новый инструмент сравнения файловых метаданных
описаны в [протоколе 2026-10-09](telegram_storage_experiment_2026-10-09.md).
Чтение семантических полей из tdata по-прежнему не реализовано. Указанные выше
размеры и количество файлов относятся к прошлому наблюдению 6 октября.
