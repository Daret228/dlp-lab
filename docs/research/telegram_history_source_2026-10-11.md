# Поиск локальной истории сообщений Telegram — 2026-10-11

## Задача и результат

Проверить наличие конкретного дискового источника текстов уже отправленных и
полученных сообщений, который можно добавить к offline-reader без изменения клиента,
сетевой авторизации и доступа к памяти процесса. Исследованы публичные исходники
Telegram Desktop v7.2.9, соответствующие последней поддержанной версии writer.
Это не идентификация текущего бинарника на компьютере пользователя.

**В изученных путях сохранения не найден дисковый архив обычных текстов переписки.**
Кандидат для расширения reader полной истории не установлен. Это ограниченный вывод
по исходникам, не доказательство невозможности любых следов сообщения на диске.
В профиле могут существовать черновики, кешированные текстовые вложения, экспорт,
особые данные ботов и другие объекты; они не равны архиву сообщений. Другие версии,
форки, системный swap и полный forensic-анализ не исследовались.

Профиль пользователя в этой работе не читался, Telegram не изменялся и не запускался.
Новый reader истории не реализован. DOCX и исходники ВКР не менялись по указанию
пользователя. Архив публичных исходников (2883 .cpp/.h) расположен в
build/telegram-history-source-7.2.9; хеши ключевых файлов сохранены в соседнем JSON.
Загрузка дерева для поиска не означает построчный аудит всех 2883 файлов; сторонние
submodules не входят в это покрытие.

## Проверенные цепочки

| Область | Наблюдение в исходниках | Значение для DLP |
|---|---|---|
| Карта tdata | storage_account.cpp: enum Local Storage Keys, readMapWith, writeMap, collectGoodNames | Есть черновики, locations, настройки и другие служебные данные; отдельной секции архива обычных сообщений не обнаружено |
| Первичная загрузка истории | history_widget.cpp: firstLoadMessages, MTPmessages_GetHistory → messagesReceived | Клиент имеет сетевой путь получения истории; один этот факт не доказывает отсутствие дискового кеша |
| Модель сообщений | data_session.h: Messages и _messages; data_session.cpp: processExistingMessages, registerMessage | Полученные сообщения представлены объектами HistoryItem в контейнерах памяти; рассмотренные функции не сериализуют их в архив |
| Кеш файлов | storage_account.cpp: cachePath/cacheBigFilePath; file_download.cpp: finishWithBytes; file_upload.cpp: кеш миниатюр и содержимого документа | Кеш хранит данные файлов и медиа; нельзя объявить его базой текстовых сообщений по имени Database |
| SharedMedia | storage_facade.cpp и storage_shared_media.cpp | Индексы объектов и идентификаторов в памяти; в рассмотренном коде нет записи полного текста переписки в файл |
| История загрузок | data_download_manager.cpp: serializator/deserialize | Локальная запись содержит ссылки на сообщения, путь, размер и служебные признаки загрузки, но не текст сообщения |
| Восстановление сообщения загрузки | data_download_manager.cpp: resolve-путь, MTPmessages_GetMessages/MTPchannels_GetMessages | Если объекта сообщения нет в памяти, клиент запрашивает его по сети; наш reader таких запросов не делает |

Выполнены поиски вызовов cache()/cacheBigFile(), GetHistory и сериализации history/message
по полученному дереву. Прямые места записи кеша связаны с документами, изображениями,
потоковым медиа, стикерами и Passport. Поиск по имени функции не покрывает все косвенные
вызовы, поэтому не используется как самостоятельное доказательство отсутствия данных.

## История загрузок как отдельный кандидат

Внутри уже известного locations-контейнера может быть downloadsSerialized. Схема
serializator: count int32; для каждой записи objectId uint64, type int32, started
int64, size uint32, peer uint64, messageId int64, peerAccessHash uint64, path QString.
Текст и подпись сообщения не сериализуются. started формируется из секунд локального
часа ×1000 и счётчика порядка в пределах секунды; нельзя называть младшие разряды
измеренной миллисекундой начала загрузки или временем отправки сообщения.

peerAccessHash — служебное поле API, не пароль и не сетевой ключ авторизации. Для
ограниченного DLP-reader оно не требуется: пропускать байты, не выводить и не
использовать для обращения к сети. Личные ID и пути посторонних файлов не выводить.
Допустимый будущий результат: наличие связи выбранного искусственного файла с записью
сообщения без экспорта идентификаторов. Это отдельная функция косвенных признаков,
не чтение текста истории.

В реальном опыте 9 октября downloadsSerialized был пуст: unparsed_downloads_bytes=0.
Поэтому нельзя обещать, что расширение parser немедленно даст данные на этом профиле.
Для реализации нужны искусственные fixtures и отдельный ручной опыт реального
скачивания тестового вложения; обычное «Сохранить как» уже имеющегося файла не следует
считать гарантией появления истории загрузок. Текущий этап ограничен исследованием.

## Решение

Не добавлять фиктивную команду analyze-history, выдающую черновики или файловые записи
за сообщения. Сохранить раздельные источники JSON, локальный черновик, file locations
и живое поле. Требование полной локальной истории остаётся незакрытым. Возможный
следующий этап разработки — ограниченное чтение косвенных признаков загрузок с явным
указанием, что оно не закрывает требование текста истории. Получение сообщений через
отдельную сетевую сессию либо изменение Telegram не выбирались и не выполнялись.
