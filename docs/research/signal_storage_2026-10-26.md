# Первичная проверка локального хранилища Signal — 2026-10-26

## Проверено на стенде

Пакет Signal Desktop имеет версию 8.32.0. Только lstat известных путей:
в ~/.config/Signal существуют обычные файлы sql/db.sqlite и config.json.
На момент проверки db.sqlite-wal и db.sqlite-shm отсутствовали. Отсутствие WAL
не доказывает завершение клиента или согласованность базы. Содержимое файлов,
ключи, сообщения и системное хранилище секретов не читались.

## Первичный источник

Официальный DATABASE_SCHEMA.md в ветке main:
https://github.com/signalapp/Signal-Desktop/blob/main/DATABASE_SCHEMA.md

Он описывает таблицы сообщений и связанных данных. Это ориентир для исследования,
а не доказательство схемы установленной 8.32.0 или доступности её расшифровки.
Попытки получить app/main.ts и ts/sql/Server.ts по предполагаемому тегу v8.32.0
вернули 404; механизм ключей для этой сборки пока не проверен по исходникам.
Наличие файла с расширением sqlite не доказывает возможность открыть его
обычным sqlite3. Reader и извлечение истории Signal не реализованы.

## Следующие шаги

1. Найти точные исходники механизма открытия БД установленной сборки.
2. Определить допустимый способ доступа к собственной тестовой базе без
   изменения клиента, ослабления защиты и обхода хранилища секретов.
3. Подготовить минимальный reader на синтетической базе: ограничение выборки,
   read-only, передача текста в анализатор без сохранения исходного текста в журнал.
4. Только после проверки схемы и способа доступа провести отдельный опыт
   с согласованной копией собственной тестовой базы. Не объявлять синтетический
   reader или инвентаризацию чтением реальной истории.

## Проверка установленного кода и диагностический модуль

Прочитан архив приложения /opt/Signal/resources/app.asar как файл данных;
код не выполнялся, клиент не менялся. package.json подтверждает версию 8.32.0
и зависимость @signalapp/sqlcipher 4.1.0 (это версия npm-пакета).
В bundles/main.js функция с логами getSQLKey читает key/encryptedKey,
использует safeStorage.decryptString и проверяет совпадение Linux backend.
Она также меняет config при миграции; её нельзя вызывать как read-only reader.
В bundles/workers/sql.js обнаружены sql/db.sqlite, PRAGMA key, WAL и миграции.
Повторное использование штатного initializer не подходит для read-only анализа.
Это выводы по установленному коду, а не по предполагаемому upstream тегу.

Копии только программного кода для исследования лежат в игнорируемом build/signal-source;
профиль и ключи туда не копировались. SHA256 извлечённых bundles:
- main.js: 2f2a7fc60fcb75b584da1cba2fb0a490e5237a5abeda86d915771d00e7805adf
- sql.js: 882d7ec14326c128552f620e9cfa0d0a644cdffbe72cd2f034551bc12786fb81

Добавлен src/dlp/signal_storage.py и scripts/probe-signal-storage.py --root PATH.
Диагностика читает только первые 16 байт БД, config.json проверяет через stat,
не подключается к SQLite и не возвращает исходные байты. Фиксированные результаты
без путей/содержимого: messages_read=0, content_analysis=false. Символьные ссылки
на профиль, sql и файл БД не открываются; нет рекурсивного обхода.
На стенде результат not_plaintext_sqlite; сам по себе он не доказывает шифрование
(повреждённый файл даёт тот же результат). Вместе с кодом SQLCipher это основание
исследовать доступ через ключ, но не заявлять чтение сообщений.
4 теста прошли: обычный/неизвестный/короткий заголовок, отсутствие, symlink,
сохранение содержимого/mtime и отсутствие чтения некорректного config.
Ключи и системное хранилище секретов по-прежнему не читались. Следующий этап:
определить применённый механизм хранения ключа в собственной тестовой установке;
не ослаблять safeStorage, не менять config и не запускать миграции.

## Способ хранения ключа на стенде — 2026-10-26

Конфигурация прочитана ограниченно (regular file, O_NOFOLLOW, максимум 1 MiB),
без вывода значений ключей. Санитизированный результат: legacy_key_present=false,
encrypted_key_present=true, backend=gnome_libsecret. JSON-парсер обрабатывал
конфигурацию в памяти, включая зашифрованное значение; расшифровка не выполнялась.
Открытый ключ не получен, GNOME Keyring не опрашивался, сообщения не читались.

Штатный доступ к ключу и чтение копии собственной тестовой базы Signal предложены
пользователю отдельно: прежнее явное разрешение на ключ касалось Telegram.
До ответа зависимые действия не выполнять. Не подменять backend на basic_text,
не менять config, не отключать защиту и не вызывать initializer клиента.

Зависимости на стенде: Python gi доступен; secretstorage/sqlcipher3/pysqlcipher3
не найдены в системном Python, sqlcipher/secret-tool не найдены в PATH.
Установленное приложение содержит собственный native @signalapp/sqlcipher;
совместимость с отдельным runtime не проверена. Никакие зависимости не установлены.
После разрешения сначала выбрать и проверить read-only путь на синтетической
зашифрованной БД, затем при закрытом Signal — согласованная копия тестового профиля.
Ключ не передавать в аргументах команд, не печатать и не сохранять; исходный текст
не писать в журнал. Не считать разрешение на локальное чтение разрешением на
сетевые запросы, отправку сообщений или изменение базы.

## Синтетический read-only опыт и разрешение

Пользователь разрешил штатный доступ через GNOME Keyring для своей тестовой базы.
Ожидается подтверждение полного закрытия Signal. Реальный Keyring ещё не читался.
libsqlcipher1 4.6.1-2 из репозитория Debian распакован локально без установки.
Модуль signal_sqlcipher: принудительный SQLITE_OPEN_READONLY, URI mode=ro,
query_only=ON, trusted_schema=OFF. Опыт: зашифрованная синтетическая таблица
прочитана, INSERT отклонён, байты не изменились, неверный ключ отклонён.
3 теста прошли с DLP_SQLCIPHER_LIBRARY, включая opt-in библиотечный тест.
Сообщения HMAC error в отрицательном тесте ожидаемы, не содержат ключа.
SQLCipher не запускает функции и миграции клиента Signal.

Основание Linux v11 (проверенная версия Chromium, не утверждение о версии
Chromium установленного Electron):
https://raw.githubusercontent.com/chromium/chromium/130.0.6723.58/components/os_crypt/sync/os_crypt_linux.cc
https://raw.githubusercontent.com/chromium/chromium/130.0.6723.58/components/os_crypt/sync/key_storage_libsecret.cc

В этих исходниках: v11, PBKDF2 salt saltysalt/1 iteration/AES128, CBC с IV пробелы;
libsecret lookup по application. Наш код отклоняет неизвестные префиксы и пустой
пароль, не использует upstream fallback и не создаёт секрет при отсутствии.
Соответствие реальному защищённому ключу Signal ещё не проверено. Не перепутать
исследовательский прототип с установленным пакетным агентом: пакет не менялся.

## Успешный опыт на реальной тестовой базе

Пользователь подтвердил полный выход. Проверка /proc: 0 процессов с executable
/opt/Signal/signal-desktop. Через libsecret найден ровно один секрет по точному
атрибуту application=Signal; хранилище уже разблокировано. Запрошен только этот
секрет в рамках разрешения. Ключ расшифрован в памяти, не выведен и не сохранён.

Временная копия db.sqlite (и WAL/SHM при наличии) создана в каталоге 0700,
файлы 0600; config обработан только в памяти. Чтение ограничено по размеру,
O_NOFOLLOW, регулярным файлом, проверкой size/mtime при копировании. До и после
копирования проверяется отсутствие Signal. Исходные файлы не менялись:
SHA256 сравнены в памяти до/после, значения в отчёт не включены. TemporaryDirectory
удалила копию по завершении. Процесс имел core limit=0 и тайм-аут SIGALRM.

Первый проход подтвердил read-only открытие и таблицу messages с ожидаемыми
полями. Второй проход использовал analyze_recent_messages: максимум 100 последних
непустых body, максимум 16 KiB на текст, без JSON/вложений/идентификаторов в выводе.
Результат: analyzed=1, ALLOW=1, WARN=0, BLOCK=0, incomplete=0, skipped_oversize=0,
more_text_rows=false. Исходный текст не включён в вывод/отчёт. Журнал-результат
build/signal-storage-probe/result.json содержит только агрегаты опыта.

Это подтверждённое чтение и анализ сохранённого body собственного Signal 8.32.0,
но не полнота истории, не все типы сообщений и не запрет отправки. Положительный
секретный пример ещё требуется. 11 тестов test_signal_*.py прошли с явной SQLCipher
библиотекой, включая лимиты, пропуск больших body и отсутствие текста в summary.
Эксперимент запускается отдельным локальным скриптом в build, пока не является
поддерживаемой CLI-командой/службой/пакетом. Полный suite в этом ходе не запускался.
Следующее: synthetic BLOCK/WARN в собственном чате, повторное закрытие и сравнение;
затем оформить воспроизводимый CLI с явными параметрами и тестами ошибок snapshot.

## Чувствительное сохранённое сообщение Signal обнаружено — 2026-10-26

После пользовательского подтверждения выхода повторён read-only опыт копии
с проверкой отсутствия процессов Signal. В реальной таблице messages найдено
точное совпадение с подготовленной пользователем синтетической фразой; в выводе
только test_message_found=true и decision=BLOCK. Текст из базы не выводился.
Ограниченная выборка: analyzed=2, ALLOW=1, WARN=0, BLOCK=1, incomplete=0,
skipped_oversize=0, more_text_rows=false. Исходные файлы неизменны по сравнению
хэшей в памяти; временная копия удалена. Ключ не сохранён/не выведен.
Агрегатный отчёт build/signal-storage-probe/sensitive-result.json вне Git.
Таким образом реально подтверждены ALLOW и BLOCK при анализе сохранённых body
Signal 8.32.0. Это ретроспективное обнаружение; отправка не запрещалась, уведомление
в этом опыте не вызывалось. В службу/DEB reader ещё не включён, CLI пока отдельный
исследовательский скрипт. Далее: оформить поддерживаемую команду offline-анализа,
проверки snapshot/ошибок и подключить журналирование/уведомления. Signal можно открыть.

## Команда Signal с журналом и видимым предупреждением — 2026-10-26

Добавлен signal-local-check (--root, --sqlcipher-library, --journal, --limit,
--no-notify, --executable). Отдельный worker ограничен 45 секундами, core dumps
отключены. Parent управляет временным каталогом и удаляет копию при завершении/
тайм-ауте worker. Произвольный SIGKILL parent не гарантирует уборку — это ограничение
описано в README. Snapshot проверяет owner/regular/O_NOFOLLOW/лимиты, отсутствие
клиента и наличие/хэши config+db+WAL+SHM до/после; config и ключ не сохраняются.
Read-only SQLite и контроль неизменности не означают атомарный snapshot при
намеренном вмешательстве пользователя. Модуль требует добровольно закрытого клиента.

Первый live-запуск корректно отказал на недоступных /proc/exe системных процессов.
Добавлено узкое разрешение известных имён session helper (systemd, sd-pam,
ssh-agent, vmtoolsd) при недоступном exe; неизвестный процесс даёт отказ. Это
liveness guard, не аттестация процессов/защита от подмены comm. Тесты покрывают
оба случая; первоначальный mock перекрывал resolve Python symlink, тест исправлен.

Повторный live CLI: 08:50:07 UTC, analyzed=2, ALLOW=1/BLOCK=1, непроверенных=0,
source_files_unchanged=true; 08:50:08 notification_delivery=accepted,
display_confirmed=false автоматически. Пользователь отдельно подтвердил «Да,
появилось» — видимость предупреждения подтверждена человеком, JSON не переписан.
Журнал build/signal-storage-probe/agent-check.jsonl создаётся 0600 и содержит
только агрегаты/статус доставки, без текста/ключей/идентификаторов. Повторный запуск
повторяет аудит и максимум одно предупреждение, дедупликация между запусками пока
не реализована. Сигналы ALLOW/WARN/BLOCK — ретроспективный анализ, не send veto.

README содержит запуск и зависимости. Новая команда только в исходниках;
установленный DEB 0.2.4, files service и web UI не изменены. Библиотека SQLCipher
по-прежнему распакована локально, не установлена. Следующее: пакетные зависимости
и включение новой команды в следующую версию DEB, затем повторная проверка установки.
