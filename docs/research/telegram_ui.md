# Telegram Desktop: исследование UI (план)

Установленный executable обнаружен, но реальный PID и accessibility tree
недоступны в текущем ограниченном окружении процессов. Фреймворк этой сборки
и его версия **UNKNOWN**. Наличие libatspi в ОС не доказывает поддержку клиентом.

| Проверка | X11 | Wayland |
|---|---|---|
| Идентификация целевого процесса и поля draft | UNKNOWN | UNKNOWN |
| Text.get_text читает draft | UNKNOWN | UNKNOWN |
| Событие send доступно до отправки | UNKNOWN | UNKNOWN |
| Надёжный синхронный запрет send | UNKNOWN | UNKNOWN |

Wayland указан в окружении; самостоятельная X11-сессия не исследовалась.
План: для конкретной версии и тестового аккаунта найти только дерево целевого
PID, проверить role/state/Text interface поля, обычный текст, multiline, edit,
черновики в разных чатах и отправку кнопкой/Enter. Измерить порядок событий.
При отсутствии synchronous veto реализовать только наблюдение/предупреждение,
не называть его предотвращением отправки. Не включать глобальные key listeners.

[AT-SPI Text API](https://gnome.pages.gitlab.gnome.org/at-spi2-core/libatspi/iface.Text.html)
описывает чтение текста, но не гарантирует такую поддержку Telegram.

## Эксперимент 2026-09-24: текущая Wayland-сессия

AT-SPI и Python bindings доступны на host. Среди 17 зарегистрированных приложений
найден Telegram PID 13795, подтверждённый ProcessDetector. Его Accessible root
имеет role=application, interfaces=[Accessible, Collection], child_count=0.
Результат повторён после подготовки пользователем тестового черновика
`DLP_TEST коммерческая тайна` и сброса клиентского accessibility cache.

Это означает, что получить поле ввода через доступное дерево в данном запуске
не удалось. Это не доказательство отсутствия accessibility во всех сборках.
Пользователю предложен локальный перезапуск с
`QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1 /usr/bin/telegram-desktop` — документированной
настройкой Qt. Глобальные настройки accessibility не менялись, приложение
автоматически не закрывалось.

Добавлен воспроизводимый read-only probe:

```bash
PYTHONPATH=src:.deps timeout 20s python3 scripts/probe-telegram-ui.py --marker DLP_TEST
```

Он обследует только процессы, совпавшие с TelegramAdapter; не читает имена
элементов или историю сообщений. При явном --marker проверяет текст только
видимого сфокусированного редактируемого элемента, исключая password role,
и возвращает факт наличия маркера без исходного текста. Это диагностический
инструмент, а не реализованный TextMonitor и не перехват отправки.

[Qt QAccessible](https://doc.qt.io/qt-6/qaccessible.html) описывает флаг включения
Linux accessibility и необходимость интерфейсов для собственных виджетов.
[AT-SPI Text.get_text](https://gnome.pages.gitlab.gnome.org/at-spi2-core/libatspi/method.Text.get_text.html)
предоставляет чтение текста.
[EventListener](https://gnome.pages.gitlab.gnome.org/at-spi2-core/libatspi/class.EventListener.html)
предоставляет уведомления. Эти возможности сами по себе не доказывают наличие
синхронного запрета отправки. Автоматическое стирание текста, перехват всех клавиш
и гонка с нажатием Enter не считаются надёжным enforcement и не реализованы.

## После перезапуска с Qt accessibility

Пользователь перезапустил Telegram с указанным флагом и подготовил черновик.
Новый PID 15840: AT-SPI зарегистрировал два application root, один пустой,
другой с деревом виджетов. Найдены два видимых editable/Text элемента.
Тестовый маркер обнаружен в одном из них. Фокус находился вне Telegram,
поэтому для явной проверки маркера разрешены видимые editable поля без FOCUSED.
Содержимое истории и имена элементов не читались и не журналировались.

В Python GI `Accessible.get_text()` конфликтует с одноимённым методом Text.
Рабочий вызов: `Atspi.Text.get_text(node.get_text_iface(), 0, count)`.

На этой основе реализован экспериментальный `text-monitor`: пользователь
помечает тестовый draft уникальным маркером, агент привязывается ровно к одному
видимому editable/Text объекту и опрашивает его каждые 300 мс. При изменении текста
вызывает общий ContentAnalyzer и пишет только findings/offsets/decision.
При WARN/BLOCK пытается показать стандартное desktop notification через notify-send.
Полный текст остаётся только в памяти на время работы. История сообщений не собирается.

Проверено на реальном черновике 2026-09-24 10:33:16 UTC:
`secret_keywords`, score=0.8, decision=BLOCK, complete=true.
Но фактическое действие — `enforcement=observe_only`, `send_blocked=false`.
Через 3 секунды тестовый monitor штатно завершился.

Границы: проверен один подготовленный элемент в текущей Wayland-сессии;
backend окна (native Wayland/XWayland) не установлен, отдельная X11-сессия не проверена.
Не проверены все режимы compose/edit/caption, разные окна и аккаунты.
При исчезновении элемента или смене процесса monitor останавливается.
Отправка Enter/кнопкой и синхронное veto не исследованы экспериментально.
Никакое решение BLOCK из анализа черновика не следует выдавать за блокировку send.

## Исследование send veto — результат

Проверены семантика AT-SPI EventListener/Action и пути отправки upstream Telegram.
В выбранном механизме не обнаружен синхронный внешний permission hook для текста.
Проверка черновика остаётся observe_only. Для блокировки требуется отдельная
интеграция в контролируемый путь отправки; она меняет область реализации.
Обоснование, альтернативы и условия проверки:
[ADR-004](../decisions/004-text-send-enforcement.md).
