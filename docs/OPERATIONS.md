## 1. Роли и готовность

| Обозначение | Где выполнять |
| --- | --- |
| **Сервер** | Компьютер администратора: центральный журнал, регистрация устройств, задания |
| **Агент** | Рабочая машина с Telegram/Signal и файловой защитой |
| **Пользовательский сеанс** | Терминал пользователя, запустившего мессенджер, внутри графической сессии; без sudo |

На текущем стенде сервер — `roman@192.168.17.131`, второй агент —
`roman1@192.168.17.133`. На серверной машине также работает собственный агент.
Это примеры адресов, а не обязательные настройки. При другом IP заменяйте его
в сертификате, адресе подключения и сетевой настройке.

`sudo` нужен только для установки и администрирования системных файлов/служб.
Не запускайте текстовый монитор, чтение профилей или панель пользователя от root.

**С сервера уже доступны:** просмотр событий всех подключённых устройств и
запрос диагностики без действий пользователя рабочей машины.
**Пока недоступны:** изменение политик/служб агента, установка обновлений и
регистрация одноразовым кодом через центральную панель. Эти операции сейчас
выполняет администратор на агенте, в том числе через уже настроенный SSH.

## 2. Установка рабочего агента

### Быстрый путь: единый установщик

Администратор может подготовить установочный комплект с DEB и самостоятельным
скриптом `install-dlp.py` (Python3, стандартная библиотека; pip не требуется).
Из корня исходников, без sudo:

```bash
./scripts/build-install-kit.py --package build/dlp-lab_0.2.17_amd64.deb --output build/dlp-install-0.2.17-debian13-amd64.tar.gz
```

Для Debian 12 передайте совместимый DEB через `--package` и локальный
`libsqlcipher1` через `--sqlcipher-package`. Сборщик не включает ключи или профили;
существующий архив не перезаписывает.

**На рабочей машине:** распакуйте подходящий комплект, положите рядом со скриптом
индивидуальный `central-agent.json` (права 0600) и публичный `central-ca.crt`,
подготовленные по разделу 3. Затем:

```bash
tar -xzf dlp-install-0.2.17-debian13-amd64.tar.gz
cd dlp-install
# Положите сюда central-agent.json и central-ca.crt перед проверкой.
sudo ./install-dlp.py --check
sudo ./install-dlp.py
```

Для Debian 12 замените имя архива. Проверка не обязательна отдельным шагом:
обычный запуск тоже сначала проверяет условия, выводит план и спрашивает
подтверждение. На уже подключённой машине конфигурация может сохраняться без
нового JSON. При запуске из root-сеанса и неоднозначном выборе пользователя
добавьте `--user ИМЯ`; нестандартные пути задаются `--telegram` и `--signal`.
При существующей конфигурации пути повторно не задавайте. `--no-signal` отключает
автовыбор Signal только при первой настройке. Для автоматизации используйте `--yes`.

Если сервер не нужен, явно добавьте `--local-only`. Это не отключает ранее
работавший отправщик. Мессенджеры устанавливаются заранее; текущий setup требует
Telegram и поддерживает дополнительный Signal для одного пользователя.

Установщик проверяет Debian 12/13, архитектуру, версию, защищённость исполняемых
файлов, регистрацию, CA и зависимости через apt simulation. Затем устанавливает
пакет/зависимости, сохраняет существующую политику, настраивает files/forwarder
и автозапуск, запускает doctor и проверяет active выбранных служб. Для Debian 12
распознаётся локальный пакет libsqlcipher1 рядом со скриптом. Он не добавляет
репозитории, не скачивает сам DLP, не заменяет чужую регистрацию, не отключает TLS.
При конфликте или ошибке останавливается. Уже выполненные шаги автоматически
не откатываются; не удаляйте существующую очередь для повторного запуска.

`--check` на существующей системе может требовать sudo для чтения root-only
настройки. Никакие значения токенов установщик не выводит. Выданные комплекту
права root предполагают доверие администратору и происхождению DEB: SHA256SUMS
подтверждает целостность, но не является цифровой подписью.

**После установки всё ещё обязательны:** `monitor_started`, тестовое прикрепление,
событие в центральной панели. Автоматическая проверка сети/срока сертификата и
успешного приёма события не заявляется. Текст/локальные базы требуют пользовательского
сеанса и отдельной настройки. Проверка без изменений прошла на текущих Debian 12/13;
повторное применение установщика на Debian 12 и автозапуск после перезагрузки
подтверждены. После установки 0.2.14 пользователь подтвердил исправление
.Xauthority и контроль public/secret. Полная новая установка на чистой VM пока
не проверена.

Без комплекта можно запускать исходный скрипт с явными параметрами:

```bash
sudo ./scripts/install-dlp.py --package ./build/dlp-lab_0.2.17_amd64.deb --user YOUR_USER --central-config /path/to/central-agent.json --ca /path/to/central-ca.crt
```

Далее описан ручной путь, который сохраняется для диагностики и нестандартных
установок. Если комплект успешно настроил агент, повторять раздел 2 не требуется.

### 2.1 Подготовить пакет

**На машине сборки совместимой ОС, без sudo.** Исходники не содержат готовых DEB.
Для сборки нужны пакеты из `Build-Depends` файла `debian/control`. Из корня проекта:

```bash
./scripts/build-deb.sh
```

Результат Debian 13 amd64 — `build/dlp-lab_0.2.17_amd64.deb`.
Сборка выполняет тесты. Не переносите бинарный пакет Debian 13 на Debian 12:
соберите совместимый вариант. На стенде для Debian 12 используются
`dlp-lab_0.2.14~deb12u1_amd64.deb` и локальный `libsqlcipher1` версии 4.6.1.
[Подготовка Debian 12 и SQLCipher](research/debian12_port_2026-10-30.md).
Отсутствующие зависимости apt должен получить из настроенных доверенных источников.

### 2.2 Установить

**На агенте, sudo.** Скопируйте подходящий DEB на рабочую машину и перейдите в его
каталог. Для Debian 13:

```bash
sudo apt install ./dlp-lab_0.2.17_amd64.deb
```

Для подготовленного Debian 12-стенда из каталога с обоими пакетами:

```bash
sudo apt install ./libsqlcipher1_4.6.1-2~dlplab12.1_amd64.deb ./dlp-lab_0.2.14~deb12u1_amd64.deb
```

Если работает старый файловый монитор из исходников, сначала остановите его
через `./scripts/dlp agent stop files` от пользователя. При миграции также
отзовите старое лабораторное правило NOPASSWD по [README.Debian](../packaging/README.Debian).

### 2.3 Настроить файловый контроль

**На агенте, sudo.** Можно отказаться от настройки в диалоге apt и использовать:

```bash
sudo dlp-lab-configure --wizard
```

Укажите пользователя рабочего стола, путь Telegram и при необходимости Signal.
Выберите запуск и автозапуск, проверьте итог и подтвердите. Пути зависят от
способа установки клиента; мастер не устанавливает сами мессенджеры.
Он требует Telegram, Signal добавляется опционально. Исполняемые файлы должны
принадлежать root и быть защищены от записи обычными пользователями.

Если настройка уже была выполнена в apt, мастер повторять не нужно. Для скриптов
вместо мастера (замените `YOUR_USER`):

```bash
sudo dlp-lab-configure --user YOUR_USER --telegram /usr/bin/telegram-desktop --signal /opt/Signal/signal-desktop --enable
```

Без Signal исключите `--signal` с его значением.

```bash
dlp-agent doctor
sudo systemctl status dlp-lab-files.service --no-pager
sudo journalctl -u dlp-lab-files.service -n 20 --no-pager
```

Ожидается `monitor_started`. Сам факт установки или `active` не заменяет проверку
файла. Файловый контроль использует локальные файловые системы с исключениями,
а не только демонстрационный каталог. После появления нового монтирования нужен
перезапуск службы. Текст и базы сами при установке не включаются.

## 3. Сервер и подключение устройства

**Текущий сервер уже перенесён в Docker.** Для него используйте
[управление после переноса](DOCKER.md#текущий-стенд-после-переноса).
Разделы 3.1–3.2 ниже описывают альтернативную новую установку через systemd.
На текущем сервере их не повторяйте: адреса уже заняты Docker, база принадлежит
UID 10001. Повторная инициализация и повторный запуск миграции не нужны.

### 3.1 Запустить центральный сервер

**На сервере, sudo.** Установите подходящий DEB так же, как в разделе 2. На отдельном
сервере без мессенджеров откажитесь от настройки файлового контроля.
Следующий блок предназначен для первой настройки, не для перезаписи рабочего конфига:

```bash
sudo install -d -m 0755 /etc/dlp-lab
printf '%s\n' '{"host":"127.0.0.1","port":8766}' | sudo tee /etc/dlp-lab/central-server.json >/dev/null
sudo systemctl enable --now dlp-lab-central.service
sudo journalctl -u dlp-lab-central.service -n 20 --no-pager
```

Откройте на сервере `http://127.0.0.1:8766/`. Токен администратора покажет:

```bash
sudo dlp-admin-token
```

Команда читает существующий токен, не меняет его и не перезапускает службы.
В ранее собранных DEB до версии 0.2.14 включительно команды ещё нет. Для текущей
установки добавьте её один раз из обновлённых исходников:

```bash
sudo install -o root -g root -m 0755 /home/roman/dlp-lab/packaging/dlp-admin-token /usr/sbin/dlp-admin-token
```

Введите его только в поле центральной панели. Не пересылайте его агентам.
После перезагрузки страницы токен потребуется снова. «Обновить» обновляет данные
без перезагрузки страницы.

### 3.2 Подготовить HTTPS для другой машины

**На сервере.** Loopback8766 доступен только локально. Для сети нужен сертификат,
соответствующий адресу сервера, и доверие к его CA на агенте. Для лабораторного
стенда используется второй listener8767 с той же базой. Требуются `openssl` и
проверенная копия исходников проекта.

Если сертификаты уже настроены, этот шаг пропустите. Пример создания нового
лабораторного CA/сертификата, **без sudo, из корня проекта**:

```bash
umask 077
mkdir -m 700 build/tls-new
cd build/tls-new
openssl req -x509 -newkey rsa:3072 -nodes -days 365 -keyout ca.key -out ca.crt -subj '/CN=DLP Lab CA' -addext 'basicConstraints=critical,CA:TRUE,pathlen:0' -addext 'keyUsage=critical,keyCertSign,cRLSign'
openssl req -new -newkey rsa:3072 -nodes -keyout server.key -out server.csr -subj '/CN=DLP Lab server'
printf '%s\n' 'basicConstraints=critical,CA:FALSE' 'keyUsage=critical,digitalSignature,keyEncipherment' 'extendedKeyUsage=serverAuth' 'subjectAltName=IP:192.168.17.131' > server.ext
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 365 -out server.crt -extfile server.ext
cd ../..
sudo /usr/bin/env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin /bin/bash scripts/install-central-tls.sh 192.168.17.131 "$PWD/build/tls-new"
```

Замените IP **и в SAN, и в команде**. Скрипт отказывается заменять существующие
TLS-файлы. CA private key храните отдельно защищённо; агенту передавайте только
`ca.crt`. Проверьте доступность 8767 в сети, при необходимости настройте firewall
по правилам своей сети. Скрипт firewall не меняет. Сертификаты истекают через 365 дней;
смена адреса требует нового подходящего сертификата и настройки подключения.
Не отключайте проверку TLS.

### 3.3 Зарегистрировать агент и передать конфигурацию

**Для текущего Docker-сервера**, выберите уникальное имя:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json exec local python3 /app/entrypoint.py add-agent --name linux-02 --server https://192.168.17.131:8767 --out /var/lib/dlp-central/linux-02.json
```

**Только для альтернативного systemd-сервера:**

```bash
sudo -u dlp-central dlp-agent central add-agent --state /var/lib/dlp-central --name linux-02 --server https://192.168.17.131:8767 --out /var/lib/dlp-central/linux-02.json
```

Передайте этот JSON на соответствующую рабочую машину по административному SSH.
Пример для текущих пользователей; замените имя и адрес для нового устройства.
**На сервере, от roman**, из корня исходников:

```bash
install -d -m 0700 "$HOME/dlp-provision"
sudo install -o "$(id -un)" -g "$(id -gn)" -m 0600 /var/lib/dlp-central/linux-02.json "$HOME/dlp-provision/central-agent.json"
ssh roman1@192.168.17.133 'install -d -m 0700 ~/dlp-provision'
scp "$HOME/dlp-provision/central-agent.json" roman1@192.168.17.133:dlp-provision/
sudo install -o "$(id -un)" -g "$(id -gn)" -m 0644 /etc/dlp-lab/tls/ca.crt "$HOME/dlp-provision/central-ca.crt"
scp "$HOME/dlp-provision/central-ca.crt" roman1@192.168.17.133:dlp-provision/
scp scripts/install-central-forwarder.sh roman1@192.168.17.133:dlp-provision/
```

Каталог `/etc/dlp-lab/tls` закрыт для обычного пользователя, поэтому выше
экспортируется только публичный CA.

Никогда не передавайте `admin.json`, `server.key` или `ca.key`. Не используйте
один JSON для разных устройств. На уже подключённой машине повторная регистрация
не нужна: её конфигурация и очередь привязаны к существующему устройству/серверу.

**На новом агенте, sudo:**

```bash
sudo /usr/bin/env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin /bin/bash "$HOME/dlp-provision/install-central-forwarder.sh" "$HOME/dlp-provision"
sudo journalctl -u dlp-lab-forwarder.service -n 20 --no-pager
```

Установщик сохраняет root-owned конфиг 0600, публичный CA и доверие к нему только
для отправщика. Существующий конфиг не перезаписывает. Ожидается
`Events acknowledged: N`: ноль — нет новых событий, положительное число — сервер
подтвердил приём. Проверьте затем реальное тестовое событие в панели.
После успешного подключения промежуточные копии agent JSON нужно хранить как
секрет либо удалить вручную по правилам администратора.

Для агента на самом сервере допустима регистрация с `http://127.0.0.1:8766`:
установите его JSON через `sudo install -o root -g root -m 0600 ...
/etc/dlp-lab/central-agent.json`, затем `sudo systemctl enable --now
 dlp-lab-forwarder.service`. HTTPS-установщик предназначен для HTTPS, не loopback HTTP.

### 3.4 Какие события отправляются

Системный отправщик читает журнал **системной файловой службы**. Текст/базы,
запущенные прямыми CLI-командами, не становятся центральными событиями автоматически.
Для пользовательских systemd-модулей предусмотрен отдельный user forwarder.
[Настройка пользовательского отправщика и его отдельной очереди](CENTRAL_SERVER.md#службы-deb-026).
При частном CA также задайте ему `SSL_CERT_FILE` через user systemd drop-in:

```bash
# Пользовательский сеанс агента, без sudo, после настройки user forwarder:
systemctl --user edit dlp-lab-forwarder-user.service
# Добавить:
# [Service]
# Environment=SSL_CERT_FILE=/etc/dlp-lab/central-ca.crt
systemctl --user restart dlp-lab-forwarder-user.service
```

## 4. Ежедневная работа

**Центральная панель на сервере:** введите токен, нажмите «Обновить», найдите
устройство. В таблице событий проверяйте и «Решение», и «Применение».
`BLOCK/DENY` — анализ и запрет открытия, `WARN/ALLOW` — предупреждение без запрета.
Количество строк не равно количеству уникальных файлов или утечек.

Для диагностики нажмите кнопку у устройства, через 30 секунд — «Обновить».
Одно задание ожидает агента до 15 минут. «Выполнено» означает доставленный отчёт.
`INFO` у серверных ролей на рабочей машине нормально: сервер там не требуется.
`UNKNOWN` у очереди означает отсутствие этой проверки, а не ошибку доставки.
Не путайте старые отчёты с новым результатом.

**Агент, системные службы:**

```bash
dlp-agent doctor
sudo systemctl restart dlp-lab-files.service
sudo journalctl -u dlp-lab-files.service -n 30 --no-pager
sudo journalctl -u dlp-lab-forwarder.service -n 20 --no-pager
```

Перезапуск кратковременно прерывает защиту. Остановить и отключить автозапуск:
`sudo systemctl disable --now dlp-lab-files.service`. Вернуть:
`sudo systemctl enable --now dlp-lab-files.service`.

**Ручной режим на агенте, sudo:**

```bash
sudo systemctl stop dlp-lab-files.service
sudo dlp-lab-run-files
# Ctrl+C; после завершения:
sudo systemctl start dlp-lab-files.service
```

Системный, ручной и лабораторный файловые мониторы одновременно не запускаются.
Для разового анализа, **без sudo**:

```bash
dlp-agent analyze --text 'коммерческая тайна'
dlp-agent analyze --file /absolute/path/to/document.docx
```

Код выхода 0 означает завершённый анализ, в том числе BLOCK; смотрите поле
`decision`. Неполный анализ/ошибки отличайте по `complete` и `reason`.

## 5. Текст и локальные данные

Все команды раздела — **пользовательский графический сеанс агента, без sudo**.
Не запускайте их от служебного пользователя отправщика.

### Текстовый черновик

Откройте собственный тестовый чат, введите `DLP_TEST коммерческая тайна`, оставьте
окно видимым. Для Telegram при проблемах доступности полностью завершите клиент
и запустите `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1 /usr/bin/telegram-desktop`.
Для Signal нужна проверенная AT-SPI-доступность установленной версии.

```bash
dlp-agent text-monitor --messenger telegram --marker DLP_TEST --seconds 120
# Для Signal — отдельный запуск вместо Telegram:
dlp-agent text-monitor --messenger signal --marker DLP_TEST --seconds 120
```

Ожидаются `text_monitor_started` и `draft_analysis`. Отсутствие видимого поля с
маркером не является успешным запуском. Это observe-only: текст не удаляется,
отправка не блокируется. Ctrl+C останавливает наблюдение.

### Telegram JSON-экспорт

Экспортируйте свой тестовый чат официальным клиентом в JSON, затем:

```bash
dlp-agent analyze-export --file /absolute/path/to/result.json
```

Это разовая проверка экспортированных данных, не доступ ко всей локальной истории.

### Telegram: исследованный локальный черновик

Только собственный тестовый профиль **без локального код-пароля**. Оставьте
черновик `DLP_STORAGE_TEST коммерческая тайна`, полностью завершите Telegram:

```bash
dlp-agent local-check --root "$HOME/.local/share/TelegramDesktop/tdata" --profile-closed --no-passcode --marker DLP_STORAGE_TEST
```

Эти флаги подтверждают реальные условия опыта, а не отключают защиту клиента.
Если установлен пароль или профиль расположен иначе, не копируйте команду
без проверки условий. [Исследование и ограничения](research/telegram_local_reader_2026-10-09.md).

### Signal: сохранённые сообщения

Полностью завершите Signal, обеспечьте штатный доступ к своему GNOME Keyring:

```bash
dlp-agent signal-local-check --root "$HOME/.config/Signal" --journal "$HOME/dlp-signal-local.jsonl"
```

По умолчанию проверяется до 100 последних непустых текстов, до 16КиБ каждый.
SQLCipher открывает временную копию read-only; проверяется неизменность оригинала.
Уведомление при риске не запрещает отправку уже сохранённого сообщения.
В журнал попадают агрегаты, не содержимое. Вложения и вся семантика истории
не покрыты. Keyring может показать штатный запрос разблокировки.

### Пользовательские модули и локальная панель

```bash
dlp-agent dashboard
# В другом терминале при необходимости:
dlp-agent agent status
dlp-agent agent logs --lines 30
```

Панель 8765 управляет пользовательскими лабораторными модулями. Центральная 8766
показывает устройства и задания. Кнопка файлов локальной панели не заменяет
управление системной `dlp-lab-files.service`. Не запускайте через неё второй
файловый монитор поверх пакетного. Для лабораторного запуска из исходников
используйте `./scripts/dlp` вместо `dlp-agent` из корня проекта с зависимостями.

## 6. Правила и исключения

**На агенте, администратор.** В0.2.15 центральная панель правила не применяет.
Пакетная политика: `/etc/dlp-lab/system/policy.yaml`. Политика исходников
`config/policy.yaml` — другой файл. Редактор локальной панели не заменяет
системную политику установленного пакета.

Безопасный порядок: редактировать отдельную копию, проверить её на синтетических
примерах без sudo, затем установить и перезапустить службу:

```bash
# Пользователь на агенте, без sudo:
install -m 0600 /etc/dlp-lab/system/policy.yaml "$HOME/dlp-policy-candidate.yaml"
nano "$HOME/dlp-policy-candidate.yaml"
dlp-agent --policy "$HOME/dlp-policy-candidate.yaml" analyze --text 'Открытая информация'
dlp-agent --policy "$HOME/dlp-policy-candidate.yaml" analyze --text 'коммерческая тайна'
# Только после проверки результата, администратор:
sudo cp -a /etc/dlp-lab/system/policy.yaml /etc/dlp-lab/system/policy.yaml.previous
sudo install -o root -g root -m 0644 "$HOME/dlp-policy-candidate.yaml" /etc/dlp-lab/system/policy.yaml
sudo systemctl restart dlp-lab-files.service
sudo journalctl -u dlp-lab-files.service -n 20 --no-pager
```

Дождитесь `policy_loaded`/`monitor_started`, повторите прикрепление тестового файла.
`policy.yaml.previous` в этом примере хранит только последнюю копию; для нескольких
версий используйте отдельный архив. Откат:

```bash
sudo cp -a /etc/dlp-lab/system/policy.yaml.previous /etc/dlp-lab/system/policy.yaml
sudo systemctl restart dlp-lab-files.service
```

Пороговые значения, правила, разрешённые типы и ML описаны в
[примере политики](../config/policy.yaml). ML включается `ml_alerts.enabled: true`,
действие остаётся WARN. В новой политике 0.2.15 ML уже включён, но обновление
с сохранением старой политики не меняет её настройку. Перед применением оцените ложные срабатывания на своих
разрешённых тестах. [Оценка ML](research/ml_quality_2026-10-19.md).

Исключения файлового контроля — строки `exclude=` в
`/etc/dlp-lab/system-gateway.conf`. Сначала сделайте root-only резервную копию,
измените через `sudoedit`, перезапустите files и проверьте `excluded_roots` в журнале.
Начиная с 0.2.14 служебный файл `<home>/.Xauthority` исключён из анализа,
если это обычный файл владельца контролируемого сеанса, без доступа группы/прочих
и без дополнительных жёстких ссылок; проверяется совпадение открытого файла
с записью каталога. Домашний каталог должен принадлежать тому же пользователю
и не допускать запись группы/прочих. Символические ссылки не исключаются.
Содержимое по этому точному пути не проверяется, даже если туда намеренно
поместить документ. Это явное ограничение покрытия для работы X11;
одноимённые файлы в других каталогах проверяются обычным образом.

Каждое исключение сокращает область проверки. Для замены пользователя/путей
остановите files и используйте `dlp-lab-configure --replace` со всеми нужными
мессенджерами; это сохраняет резервную копию настроек и сбрасывает исключения.

## 7. Обновление и резервное копирование

**На каждой обновляемой машине, sudo:**

```bash
sudo apt install ./новая-совместимая-версия.deb
dlp-agent doctor
```

Это обозначение имени файла, замените его фактическим DEB. При обновлении не нужно
повторно регистрировать агент или запускать `--replace`. Dpkg сохраняет локальные
изменения conffile штатным механизмом; при вопросе сравните версии политики.
Обновление/перезапуск может дать краткий перерыв файловой защиты.

**На текущем Docker-сервере** обновление DEB не обновляет образ. Используйте
[обновление Docker-сервера](DOCKER.md#обновление-текущего-docker-сервера).
`update-central-ui.sh` для него не применяется.

**Только для альтернативного сервера через systemd**, если включён TLS unit:

```bash
sudo systemctl restart dlp-lab-central-tls.service
```

Он создан отдельно от DEB и не перезапускается пакетным lifecycle. Если используется
пользовательский отправщик, после обновления в пользовательском сеансе:

```bash
systemctl --user restart dlp-lab-forwarder-user.service
```

После обновления перезагрузите страницу панели, введите токен, запросите новые
отчёты. Сверьте версии через `dpkg-query -W dlp-lab` на каждой машине.

Для текущего Docker-сервера есть [команды согласованной резервной копии](DOCKER.md#резервная-копия-текущего-сервера).

Для резервной копии нужны `/etc/dlp-lab`, `/var/lib/dlp-central` на сервере и
`/var/lib/dlp-forwarder` на агенте. Они содержат секреты/аудит: архив доступен только
администратору. Для согласованной копии SQLite штатно остановите все процессы,
пишущие в соответствующую БД (на сервере оба listener, на агенте forwarder),
скопируйте **весь каталог**, затем запустите ранее работавшие службы. Не копируйте
только `state.sqlite` во время записи, игнорируя WAL. Файловую защиту для копии
очереди останавливать не требуется. После восстановления сохраните владельцев,
права и привязку очереди к исходному устройству/серверу.

## 8. Устранение ошибок

| Симптом | Проверка и действие |
| --- | --- |
| Central systemd unit inactive после миграции | Это ожидаемо: сервер в Docker. Проверяйте `docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json ps` через sudo; старые units не включайте |
| `Address already in use` | `ss -ltnp` и состояние нужных служб; используйте уже работающую панель. Не завершайте неизвестные процессы вслепую |
| Страница старая, нет кнопок заданий | Перезагрузите страницу после обновления сервера, повторно введите токен |
| Нет доступа в панели | Используйте admin token именно этого серверного state, а не токен агента |
| `Already configured` | Не повторяйте мастер при обновлении; замена конфигурации отдельной командой с `--replace` |
| Files active, но нет проверки | Ищите `monitor_started`, правильный UID/путь мессенджера, исключения и фактический DENY в свежем опыте |
| Файл разрешён при WARN | Штатное поведение: WARN не запрещает открытие |
| Поле с маркером не найдено | Проверьте видимость/маркер/AT-SPI; не запускайте монитор через sudo или SSH вне графической сессии |
| `Events acknowledged: 0` | Нормальный пустой цикл; создайте тестовое событие files и сравните оба журнала |
| `Delivery failed` | Адрес, сеть, время, срок/SAN сертификата, CA в drop-in, действительность токена; не отключайте TLS-проверку и не удаляйте очередь |
| `Collection failed` | Права журнальной службы, предупреждения journald, потерянный cursor после ротации; не сбрасывайте состояние без выяснения причины |
| Задание ожидает/истекло | Версия системного forwarder, его состояние, TLS listener и синхронизация часов; старые/пользовательские отправщики задания не выполняют |
| Старое `Мессенджеры: ERROR` | На 0.2.12 была ошибка UID диагностики; обновите до 0.2.14 и создайте новый отчёт |
| Signal Keyring/SQLCipher ошибка | Закройте клиент, используйте его графический сеанс и поддерживаемую SQLCipher4; секреты не отправляйте в чат |
| Предупреждение apt про `_apt` | Если установка завершилась успешно, это уведомление о чтении локального DEB, не отказ запуска агента |

Полезные команды: `dlp-agent doctor`, `systemctl status ... --no-pager`,
`sudo journalctl -u ИМЯ_СЛУЖБЫ -n 30 --no-pager`. Перед передачей журналов
проверьте отсутствие личных данных; токены и профили передавать не нужно.

## 9. Остановка и удаление

**Агент, sudo:** остановить только отправку —
`sudo systemctl disable --now dlp-lab-forwarder.service` (локальная защита продолжает
работать). Остановить защиту — `sudo systemctl disable --now dlp-lab-files.service`.

**Пользовательский сеанс:** если включён user forwarder:

```bash
systemctl --user disable --now dlp-lab-forwarder-user.service
```

Остановите также запущенные текстовые/локальные задания. **Текущий Docker-сервер**
останавливается отдельно; удаление DEB его контейнеры не удаляет:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json stop
```

**Только для systemd-сервера**, перед удалением пакета отключите отдельный TLS listener:

```bash
sudo systemctl disable --now dlp-lab-central-tls.service
```

**На удаляемой машине, sudo:** `sudo apt remove dlp-lab` останавливает пакетные
системные службы и сохраняет конфиги. `sudo apt purge dlp-lab` дополнительно
удаляет пакетную политику и сгенерированные настройки хоста. Даже purge сохраняет
центральные credentials, базы, служебные аккаунты и пользовательские данные;
это не полное стирание истории. Отдельный TLS unit/сертификаты также требуют
ручного сопровождения. Не удаляйте их без резервной копии и решения администратора.

Чтобы отозвать токен устройства **на текущем Docker-сервере**, замените `DEVICE_ID`:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json exec local python3 /app/entrypoint.py revoke-agent --id DEVICE_ID
```

Для альтернативного **systemd-сервера**:

```bash
sudo -u dlp-central dlp-agent central revoke-agent --state /var/lib/dlp-central --id DEVICE_ID
```

История остаётся. Отзыв доступа к серверу не выключает локальную защиту агента.

## 10. Приёмочная проверка

1. На агенте видны версия 0.2.14+, `monitor_started`, корректные UID и мессенджеры.
2. В своём тестовом чате публичный файл прикрепляется, файл с синтетической
   «коммерческой тайной» блокируется. Реальные секреты для теста не нужны.
3. В журнале есть `file_access_attempt`, отдельно decision и enforcement.
4. Forwarder подтверждает непустую отправку, в центральной панели событие
   принадлежит нужному устройству.
5. Диагностика из панели завершена; отдельно рассмотрены INFO/UNKNOWN.
6. Текст, локальные базы, уведомления проверены отдельными опытами, если нужны.
7. Проверка после перезагрузки и опыт отключения сервера фиксируются отдельно;
   успешность предыдущих пунктов не заменяет эти опыты.

Последние подтверждённые результаты и следующие задачи:
[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md). Исторические версии команд:
[README_HISTORY.md](README_HISTORY.md) — не инструкция для новой установки.

### Центральный журнал: работа с новым интерфейсом

Вход в панель 8766 выполняется токеном администратора. Токен хранится только
в памяти открытой вкладки, не в localStorage; после обновления страницы
нужен повторный вход. «Выйти» очищает данные текущей вкладки, но не отзывает
сам токен на сервере.

Обзор показывает устройства и число файловых WARN/DENY в последних 200
серверных записях. Уведомления не дублируют файловые счётчики. Это не число
уникальных отправок. «Недавняя связь» означает запрос агента за 2 минуты,
а не исправность защиты. Отчёт диагностики показывается со своей датой.
Фильтры работают только в загруженной выборке, период — по времени получения
сервером. В подробностях доступны переданные категории и признак complete;
имена файлов, исходный текст и подробные правила сервер не получает.
Автообновление выполняется каждые 15 секунд в видимой вкладке; его можно отключить.

**Исторический способ только для systemd-сервера. На текущем Docker-сервере
не запускать:** скрипт попытается включить старую службу на занятом порту.
Для установки только этой версии интерфейса поверх совместимой серверной
логики из корня исходников: `sudo ./scripts/update-central-ui.sh`.
Скрипт сравнивает серверный код вне HTML, делает резервную копию трёх файлов
в /var/backups/dlp-central-ui.*, устанавливает интерфейс и перезапускает
только dlp-lab-central.service. Он не меняет файловую защиту, регистрацию,
политику, базу событий или HTTPS-службу. При различии серверного кода требуется
пакетное обновление. При обычной сборке DEB новый HTML включается автоматически.

### Объединение повторных открытий

Начиная с0.2.17 повторные файловые события с одной группой и результатом
показываются одной строкой с количеством попыток. Исходный аудит не удаляется.
[Порядок обновления и применение на текущем Docker-стенде](DOCKER.md#повторные-открытия-одного-файла-0217).
Старые события без группы остаются отдельными; первыми обновляются серверы,
затем отправщики. Уведомления рабочего стола этим изменением не меняются.
