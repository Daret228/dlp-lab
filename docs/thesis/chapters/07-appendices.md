:::subtitle (обязательное)
:::subtitle ТРАССИРОВКА ТРЕБОВАНИЙ И ПРОВЕРОК

Таблица А.1 связывает постановку задачи с фактической реализацией. «Частично» означает наличие проверенного ограниченного механизма, а не отсутствие результата. Вид доказательства не подменяется количеством файлов исходного кода.

:::table А.1|Требования и подтверждения
Код|Требование|Реализация и проверка|Статус
R01|Общий анализ текста|ContentAnalyzer; unit-тесты и синтетический набор|Реализовано
R02|Настраиваемая политика|YAML, проверка ключей и порогов|Реализовано
R03|Файловый запрет|fanotify, kernel/gateway и выбор файла Telegram|Файловые системы с исключениями
R04|Фильтр мессенджера|UID, executable, inode/device, starttime|Telegram и Signal проверены
R05|Контроль поля ввода|AT-SPI, анализ, видимое предупреждение и journal|Проверено на стенде
R06|Запрет отправки текста|Синхронный механизм не найден в изученных API|Не реализовано
R07|Чтение истории|JSON одного чата, два реальных экспорта|Разовая проверка
R08|Прямое чтение tdata|Черновики и file locations|Полная история не читается
R09|Проверка вложений экспорта|Пути учитываются, файлы не открываются|Не реализовано
R10|Управляемый запуск|Системные службы и ручной режим|Проверены, включая перезагрузку
R11|Защищённая политика|Системные файлы root; полного tamper protection нет|Частично
R12|Машинное обучение|Обучение и сравнение на синтетическом наборе|Эксперимент; преимущество не доказано
R13|Другой мессенджер|Signal: файлы и локальные тексты|Проверено на стенде

R16|Управление политиками с сервера|Редактор, CAS, root-брокер, policy_loaded на двух устройствах|Реализовано

Для принятия очередного изменения следует выбрать требование и указать новый вид доказательства. Например, поддержка подписи через JSON не закрывает контроль подписи в живом редакторе. Добавление executable в конфигурацию не подтверждает доступ к истории этого приложения. Для переноса решения на другой клиент необходимы отдельные результаты по каждому направлению.

Отсутствие реализации R06 не отменяет результатов R05: раннее обнаружение остаётся самостоятельной функцией. Однако пользовательский интерфейс должен явно различать эти требования. Аналогично R07 не закрывает R08. Такая трассировка предотвращает расширение формулировок за пределы проведённых опытов.

# ПРИЛОЖЕНИЕ Б

:::subtitle (обязательное)
:::subtitle КОНФИГУРАЦИЯ АНАЛИЗА И ОБЛАСТИ КОНТРОЛЯ

Приведены фрагмент политики и пример фильтра процессов. Они иллюстрируют конфигурацию репозитория, а не состояние всех работающих служб. Загруженную версию проверяют отдельно.

```yaml
thresholds:
  warn: 0.3
  block: 0.7
on_error: BLOCK
file_types:
  allow: [text, pdf, docx]
  deny: [elf, dos_pe, script, zip, gzip, 7z, rar]
```

Полный пример политики находится в config/policy.yaml [23]. Ниже показан фильтр клиентов; пути и UID соответствуют конкретному стенду.

:::codefile config/processes.yaml

Изменение конфигурации требует перезапуска монитора. Системный gateway использует защищённые настройки, лабораторный — настройки проекта. Файловый системный режим допускает только messengers.

Значение on_error=BLOCK описывает ошибку содержательного анализа. В исторической проверке оно не отменяет выполненную операцию.

# ПРИЛОЖЕНИЕ В

:::subtitle (справочное)
:::subtitle ФОРМАТЫ СОБЫТИЙ И ПРАВИЛА ИНТЕРПРЕТАЦИИ

События представлены строками JSON с временем UTC. Структура меняется в зависимости от источника. Приведённые ниже примеры искусственные; они не содержат переписку пользователя и не являются копиями личных событий.

:::table В.1|Поля результата анализа
Поле|Тип|Значение и ограничение
findings|Массив|Найденные признаки без фрагментов текста
score|Число|Сумма вкладов правил, может превышать 1
 decision|Строка|ALLOW, WARN или BLOCK
complete|Логический|Проверка доступного входа завершена
reason|Строка или null|Причина неполноты или ошибки
location|Пара целых|Диапазон символов нормализованного текста
:::

Пример словарного срабатывания в историческом источнике:

```json
{
  "event": "export_message_analysis",
  "source": "telegram_json_export",
  "scope": "message_text_only",
  "record_index": 3,
  "retrospective": true,
  "enforcement": "none",
  "attachments_analyzed": false,
  "result": {
    "findings": [{
      "analyzer": "dictionary",
      "rule_id": "secret_keywords",
      "category": "confidential",
      "confidence": 1.0,
      "severity": 0.8,
      "location": [4, 17],
      "metadata": {}
    }],
    "score": 0.8,
    "decision": "BLOCK",
    "complete": true,
    "reason": null
  }
}
```

В экспортном событии record_index относится к позиции записи, включая служебные позиции исходного массива. Номер не является идентификатором Telegram. Для сверки оператор использует тот же экспорт, а не произвольную новую выгрузку, где порядок мог измениться.

:::table В.2|Признаки действий и покрытия
Признак|Смысл|Недопустимое толкование
file_access_attempt|Попытка открыть файл|Сообщение отправлено
file_operation|Итог серии открытий одной версии файла|Подтверждённая отправка
policy_loaded|Загружена политика текущего запуска|Все правила применены к другим модулям
send_confirmed=false|Отправка не подтверждена|Отправки точно не было
observe_only|Наблюдение и уведомление|Клиент ждёт разрешение
send_blocked=false|Запрет отправки не применён|Полная защита ввода
retrospective=true|Проверка истории|Онлайн-контроль канала
text_analysis_complete|Выбранный текст обработан|Вся история и медиа проверены
queue_overflow|Зафиксирована потеря покрытия|Все операции учтены
:::

Итоговая файловая операция передаётся отдельным событием. Искусственный пример:

```json
{
  "event": "file_operation",
  "decision": "BLOCK",
  "enforcement": "DENY",
  "messenger": "telegram",
  "file_path": "/home/user/secret.txt",
  "reasons": ["file_type_denied"],
  "operation_count": 4,
  "complete": true
}
```

Поле operation_count равно числу объединённых открытий; итоговый статус выбирается по приоритету BLOCK, WARN, ALLOW, а DENY сохраняется при хотя бы одном фактическом отказе. Причина file_type_denied означает решение по типу файла без проверки содержимого.

При интерпретации следует сначала установить источник, затем завершённость, решение и фактически применённое действие. Отсутствие findings имеет смысл только вместе с complete и scope. Причина process_out_of_scope обозначает сознательное исключение процесса, а не результат содержательной проверки.

Время аудита относится к проверке, время сообщения — к данным источника; при корреляции они сохраняются раздельно.

# ПРИЛОЖЕНИЕ Г

:::subtitle (обязательное)
:::subtitle МЕТОДИКА ДЕМОНСТРАЦИИ ПРОТОТИПА

Для актуальной пакетной установки демонстрация начинается на машине агента с проверки состояния системных компонентов. Должны быть заранее настроены клиент, пользователь и индивидуальное подключение к серверу.

```bash
dlp-agent doctor
systemctl is-active dlp-lab-files.service
systemctl is-active dlp-lab-forwarder.service
sudo journalctl -u dlp-lab-files.service -n 20 --no-pager
```

В собственном тестовом чате по очереди выбирают обычный и чувствительный TXT. Ожидаются разрешение первого и отказ второго; отправлять сообщения для проверки открытия не требуется. Для Signal опыт повторяется отдельно. Событие сопоставляют с новым временем, приложением и фактическим действием, не только с решением анализатора. Дополнительно показывают вложение-изображение PNG: поставляемая политика запрещает его тип по сигнатуре, поэтому ожидается отказ с причиной file_type_denied и непроверенным содержимым.

На сервере открывают центральную панель и выбирают нужное устройство. Проверяют появление одной итоговой строки «Операция с файлом» для каждой серии, раскрывают подробности и показывают режимы фильтра журнала: основной режим скрывает служебные чтения со счётчиком скрытого, режим технических событий возвращает их. В разделе «Политики» демонстрируют загрузку копии действующей политики устройства и команду применения; завершённое задание и событие policy_loaded сверяют с заданием по времени. Ввод токена выполняет администратор; токен, ключи и сообщения не включаются в демонстрационные материалы. UNKNOWN в отчёте означает непроведённую проверку, а не успешную доставку.

Автозапуск проверяют отдельной перезагрузкой после сохранения работы. До и после неё сравнивают состояние служб и повторяют тестовое открытие. Подтверждение работы служб не заменяет отдельный опыт текстового мониторинга. Не следует запускать лабораторный files параллельно системной файловой службе.

Центральная веб-панель объединяет устройства, события и результаты диагностики. Пользовательские модули запускаются через CLI в графическом сеансе. Локальная веб-панель удалена из агента версии 0.2.18.

Демонстрация проводится на собственной тестовой станции от обычного пользователя. Ограниченный gateway предварительно установлен. Root перед scripts/dlp не требуется. Политика и фильтр должны соответствовать приложению Б. Сначала проверяется состояние; старые ручные мониторы необходимо завершить отдельно, поскольку agent управляет только своими unit.

```bash
cd /home/roman/dlp-lab
./scripts/dlp agent status
./scripts/dlp agent logs --follow
```

Последняя команда занимает терминал. Ctrl+C прекращает только просмотр. Остальные команды выполняются во втором терминале из каталога проекта. В журнале могут быть предыдущие запуски, поэтому результат сопоставляется по времени и новым сообщениям готовности.

Первый этап — разовая проверка искусственного экспорта:

```bash
./scripts/dlp agent export --file \
  examples/telegram-export-synthetic.json
./scripts/dlp agent logs --lines 15
```

Ожидаются три проверенных текста с ALLOW, WARN и BLOCK. Одна служебная запись и вложение без подписи пропускаются с явными счётчиками. После завершения экспорт отображается остановленным, что соответствует разовому заданию. Код 0 не означает, что все сообщения получили ALLOW.

Второй этап — файловое наблюдение:

```bash
./scripts/dlp agent start files
./scripts/dlp agent status
./scripts/dlp agent logs --lines 15
```

Необходимо увидеть новое monitor_started с UID обычного пользователя и режимом messengers. Затем в тестовом чате вручную выбрать подготовленные dlp-public-demo.txt и dlp-secret-demo.txt из /var/lib/dlp-lab/watch. Отправка не нужна. Ожидаются ALLOW и DENY в file_access_attempt для процесса Telegram. Повторные открытия допустимы; их нельзя считать отдельными отправками.

```bash
./scripts/dlp agent stop files
```

После stop соответствующее файловое наблюдение прекращается. Следует показать переход status в остановленное состояние и объяснить, почему прежнее решение BLOCK в журнале не означает продолжающуюся защиту.

Третий этап — текстовое поле. Сначала сохранить нужные черновики, полностью выйти из Telegram и запустить его с включённой доступностью:

```bash
QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1 \
  /usr/bin/telegram-desktop
```

В тестовом чате набрать DLP_TEST, оставить окно видимым и запустить:

```bash
./scripts/dlp agent start text \
  --marker DLP_TEST --seconds 120
./scripts/dlp agent logs --follow
```

После text_monitor_started можно менять черновик на обычный текст, email и искусственную секретную фразу. Отправлять не требуется. Ожидаются draft_analysis с изменяющимися решениями и send_blocked=false. Если поле не найдено за 30 секунд, опыт считается не выполненным; ошибка анализируется по журналу.

Четвёртый этап — явное завершение:

```bash
./scripts/dlp agent stop
./scripts/dlp agent status
```

Дополнительный опыт проверяет локальный источник. В собственном тестовом чате оставляют неотправленный черновик DLP_STORAGE_TEST с секретной фразой и полностью завершают Telegram. При отсутствии локального код-пароля выполняют:

```bash
scripts/dlp agent local --profile-closed --no-passcode
scripts/dlp agent logs --lines 30
```

Ожидаются local_draft_analysis, предупреждение и local_check_finished. Ненайденный или неоднозначный маркер означает неполную проверку, а не ALLOW. Клиент остаётся закрытым до завершения. Отдельная команда agent notification-test проверяет предупреждение на искусственном тексте без чтения профиля. Появление окна подтверждается визуально, а accepted означает лишь принятие запроса службой рабочего стола.

После лабораторного опыта его пользовательские модули останавливают. Логи сохраняются по правилам journald. Системный автозапуск пакетного агента проверяется отдельным сценарием выше. На защите отдельно объясняются границы каждого механизма: реальный файловый отказ, наблюдение черновика, offline-чтение tdata и ретроспективный экспорт.

Протокол содержит дату, конфигурацию, ожидаемое решение, фактическое событие и ограничение. Переписка и ключи профиля не сохраняются.

# ПРИЛОЖЕНИЕ Д

:::subtitle (справочное)
:::subtitle СИНТЕТИЧЕСКИЙ КОРПУС И МЕТОДИКА ИЗМЕРЕНИЯ

Все примеры созданы для исследования правил и не получены из переписки. Функциональные случаи проверяют реализацию активной политики. Диагностические пробы проверяют границы применимости и не должны смешиваться с независимой оценкой качества.

:::functional

Для повторения используется скрипт docs/thesis/measure_synthetic.py. Он загружает config/policy.yaml, формирует TextContent, выполняет правила и записывает результаты в docs/research/thesis_synthetic_experiment_2026-10-06.json. Повторный запуск заменяет этот файл новыми измерениями; для сравнения серий следует заранее сохранить предыдущий протокол под отдельным именем.

```bash
cd /home/roman/dlp-lab
PYTHONPATH=src:.deps python3 \
  docs/thesis/measure_synthetic.py
```

Временной эксперимент использует текст из повторяющихся нейтральных ASCII-слов. Строка обрезается до заданного размера в байтах, поскольку ASCII-символ занимает один байт в UTF-8. Перед измерением выполняются пять прогревов. Для каждого из трёх размеров сохраняется 31 индивидуальное значение. Непосредственно измеряемый участок приведён ниже.

```python
samples = []
for _ in range(31):
    start = time.perf_counter_ns()
    result = analyzer.analyze(TextContent(text))
    elapsed_ms = (time.perf_counter_ns() - start) / 1e6
    samples.append(elapsed_ms)
assert result.complete
assert result.decision == 'ALLOW'
```

Фиксируются минимум, медиана и максимум, версия Python и контрольная сумма политики. Другие процессы стенда не изолировались, загрузка CPU не записывалась. Поэтому значения пригодны для описания конкретной серии и формирования гипотезы, но не для гарантии времени отклика в другой среде.

Для расширенного исследования следует фиксировать модель CPU, режим питания, фоновую нагрузку, распределение размеров и структуру текстов. Необходимо разделить холодный запуск, устойчивый режим, совпадения в начале и конце строки, а также входы для сложных regex.
