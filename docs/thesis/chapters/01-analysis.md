# 1 АНАЛИЗ ЗАДАЧИ КОНТРОЛЯ ИНФОРМАЦИИ В МЕССЕНДЖЕРАХ

## 1.1 Информационные потоки и точки наблюдения

Для рассматриваемой задачи выделяются три потока. Первый связан с файлами: пользователь выбирает документ, приложение открывает его и получает содержимое. Второй связан с текстом: пользователь вводит или вставляет данные в редактор сообщения. Третий связан с накоплением доступной истории: приложение поддерживает собственные файлы состояния либо предоставляет средство экспорта. Во всех случаях содержание может иметь одинаковые признаки конфиденциальности, но момент наблюдения и возможности вмешательства различаются.

В файловом потоке точкой принятия решения может стать запрос приложения к ядру на открытие объекта. Такая точка находится до получения нового файлового дескриптора и потенциально позволяет запретить соответствующую операцию. Однако открытие используется также для просмотра, индексирования и чтения метаданных. Из одного события нельзя достоверно вывести намерение отправить файл определённому адресату. В проекте поэтому фиксируется попытка доступа, а подтверждение отправки остаётся отдельным, отсутствующим свидетельством.

В текстовом потоке интерес представляет поле редактирования до нажатия кнопки отправки. Получение его содержимого обеспечивает раннее обнаружение, но не обязательно даёт право приостановить действие приложения. Между чтением поля и отправкой пользователь может изменить текст. Даже неизменившийся текст может передаваться сервису в рамках иной функции, например синхронизации состояния. Последняя возможность на исследуемом профиле не проверялась, поэтому локальное наблюдение не принимается за доказательство отсутствия сетевой передачи.

История сообщений имеет ретроспективный характер. Анализ существующей записи позволяет обнаружить совпадения с политикой и подготовить материал для разбора инцидента. Он не может отменить ранее выполненное действие. Локальные файлы приложения могут быть зашифрованы, представлены собственным форматом либо содержать только часть состояния. Существование каталога профиля не доказывает наличия открытой базы всей переписки.

Для файлов важно проверить реальный отказ в открытии, область наблюдения и задержку разрешения. Для текста — правильность привязки к полю, доступность содержимого и отсутствие сбора из посторонних элементов. Для истории — корректность схемы, сохранение порядка фрагментов и явный учёт пропусков. Общий процент срабатываний без указания источника не описывает качество системы. Сопоставление каналов приведено в таблице 1.

:::table 1|Источники данных и смысл результата
Канал|Наблюдаемое событие|Действие прототипа|Что не доказано
Файл|Запрос открытия в контролируемой области|Разрешение или отказ|Отправка и адресат
Поле ввода|Изменение выбранного черновика|Проверка и уведомление|Запрет отправки
JSON-экспорт|Запись в выбранном файле|Проверка истории|Полнота истории
Локальное tdata|Черновик и файловые сведения|Анализ и косвенные признаки|Архив всей переписки
:::

## 1.2 Сопоставление технических подходов

Выбор механизма контроля определяется тем, на каком этапе он предоставляет данные. Сетевой монитор может наблюдать соединения, но для анализа содержимого защищённого прикладного обмена потребуется иной источник открытого текста. В настоящей работе вмешательство в защищённые соединения исключено исходными ограничениями. Поэтому сетевое наблюдение не выбрано основным каналом контентного анализа.

Подсистема fanotify предоставляет уведомительные события и события, требующие решения о разрешении файлового доступа. Документация отдельно описывает чтение очереди и запись ответа для permission-событий [2]. Это позволяет связать решение анализатора с конкретной ожидающей операцией. Функции создания группы и установки меток определяют класс обработки и область наблюдения [3, 4]. В системном режиме проекта контролируются открытия на локальных файловых системах; служебные каталоги выделены в явно заданные исключения.

Другой класс механизмов представлен Linux Security Modules — инфраструктурой ядра для реализации контроля безопасности [5]. Такой подход потребовал бы отдельного исследования политики, установки и совместимости с конфигурацией стенда. В рамках работы не разрабатывается модуль ядра и не утверждается, что fanotify заменяет все функции LSM. Выбран пользовательский прототип с небольшим привилегированным участком, достаточный для проверки контентного решения на открытии.

Для взаимодействия с графическим приложением рассматривается AT-SPI. Интерфейс Text предоставляет операции доступа к текстовому содержимому доступного элемента [6]. Интерфейс Action описывает выполнение предоставленных элементом действий [7]. Эти возможности полезны для наблюдения, но сами по себе не устанавливают обязательный этап согласования отправки с внешним процессом. Поддержка доступности Qt зависит от интеграции приложения [8], поэтому гипотеза проверялась на реальном окне Telegram.

Готовые средства поиска признаков также не решают всю задачу автоматически. YARA описывает правила на основе строк и условий [9], а документация ClamAV рассматривает сканирование и способы его организации [10]. Для проектирования полезно разделение движка поиска и доставки данных. Однако обнаружение шаблона в файле не создаёт адаптер редактора Telegram и не делает доступным его хранилище. Сравнение проводится на уровне архитектурных функций, без заявления о превосходстве прототипа над этими средствами.

Выбран комбинированный подход: fanotify принимает решение о разрешении файлового открытия, AT-SPI передаёт содержимое выбранного поля для обнаружения и предупреждения, а адаптеры локальных данных и экспорта обеспечивают ретроспективный анализ. Свойства подходов обобщены в таблице 2.

:::table 2|Сравнение подходов для прототипа
Подход|Сильная сторона|Ограничение для задачи
fanotify|Связь ответа с файловой операцией|Нет смысла сообщения и адресата
AT-SPI|Доступ к выбранному редактору|Нет подтверждённого send veto
Экспорт клиента|Структурированные записи|Требуется действие пользователя
LSM|Интеграция с контролем ядра|Отдельная область разработки
Сетевое наблюдение|Сведения о соединениях|Не даёт открытый текст в выбранных рамках
:::

## 1.3 Модель угроз и доверительные границы

Защищаемыми объектами являются тестовые документы и текстовые фрагменты, которые правила относят к конфиденциальным категориям. Метки категорий используются как технические признаки. Они не устанавливают юридический режим документа и не заменяют классификацию владельца информации. Наличие слов о тайне в учебном предложении может вызвать правило, хотя предложение не содержит реального секрета.

Основной сценарий — ошибочное действие пользователя: выбор чувствительного файла или ввод фрагмента, который следует дополнительно проверить. Прототип может выявить некоторые намеренные действия, но не рассчитан на противодействие пользователю, способному остановить свой процесс агента или изменить доступный ему код. Пакетная установка защищает системные файлы правами root, однако полная устойчивость к обходам и административное применение политики с сервера остаются задачами развития.

Доверенными считаются ядро ОС, установленный gateway и конфигурация оператора. Мессенджер рассматривается как наблюдаемое приложение, но не как достоверный источник утверждения о завершённой отправке. Данные JSON поступают извне анализатора и валидируются. Пути вложений не используются для автоматического открытия: строка в экспорте не является полномочием на чтение произвольного объекта.

Граница между привилегированной настройкой и обработкой текста сокращается до C-компонента. В системной реализации C-брокер обслуживает группу fanotify, а Python-анализатор запускается от настроенного пользователя. Это снижает объём кода с расширенными правами, но не обеспечивает защиту от администратора машины или всех действий в пользовательском сеансе. Разделение прав следует оценивать вместе с доступом к конфигурации, исходным файлам и журналу.

Отдельную угрозу создаёт сбор данных. Чтение полей других приложений или сохранение переписки в диагностике превратило бы средство контроля в дополнительный источник утечки. Поэтому поле определяется явным маркером, чужие профили не исследуются, а журнал содержит решения без исходного текста. Имена файлов и пути тоже могут быть чувствительными и требуют ограниченного доступа.

За рамками покрытия остаются уже открытые FD, копии в исключённых областях, другие приложения, изображения с текстом, архивы и изменение окружения. Эти условия учитываются при воспроизведении эксперимента. В таблице 3 показана связь мер и остаточных рисков.

:::table 3|Угрозы и меры контроля
Сценарий|Мера прототипа|Остаточный риск
Выбор чувствительного файла|Анализ FD и ответ DENY|Копия вне области контроля
Ошибочный ввод|Проверка выбранного поля|Отправка до очередного опроса
Повреждённый экспорт|Проверка размера и схемы|Не все поля анализируются
Потеря worker|Закрытие группы, ошибка|Продолжение доступа после остановки
Остановка пользователем|Показ состояния|Принудительная защита отсутствует
:::

## 1.4 Требования к программному комплексу

Комплекс должен принимать текст и обычные файлы, применять настраиваемые правила, возвращать объяснимое решение и сохранять результат. Для файлов необходим механизм применения решения к открытию. Для истории нужен нормализатор структуры источника. Для поля ввода требуется явная привязка к элементу и прекращение работы при потере этой привязки.

Объяснимость означает возможность установить правило, категорию, оценку и диапазон найденного признака без записи сообщения в журнал. Анализатор должен различать завершённую проверку и ошибку получения данных. Если файл слишком велик или текст не декодируется, отсутствие findings не означает «нарушений нет». Для этого предусматриваются complete и reason, а политика определяет действие при ошибке.

Расширяемость относится к сбору и анализу. Новый мессенджер не должен требовать переписывания словарного движка. Новый анализатор не должен самостоятельно открывать окна Telegram. Связь обеспечивается общими структурами и контрактами. Наличие интерфейса или записи конфигурации при этом не объявляется готовой поддержкой клиента.

Нефункциональные требования включают ограничения объёма входа, времени и памяти служебных структур. Для лабораторного режима важны воспроизводимый запуск, диагностика и отсутствие постоянного root-Python. Приоритет отдаётся небольшой проверяемой реализации, а не максимальному числу функций без подтверждённого поведения.

Управляемость обеспечивается командами запуска, остановки, состояния и журнала. Пользователь должен отличать работающий монитор от завершённой разовой проверки. Административный контроль включает системные настройки с правами root и удалённую диагностику. Изменение политики и обновление пакета с сервера пока отсутствуют; пользовательские лабораторные настройки остаются отдельной областью. Трассировка требований к модулям и видам подтверждения приведена в приложении А.

## 1.5 Методика исследования и критерии результата

Сначала проверяются интерфейсы и формат входа, затем реализуется минимальный обработчик и проводится опыт с контролируемыми данными. Это особенно важно для хранилища. Предположение о SQLite не используется как основание для подключения к произвольному файлу. Сначала собираются ограниченные метаданные и сигнатуры, затем результат сопоставляется с документацией и исходным кодом.

На уровне ядра применяются модульные тесты порогов, повторных совпадений, обработки ошибок и минимизации аудита. Тесты протокола fanotify исследуют структуры событий и запись ответа. Интеграционные опыты подтверждают системный механизм на хосте. Ручное действие в реальном клиенте связывает событие с конкретным способом прикрепления файла.

Для текста используется искусственный материал. Ожидаемое решение определяется до выполнения команды по заданной политике. Такой корпус полезен для проверки реализации, но не представляет переписку организации. Доля совпавших ответов поэтому называется долей успешных функциональных проверок и не выдаётся за промышленную точность обнаружения утечек.

Ограничения исследуются отдельными пробами: отрицанием, изменением формы слова, необычным пробелом и символом другой письменности. Эти пробы не включаются в функциональную точность задним числом. Их назначение — показать, какие преобразования меняют решение и какие требования к нормализации ещё не выполнены.

Успех файлового опыта определяется фактическим ответом ядру; успех текстового — получением выбранного черновика и изменением решения; успех экспорта — корректностью схемы, счётчиков и правил. В каждом случае фиксируются условия и непроверенные операции. Единого универсального источника для трёх направлений не установлено, что обосновывает модульную архитектуру следующего раздела.

Требование локального источника не закрывается одним экспортом: значимы также сохранённые черновики и косвенные файловые признаки. При отсутствии надёжного запрета текста минимальный результат включает видимое предупреждение и журналирование. Оба действия проверяются отдельно от классификации.
