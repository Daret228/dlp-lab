# Центральный сервер в Docker Compose

Docker-вариант предназначен только для центрального сервера. Агенты остаются
DEB-службами на рабочих машинах. Нужны Docker Engine, Compose v2 и openssl.
На Debian 13 Docker и Compose устанавливаются командой
`sudo apt install docker.io docker-compose`. Административные команды далее
используют sudo; добавлять пользователя в группу docker не требуется.

Образ собирается локально, из разрешённого списка исходников; профили,
экспорты, токены и содержимое build/ в образ не попадают.

## Текущий стенд после переноса

**Сервер уже перенесён 5 ноября 2026. Повторно запускать миграцию не нужно.**
Два контейнера используют общую базу; агенты остаются DEB/systemd-службами.

| Назначение | Текущее значение |
| --- | --- |
| Панель на сервере | http://127.0.0.1:8766/ |
| HTTPS для другой машины | https://192.168.17.131:8767 |
| Compose-проект | `dlp-central-migrated` |
| Конфигурация | `/etc/dlp-lab/docker/compose.json` |
| База, токен, регистрации | `/var/lib/dlp-central`, владелец UID 10001 |
| Сертификат и ключ контейнера | `/etc/dlp-lab/docker/tls` |
| Образ после переноса | `dlp-lab-central:0.2.15-migration1` |
| Резервная копия до переноса | `/var/backups/dlp-central-before-docker-69ybd1j0` |

Команды для текущего сервера выполняются с явными `-p` и `-f`:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json ps
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json logs --tail 30
sudo dlp-admin-token
```

Для перезапуска обоих listener-ов:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json restart
```

Для остановки/возобновления замените `restart` на `stop`/`start`. Контейнеры
настроены на `restart: unless-stopped`: явно остановленный контейнер не считается
ожидающим автоматического запуска. Статус healthy проверяет доступность listener-а,
а не доставку событий конкретного агента.

Обычная команда `docker compose up` из репозитория использует **другой** compose.yaml
и создаёт отдельный сервер с новой базой. Для текущей установки она не нужна.
Не запускайте `update-central-ui.sh` и старые central systemd-службы: они не
обновляют контейнеры и могут конфликтовать с ними за порты.

Для агента команды не изменились:

```bash
systemctl status dlp-lab-files.service dlp-lab-forwarder.service --no-pager
sudo journalctl -u dlp-lab-forwarder.service -n 20 --no-pager
```

### Резервная копия текущего сервера

Блок ниже кратковременно останавливает **оба** listener-а, копирует всю базу
вместе с WAL и настройки, затем запускает контейнеры даже при ошибке копирования.
Агенты продолжают локальную защиту и накапливают очередь доставки.

```bash
sudo bash <<'SH'
set -eu
backup_dir=$(mktemp -d /var/backups/dlp-central-docker.XXXXXXXX)
chmod 700 "$backup_dir"
dc() { docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json "$@"; }
trap 'dc start' EXIT
dc stop
cp -a /var/lib/dlp-central "$backup_dir/state"
cp -a /etc/dlp-lab "$backup_dir/config"
printf 'Резервная копия завершена: %s\n' "$backup_dir"
SH
```

Копия содержит токены и ключи: не публикуйте её в GitHub. Для восстановления
останавливают оба контейнера, восстанавливают согласованную базу с владельцем
UID/GID 10001 и приватными правами (каталог 0700, файлы 0600), затем запускают и
проверяют панель. Восстановление старой копии удалит из текущей истории более
новые события, поэтому сначала сохраняйте копию текущего состояния.

### Обновление текущего Docker-сервера

Обновление DEB обновляет агента, но не серверный образ. Сначала сделайте backup
выше и получите проверенную версию исходников. Затем сохраните старый образ
под уникальным тегом и пересоберите используемый образ:

```bash
cd /home/roman/dlp-lab
saved_image="dlp-lab-central:before-update-$(date +%Y%m%d%H%M%S)"
sudo docker image tag dlp-lab-central:0.2.15-migration1 "$saved_image"
printf 'Предыдущий образ: %s\n' "$saved_image"
sudo docker build -t dlp-lab-central:0.2.15-migration1 -f docker/Dockerfile .
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json up -d --force-recreate
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json ps
```

Проверяйте вывод каждой команды; при ошибке сборки не переходите к пересозданию.
Тег здесь соответствует текущему compose.json; при смене тега обновляйте и
конфигурацию развёртывания. Обычный restart не заменяет образ уже созданных
контейнеров. После обновления войдите в панель прежним токеном и проверьте новое
тестовое событие. Возврат к старому образу допустим только при совместимости
формата базы; сценарий автоматического отката миграции не является системой
отката последующих обновлений.

Дальнейшие разделы описывают отдельную чистую установку и уже выполненный перенос.

## Автоматическая проверка Docker

Из корня проекта выполните:

```bash
sudo python3 scripts/test-docker.py
```

Сценарий собирает образ и создаёт отдельный временный Compose-проект на случайном
локальном порту. Проверяет healthcheck, HTTPS, вход, регистрацию, приём события
и сохранение данных после перезапуска. Токены не печатает. При завершении удаляет
только свои тестовые контейнеры и том; образ остаётся. Рабочий сервер не переносит.
Успех обозначается строкой PASS. Для постоянного сервера используйте шаги ниже.

## Новый отдельный сервер

Команды выполняются из корня проекта. Этот вариант создаёт новую базу и новый
токен. Он не переносит автоматически регистрацию уже работающих агентов.
По умолчанию используется https://127.0.0.1:8876, чтобы не занимать порт 8766
текущего systemd-сервера. Самоподписанный сертификат ниже — для локальной пробы.

```bash
mkdir -p build/docker-tls
chmod 700 build/docker-tls
openssl req -x509 -newkey rsa:3072 -nodes -days 365 \
  -subj '/CN=localhost' -addext 'subjectAltName=DNS:localhost,IP:127.0.0.1' \
  -keyout build/docker-tls/server.key -out build/docker-tls/server.crt
sudo chown -R root:10001 build/docker-tls
sudo chmod 750 build/docker-tls
sudo chmod 640 build/docker-tls/server.key
sudo chmod 644 build/docker-tls/server.crt
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose exec central python3 /app/entrypoint.py admin-token
```

Последняя команда показывает токен для входа в новую панель. Контейнер работает
от UID/GID 10001 без Linux capabilities, с файловой системой образа только для
чтения. Приватный ключ читается через отдельное монтирование только для чтения.
Не используйте UID 10001 для обычного пользователя этой машины. При rootless
Docker сопоставление UID другое: права каталога сертификатов нужно подготовить
для его user namespace отдельно; команды выше рассчитаны на обычный Docker Engine.

Для доступа из сети установите сертификат сервера с SAN, соответствующим его
DNS-имени/IP, и передайте публичный CA агентам. Вместо локального сертификата
поместите выданные server.crt/server.key в тот же каталог с теми же правами.
В корне проекта создайте .env (не коммитится):

```text
DLP_BIND_ADDRESS=192.168.17.131
DLP_HTTPS_PORT=8876
```

Выполните `sudo docker compose up -d`. Подключайте агенты по HTTPS, доверяя
этому CA. Не отключайте проверку сертификата на агентах.

## Регистрация агента и управление

```bash
sudo docker compose exec central python3 /app/entrypoint.py add-agent \
  --name test-debian --server https://192.168.17.131:8876 \
  --out /var/lib/dlp-central/test-debian.json
mkdir -m 700 -p build/docker-registration
sudo docker compose cp central:/var/lib/dlp-central/test-debian.json build/docker-registration/agent.json
sudo chmod 600 build/docker-registration/agent.json
sudo docker compose logs --tail 30 central
sudo docker compose restart central
```

Файл регистрации содержит индивидуальный секрет: передайте его только нужному
агенту и установите как /etc/dlp-lab/central-agent.json по OPERATIONS.md.
Для отзыва регистрации используйте `revoke-agent --id UUID` вместо `add-agent`.
Произвольное выполнение команд на рабочих машинах не добавляется.

Том central-data содержит SQLite, токен и регистрации. `docker compose down`
сохраняет том; **не используйте `down -v` для рабочего сервера**.
Healthcheck проверяет только доступность HTTPS-страницы внутри контейнера,
а не доставку событий. Внутренний healthcheck не проверяет доверие сертификату;
агенты и проверка ниже проверяют его штатно.

## Проверка

```bash
sudo docker compose config --quiet
sudo docker compose ps
sudo curl --cacert build/docker-tls/server.crt https://127.0.0.1:8876/ -o /dev/null
```

Для сертификата, выданного CA, передайте curl файл CA. После регистрации
тестового агента выполните файловый опыт: public разрешён, secret заблокирован;
убедитесь, что новое событие именно этого устройства появилось в панели.
Перезапустите контейнер и проверьте, что устройство, событие и токен сохранились.

В репозитории есть тест entrypoint с настоящим HTTPS, проверкой 401, регистрацией,
доставкой события и повторным запуском на той же базе. Это не заменяет проверку
сборки образа и томов в Docker Engine.

## Обновление и резервная копия

Перед обновлением остановите контейнер и сохраните согласованную копию тома:

```bash
sudo docker compose stop central
mkdir -m 700 -p build/docker-backup
sudo docker compose cp central:/var/lib/dlp-central build/docker-backup/
sudo docker compose up -d --build
```

Копия содержит секреты, храните её с ограниченным доступом. Для переноса
существующего systemd-сервера сначала остановите оба его listener-а, сделайте
согласованную копию /var/lib/dlp-central, восстановите её в том с UID/GID 10001,
правами каталога 0700 и приватных файлов 0600, настройте прежний адрес и CA.
Не запускайте независимые копии базы как один сервер: их регистрации и история
начнут расходиться. Текущий стенд перенесён отдельным сценарием ниже,
с сохранением исходного каталога базы вместо копирования в новый том.

## Перенос текущего стенда с systemd без смены адресов

Для стенда с локальным HTTP127.0.0.1:8766 и HTTPS192.168.17.131:8767:

```bash
cd /home/roman/dlp-lab
sudo python3 scripts/migrate-central-docker.py
```

Сценарий проверяет текущие настройки и доступность обоих listener-ов, собирает
образ до остановки служб, делает согласованную резервную копию базы и TLS в
/var/backups/dlp-central-before-docker-*, затем запускает два контейнера с общей
базой /var/lib/dlp-central. Владельцем базы становится UID 10001. Сохраняются
сертификат, токен, зарегистрированные устройства и прежние адреса.

Для сохранения HTTP исключительно на loopback используется host network:
контейнер local слушает 127.0.0.1:8766, контейнер https —192.168.17.131:8767.
Это Linux-вариант миграции, отдельный от обычного bridge compose.yaml.
Init-процесс передаёт сигналы остановки Python. Оба контейнера работают без
capabilities, с read-only rootfs; writable только база и временный каталог.

После успешной проверки старые две systemd-службы отключаются от автозапуска.
Файловая защита и отправщики не останавливаются. Во время переключения сервер
кратковременно недоступен; агенты используют свою очередь доставки.
При ошибке после остановки сценарий останавливает тестируемое развёртывание,
возвращает владельца текущей базы и запускает старые службы. Старой резервной
копией база не заменяется, чтобы сохранить события, принятые при переключении.
При ошибке самого отката сценарий завершается ошибкой: необходимо проверить
состояние служб, не запускать одновременно оба варианта вручную.

Управление после переноса:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json ps
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json logs --tail 30
sudo dlp-admin-token
```

Не запускайте старые central systemd-службы параллельно. Пакетные команды,
использующие sudo -u dlp-central для доступа к базе, после изменения владельца
заменяются вызовом entrypoint в контейнере local. Например:

```bash
sudo docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json exec local python3 /app/entrypoint.py add-agent --name new-device --server https://192.168.17.131:8767 --out /var/lib/dlp-central/new-device.json
```

Для резервной копии после переноса остановите ОБА контейнера, скопируйте
/var/lib/dlp-central в приватный каталог, затем запустите оба контейнера.
Сценарий не выполняет повторный перенос при наличии /etc/dlp-lab/docker.
5 ноября 2026 пользователь выполнил перенос рабочего стенда: PASS, оба
контейнера запущены, прежние адреса, сертификат, токен, устройства и история
сохранены. Дополнительно проверены HTTP200 панели и inactive/disabled старых
серверных служб. Автоматический откат и перезагрузка хоста ещё не проверены.

## Повторные открытия одного файла (0.2.17)

Новые файловые события передают случайный идентификатор группы. Сервер объединяет
их в одну строку только в пределах одного устройства, мессенджера и одинакового
результата анализа/применения. Под строкой показано «Попыток открытия: N».
Пути и содержимое файлов серверу не передаются. Исходные события остаются
в SQLite и локальном журнале; API сохраняет events и дополнительно выдаёт event_groups.

Количество относится к последним200 исходным событиям сервера, не ко всей истории
и не к количеству отправок. Старые записи без идентификатора не объединяются
по догадке. Разные решения, категории или полнота анализа отображаются отдельно.
Служебные события доставки уведомлений по-прежнему скрыты по умолчанию; их можно
включить отдельным флажком для диагностики. Уведомления рабочего стола не менялись.

Для текущего перенесённого стенда подготовлен сервер-first updater:

```bash
cd /home/roman/dlp-lab
sudo python3 scripts/update-grouped-events.py
```

Он собирает образ dlp-lab-central:0.2.17, сохраняет прежнюю Compose-конфигурацию,
пересоздаёт оба listener-а, проверяет healthy и аутентифицированный API с группами.
При ошибке серверного этапа возвращает прежнюю конфигурацию/образы. После успеха
устанавливает build/dlp-lab_0.2.17_amd64.deb с сохранением политики и перезапускает
системный отправщик. При ошибке apt новый сервер остаётся совместимым со старым
агентом; исправьте ошибку установки, не удаляйте очередь. Миграция схемы БД не нужна.
После PASS обновите страницу и повторите прикрепление тестового файла. Краткий
перерыв сервера/файловой службы возможен при обновлении. Другие агенты обновляются
своими совместимыми DEB отдельно; для Debian12 новой сборки пока нет.

Сначала обновляйте сервер: старый сервер отклоняет новое поле access_group.
Уже подтверждённые сервером записи не пересылаются заново. Пользовательские
отправщики, если они включены, после обновления DEB требуют отдельного restart.
