# Контекст проекта DLP Lab

Последнее обновление: **2026-10-27**.
Назначение: рабочая память проекта между сессиями. Читать перед продолжением;
пополнять после значимых изменений. Это сводка, а не замена проверке кода и среды.

## 1. Цель и формулировка руководителя

Руководитель предложил тему:
**«Разработка системы контроля утечек информации в мессенджерах, используемых
под управлением ОС Linux»**. Исправлена только опечатка «пож». Окончательное
утверждение названия ВКР не подтверждено.

Состав системы по руководителю:

1. Контроль локальных данных сообщений десктопных мессенджеров: чтение и
   нормализация доступных баз/хранилищ.
2. Контроль и перехват попыток загрузки файлов в мессенджеры.
3. Контроль ввода в текстовые поля через контекстный поиск или машинное обучение.

Продуктовая цель: инструмент уровня endpoint-DLP для Linux, свободно
распространяемый, расширяемый и контролируемый администратором. Мотивация —
доступность для организаций, которым недоступны дорогие коммерческие DLP.
Пользователь выбрал MIT; добавлены LICENSE и Debian copyright. Пакет собирается
локально, публикация релиза и полный аудит происхождения зависимостей не выполнены.

Новая формулировка шире прежней темы о предотвращении утечек через desktop
мессенджеры. Она включает обнаружение, аудит и доступное предотвращение.
Это не отменяет интерес пользователя к реальному запрету отправки текста,
но не позволяет объявлять мониторинг гарантированным предотвращением.
Не сводить весь проект к одной сложной задаче veto Telegram: нужны все три канала.

Уточнение руководителя, переданное пользователем **2026-10-09**:
- Локальная база обязательна: экспорт может не содержать полезные сведения,
  включая косвенные информативные признаки. JSON-адаптер остаётся дополнительным
  инструментом и не закрывает требование контроля локального хранилища.
- Если запрет отправки реализовать не получится, необходимы **информирование
  и журналирование**. Наблюдение без этих двух результатов недостаточно.
  Адресат информирования и набор косвенных признаков пока не конкретизированы.
- Это уточнение требований, не подтверждение новых функций и не разрешение
  само по себе обходить защиту хранилища или изменять клиент. Позднее пользователь
  отдельно разрешил offline-чтение собственного тестового tdata (см. раздел 2),
  и локальный черновик успешно прочитан. 2026-10-09 показ тестового предупреждения
  подтверждён пользователем, событие есть в журнале; сквозной опыт с живым
  AT-SPI-полем также подтверждён 2026-10-09 (ALLOW → BLOCK → видимое предупреждение).

## 2. Обязательные рамки

- Linux endpoint, первые целевые клиенты — Telegram Desktop и eXpress Desktop.
- Только собственные тестовые системы и аккаунты. Не читать чужие профили.
- Не использовать глобальный keylogger, перехват всех клавиш, TLS MITM,
  расшифровку трафика, уязвимости, внедрение кода или обход защиты хранилищ.
- Не предполагать, что база — SQLite или что её можно расшифровать.
  Недоступность данных документировать. Анализировать безопасно, read-only.
- GUI-фреймворк не должен определять архитектуру ядра; нужны адаптеры.
- Разделять Detection, Collection, Normalization, Analysis, Policy,
  Enforcement, Audit. Веса, пороги и правила — в конфигурации.
- Для первого MVP ML был расширением. По прямому указанию пользователя
  2026-10-18 обучаемый ML теперь обязателен и является текущим приоритетом.
  Словари и regex остаются самостоятельным слоем анализа.
- CLI/daemon сначала; администраторский GUI позднее. Управление администратором
  остаётся требованием даже до GUI: политики, управление агентом, журнал.
- Root использовать только там, где требуется. Не расширять существующий sudo
  до произвольного запуска команд.
- **2026-10-09 пользователь прямо запретил менять Telegram («не меняй»).**
  Отдельная изменённая сборка исключена из текущего плана. Исследовать внешний
  reader. Затем пользователь явно разрешил обработку зашифрованной копии своего
  тестового хранилища и локального ключа без подбора пароля и извлечения сетевых
  ключей авторизации («делай» в ответ на конкретный вопрос по ADR-007).
  Это узкое исключение прежнего ограничения; изменение клиента запрещено.
  Пользователь подтвердил: локального код-пароля нет. Ключи/текст не журналировать.

## 3. Реализовано и доказано

| Подсистема | Состояние | Граница результата |
|---|---|---|
| Content Analyzer | Dictionary, Regex, Context; интерфейс ML; TextContent/FileContent | UTF-8 и извлечение текста PDF/DOCX с лимитами; без OCR, других Office и произвольных архивов; см. раздел 19 |
| Policy Engine | YAML, валидация, веса/пороги, ALLOW/WARN/BLOCK, on_error | Решение отдельно от фактического enforcement |
| Аудит | JSONL с метаданными и findings/offsets | Исходный текст не пишется; пути могут быть чувствительны |
| fanotify | Установлен native broker + FAN_MARK_FILESYSTEM; запуск подтверждён на реальном ядре | /, /tmp, /home с исключениями; запрет TXT вне watch подтверждён через скрепку и перетаскивание; см. раздел 37 |
| Process adapters | Telegram/executable, UID, starttime, device/inode; eXpress scaffold | Не аттестация бинарника, не доказательство намерения отправить |
| Корреляция | Группировка повторных open по процессу/файлу, 5 с, до 1024 ключей | access_only; каждое открытие анализируется заново |
| Telegram-файлы | Реальный ручной опыт: 4 DENY секретного файла, 4 ALLOW обычного | Выбор вложения из тестового каталога; send_confirmed=false |
| Telegram-текст | AT-SPI монитор выбранного поля; сквозной опыт 2026-10-09: ALLOW → BLOCK, видимое предупреждение и journal | observe_only; send_blocked=false, отправка не запрещена |
| Хранилища сообщений | Инвентаризация/stat, JSON-адаптер; прямой offline-reader локального черновика tdata → TextContent → ContentAnalyzer | Реально проверены ALLOW/WARN/BLOCK и BLOCK с разметкой, FF06/writer 7002008–7002009; полная история/вложения не читаются |
| Локальные сведения о файлах | Offline-reader file locations; 7 синтетических тестов и реальный опыт: одна запись исходного тестового файла, размер/mtime совпали | Запись копии после «Сохранить как» не найдена; отправка и содержимое не определяются |
| Управление агентом | CLI agent start/stop/status/logs/export/local/notification-test, user systemd; local разово при закрытом клиенте | Нет защиты от пользователя, автозапуска, центрального управления или admin UI |

## 5. Важные особенности запуска

Из корня проекта:

```bash
make test
make privileged-test
PYTHONPATH=src:.deps python3 -m dlp.cli processes
sudo -n /usr/local/libexec/dlp-lab/fanotify-gateway
```

Текущий `config/processes.yaml`: mode=messengers; Telegram включён, eXpress выключен.
Режим all нужен для опыта блокировки cat; после смены режима перезапустить monitor.
Журнал хранить вне watch. WARN файлового монитора пока разрешает открытие.
Завершение worker снимает наблюдение (fail-open). Автозапуска нет; команды agent создают transient user systemd services.
Последний файловый опыт агент остановил. Пользователь мог запускать другие процессы:
перед новым опытом проверять текущее состояние, не считать старые PID актуальными.

Для AT-SPI Telegram должен быть **полностью завершён** и запущен так:

```bash
QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1 /usr/bin/telegram-desktop
```

Обычный перезапуск через иконку может потерять флаг. Уже наблюдалась ошибка found 0:
у нового процесса флаг отсутствовал и accessibility tree был пустым. Это проверено,
а не предположение о неправильном вводе пользователя.

Подготовить в собственном тестовом чате черновик с уникальным `DLP_TEST`, не отправляя.
В другом терминале:

```bash
cd /home/roman/dlp-lab
PYTHONPATH=src:.deps python3 -m dlp.cli text-monitor --marker DLP_TEST --seconds 120
```

Поиск поля ждёт до 30 секунд. После привязки маркер можно удалить, текст менять;
окно/элемент должны оставаться доступными. Поле проверяется каждые 300 мс.
При нескольких подходящих полях агент не выбирает произвольное. Root не нужен.
Монитор ограничен одним выбранным объектом, а не всеми полями/аккаунтами Telegram.
Очищение поля не считается событием отправки. BLOCK в журнале не останавливает send.
Проверка возможностей: `scripts/probe-telegram-ui.py --marker DLP_TEST` с PYTHONPATH.

## 6. Результат исследования запрета отправки

См. `docs/decisions/004-text-send-enforcement.md`.
В изученных AT-SPI интерфейсах нет синхронного permission hook для сообщения.
EventListener уведомляет; Action вызывает действие. Они не обязывают Telegram
ждать решения внешнего агента. В изученном upstream dev коде очистка поля идёт
после вызова отправки; это исследование исходников, не идентификация нашей сборки.

Автоочистка черновика обсуждалась пользователем, но не реализована и не выбрана:
есть гонка с Enter/кнопкой, риск потери текста. Перехват одной клавиши не покрывает
другие способы отправки. Частый polling, убийство клиента или поздняя блокировка
сети не превращают подход в гарантированный veto.

Реальный veto требует контролируемого пути отправки: проверенный неизменяемый
снимок, отказ при BLOCK/timeout, покрытие всех способов send. Отдельный TDLib-клиент
контролирует только собственные отправки, а не обычный Telegram Desktop.
Также отдельно нужно исследовать синхронизацию черновиков: запрет send не доказывает,
что текст до этого не передавался сервису. На профиле пользователя это не исследовалось.
