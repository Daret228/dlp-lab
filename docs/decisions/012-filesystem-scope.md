# ADR-012: файловый контроль вне одного каталога

Дата: 2026-10-19. Статус: реализовано и установлено 2026-10-19; запуск проверен на реальном ядре,
сквозной опыт блокировки Telegram вне watch ещё не выполнен. Пользователь явно поручил расширить
контроль за пределы watch. Клиент Telegram не изменяется.

## Решение и область

Новый фиксированный `native/filesystem_launcher.c` использует
`FAN_OPEN_PERM` + `FAN_MARK_FILESYSTEM`. При старте читает `/proc/self/mounts`,
открывает корни, исключает повторяющиеся st_dev и ставит метки только после
готовности Python. При ошибке хотя бы одной выбранной метки запуск прекращается.
`monitor_started` появляется только после подтверждения установки всех меток.

Выбираются ext2/ext3/ext4, xfs, btrfs, overlay, vfat, exfat, ntfs3; tmpfs только
для /tmp, /home и точек внутри /home. Вложенные каталоги этих файловых систем
входят в область независимо от глубины. FUSE, сетевые, виртуальные файловые
системы, /dev/shm и отдельный tmpfs /run не включены. Новые файловые системы
после старта требуют перезапуска. Поддержка перечисленных типов в конкретном
ядре проверяется при установке метки; реальные опыты со всеми типами не проведены.
Метка файловой системы распространяется и на её другие монтирования; это
шире одной точки монтирования. Область не равна «все файлы компьютера».

[fanotify_mark(2)](https://man7.org/linux/man-pages/man2/fanotify_mark.2.html),
[fanotify(7)](https://man7.org/linux/man-pages/man7/fanotify.7.html).

## Граница привилегий

Широкий fanotify FD нельзя передавать пользовательскому коду: он получает
дескрипторы событий, в том числе файлов других пользователей. Поэтому FD
остаётся только у небольшого native broker, работающего как root. Python,
анализаторы и сторонние парсеры выполняются как roman (UID/GID 1000), без
supplementary groups и с no_new_privs. У Python нет широкого fanotify FD.

Broker не принимает аргументы, очищает окружение, запускает только фиксированный
Python после сброса прав в дочернем процессе. До передачи файла проверяет все
четыре UID в /proc/PID/status, точный путь /opt/telegram-desktop/Telegram и
st_dev/st_ino исполняемого файла. Эталон берётся при запуске; после обновления
Telegram монитор нужно перезапустить. Это идентификация процесса, не аттестация
бинарника и не доказательство отправки. В данной версии привилегированный
список содержит только Telegram UID 1000; добавление eXpress требует отдельного
изменения и установки broker. Python-фильтр из processes.yaml дополнительно
сужает область; mode=all в широком режиме запрещён.

Остальные обращения сразу разрешаются без чтения содержимого и без передачи
файлов Python. Неустановленная личность разрешается с сигналом неполного покрытия,
чтобы не запрещать системные операции вслепую. Это явный возможный пропуск.
Broker использует только /proc-метаданные, stat/readlink, fanotify и локальный
socketpair; нет команд shell, разбора документов, чтения их текста или
произвольного открытия путей по запросу Python. Клиентский протокол принимает
только ALLOW/DENY для ранее выданного токена. Корневой процесс не dumpable,
no_new_privs установлен. Расширения sudoers до произвольных команд нет.

## Анализ и исключения

Через SOCK_SEQPACKET/SCM_RIGHTS передаётся read-only event FD. Python сохраняет
существующий анализ текста/PDF/DOCX, лимиты и политику. Отдельный поток принимает
события и подтверждения, основной выполняет анализ с SIGALRM. Дескрипторы не
наследуются парсерами. Открытия библиотек/временных файлов парсеров разрешаются
broker как обращения других процессов; само-блокировки Python при старте нет.

Явно исключены /usr, /opt, /etc, /bin, /sbin, /lib, /lib64,
/home/roman/.cache, /home/roman/.config, /home/roman/.local/share/TelegramDesktop,
/home/roman/.local/share/fonts и /home/roman/.fonts вместе с потомками.
Проверяется путь event FD с границами компонентов, а не исходное имя ссылки.
Эти исключения нужны для работы клиента и отсутствия анализа служебного профиля.
**Помещённый туда документ также исключён.** Это известная граница лабораторного
решения. Пути пока заданы кодом; панель их не редактирует. Поддержка произвольных
portable-профилей/других HOME не реализована. Исключения по альтернативным путям
bind mount отдельно не исследованы.

## Ошибки и подтверждение запрета

До 128 ожидающих событий у broker и до 128 в очереди Python. Переполнение
очереди запрещает соответствующий выбранный доступ; предел ожидания broker —
30 секунд с монотонными часами. Поздний ALLOW не отменяет уже применённый DENY.
Broker подтверждает результат после успешного ответа ядру; Python записывает
фактический enforcement отдельно от решения анализатора. Без подтверждения
не пишется успешное применение запрета. Сводные сообщения filesystem_coverage
отражают неизвестные процессы, переполнения и вынужденные запреты.

При отключении worker ожидающие операции получают DENY, затем группа закрывается.
При аварийном уничтожении broker закрытие группы ядром снимает контроль (fail-open).
После остановки новые открытия не контролируются. Зависший worker завершается
принудительно после ограниченного ожидания. Защиты агента от владельца сеанса нет.

Открытые до запуска FD, mmap, данные в памяти, изменение файла после анализа,
передача через другие процессы/порталы и гонки идентификации не обеспечивают
гарантированного контроля отправки. Не заявляется покрытие всех путей загрузки.

## Установка и проверка

Для уже установленного gateway:

```bash
sudo /usr/bin/env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin /bin/bash /home/roman/dlp-lab/scripts/update-fanotify-access.sh
```

Сначала остановить files через панель или `scripts/dlp agent stop files`.
Скрипт проверяет защищённые каталоги и visudo, собирает из снимка исходника,
сохраняет старый бинарник как fanotify-gateway.previous и атомарно заменяет
fanotify-gateway. Правило sudoers не меняется. Для новой установки используется
обновлённый install-fanotify-access.sh. После установки `make privileged-test`
проверяет запуск, UID/capabilities/no_new_privs, отсутствие fanotify FD у Python,
доступ постороннего cat во вложенном каталоге и снятие контроля. Сам по себе
этот smoke test не доказывает запрет Telegram.

Подготовленный ручной опыт после установки:

1. Перезапустить backend панели после обновления кода, затем запустить files в панели. Ожидаются «Локальные файловые системы» и
   monitor_started с scope=local_filesystems, а не direct_children.
2. В собственном тестовом чате выбрать через скрепку обычный файл и синтетический
   секретный файл из build/filesystem-demo/nested. Ожидание: ALLOW и DENY.
   Отправлять файлы не требуется.
3. Повторить PDF/DOCX и файл из другой папки. Сопоставить видимый результат с
   enforcement в журнале. Отдельно проверить drag-and-drop, новые диски и
   перезапуск Telegram; эти сценарии пока не проверены.
4. Остановить files. Ожидается снятие контроля.

Автоматически проверены компиляция с -Werror и hardening, протокол SCM_RIGHTS,
проверка UID/path/inode, DENY и поздний ALLOW после тайм-аута на эмуляции ядра,
неблокирующая обработка посторонних открытий, границы исключений, переполнение,
подтверждённый enforcement и отсутствие ложной записи при потере ACK.
Эти проверки не заменяют реальный fanotify/Telegram-опыт.
