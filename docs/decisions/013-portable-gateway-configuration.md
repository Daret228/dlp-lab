# ADR-013: защищённая конфигурация файлового gateway

Дата: 2026-10-20. Статус: исходники реализованы и проверяются; установка новой
версии broker на стенде отдельно фиксируется в PROJECT_CONTEXT.md.
Поручение пользователя: проверить файловый канал и убрать привязку к одному ПК.

## Конфигурация и граница прав

Фиксированный установленный gateway по-прежнему не принимает аргументы запуска.
Он читает /etc/dlp-lab/gateway.conf, например:

```ini
uid=2042
gid=2042
home=/home/alice
project=/srv/dlp-lab
telegram=/opt/telegram-desktop/Telegram
exclude=/usr
exclude=/opt
exclude=/etc
exclude=/home/alice/.cache
exclude=/home/alice/.config
exclude=/home/alice/.local/share/TelegramDesktop
```

Это строгий формат key=value, не shell/YAML: подстановок и команд нет. Все пять
основных полей обязательны, повторы/неизвестные ключи запрещены. exclude может
повторяться до 32 раз; ноль исключений означает явно пустой список. Не допускаются
root UID/GID, управляющие символы, относительные пути, .., /./, двоеточия,
обратные слеши, завершающий слеш; исключение всего / запрещено. Пробелы и Unicode
в путях допустимы. Лимит файла 64 КиБ, пути 4095 байт. UID, основной GID и HOME
должны соответствовать системной записи passwd. Telegram остаётся исполняемым
файлом root, недоступным для записи обычному пользователю.

/etc, /etc/dlp-lab и файл проверяются на root-владельца и отсутствие записи
группой/остальными. Символические ссылки не следуются, файл должен быть обычным
и иметь одну жёсткую ссылку. При проблеме broker не ставит метки и не объявляет
готовность. /etc/dlp-lab/gateway.lock, также защищённый root, удерживается broker
до завершения. Установщик берёт тот же exclusive flock: второй экземпляр и
обновление работающего нового broker отклоняются. Для миграции старого broker
без lock есть дополнительная проверка его процесса. Ранее созданные transient
user-units продолжают использовать прежний фиксированный путь gateway.

Конфигурация читается однократно при старте. После изменения нужен перезапуск.
Корневой код не запускает shell, не импортирует проект и не разбирает документы.
Python получает только event FD выбранного процесса и параметры своей среды;
не получает группу fanotify. Исключения передаются Python из защищённой
конфигурации. Прежний установленный broker совместим с новым Python: до обновления
используется прежний набор исключений, сформированный относительно HOME.

Если путь Telegram тот же, но inode/dev исполняемого файла изменился, native
broker разрешает обращение как непроверенное и сообщает target_changed_allowed.
Это повод перезапустить монитор, не доказательство контроля обновлённого клиента.
Фактический опыт обновления Telegram ещё не проводился; ветка проверена harness.

## Перенос и установка

`scripts/configure-fanotify-access.sh` — общий административный установщик;
install-fanotify-access.sh и update-fanotify-access.sh передают ему режим.
Доступные параметры: --user ACCOUNT, --project DIRECTORY, --telegram EXECUTABLE.
У чистой установки по умолчанию берутся владелец проекта, каталог репозитория
и канонический путь найденного telegram-desktop. При обновлении сохраняются
параметры установленной конфигурации и список исключений. Для миграции старой
установки они выводятся как при чистой установке. Значения не выполняются как код.

Перед первой установкой на другом ПК настроить пользовательский process adapter:

```bash
./scripts/dlp configure-processes --telegram /absolute/path/to/Telegram
sudo ./scripts/install-fanotify-access.sh --user alice --telegram /absolute/path/to/Telegram
```

configure-processes запускается без sudo, записывает текущий UID и канонический
Telegram в processes.yaml, сохраняет другие адаптеры и резервный .previous.
Повтор с теми же параметрами ничего не переписывает; конфликт/ошибка валидации
не заменяют конфигурацию. Изменение не перезапускает модули. При несоответствии
целевого пути broker и пользовательского process adapter новый worker откажется
стартовать, а не объявит работающим пустой фильтр.

На текущем стенде параметры уже совпадают. Для перехода на новую версию:

```bash
./scripts/dlp agent stop files
sudo ./scripts/update-fanotify-access.sh
```

Установка требует административного пароля и не включается в NOPASSWD.
Правило sudoers выдаётся выбранному числовому UID только на gateway без аргументов.
Проверяется visudo до/после; новая авторизация устанавливается последней и
откатывается при ошибке заключительной проверки. Бинарник и конфигурация заменяются
атомарно каждый отдельно под lock; это не транзакционная пакетная установка при
отключении питания. Сохраняются .previous для бинарника, config и правила.
При миграции со старого broker прежнего config ещё нет. Для полного отката
новой конфигурации нужно восстановить совместимые binary/config/sudoers; одиночный
откат только бинарника допустим при возвращении к старой скомпилированной версии.

## Прозрачность и измерения

monitor_started содержит область, исключения и источник конфигурации текущего
запуска. Панель показывает их в подробностях карточки и отдельно предупреждает
о неполном покрытии. Пути реально открытых файлов по-прежнему не выдаются API.
Для новой проекции нужен перезапуск backend панели.

В file_access_attempt добавлены analysis_ms и worker_elapsed_ms (монотонные часы).
Второе время начинается при обработке события основным потоком и заканчивается
после ответа/ACK, до аудита. Ожидание очереди и время до получения события не
включены; это НЕ полная задержка прикрепления в Telegram.

Остаются прежними ограничения: snapshot файловых систем при запуске, нет
автоматического добавления новых дисков, FUSE/сеть вне области, исключённые
каталоги являются обходом проверки документов, нет защиты кода/политики user-agent
от владельца сеанса. Свободно распространяемый установочный пакет, автозапуск и
полноценная проверка на втором Linux-хосте этим этапом не заявляются.
