# ADR-006: управление лабораторным агентом через user systemd

Дата: 2026-10-06. Статус: реализовано и проверено на стенде.

Проблема: отдельные CLI-проверки и мониторы не давали общего способа узнать,
какие процессы запущены, остановить их и посмотреть результаты.

Решение: тонкий Python-контроллер и scripts/dlp запускают фиксированные transient
user services для файлов, одного текстового поля и разового экспорта. Общий журнал —
выборка journalctl по трём unit. Это не внедрение постоянной root-службы.

Почему: systemd уже доступен на Debian-стенде, отслеживает процессы в cgroup,
предотвращает второй запуск unit и закрывает дочерние процессы при stop. Самописный
PID-файл потребовал бы защиты от PID reuse, гонок и потери дочернего процесса sudo.
Внешняя зависимость для других Linux: необходим работающий user systemd/journald;
прямые команды CLI остаются альтернативой.

Ограниченный gateway запускается только существующей sudo-командой без аргументов;
Python работает после сброса привилегий. Произвольные команды через контроллер
не принимаются. subprocess вызывается без shell, systemd environment expansion
отключён. Из окружения передаются только пути проекта и переменные desktop-сеанса.
Нет автоматического restart, автозапуска, новых sudoers и защит от пользователя.

SIGINT/код 130 считаются штатной остановкой мониторов, но не успехом анализа
экспорта. TimeoutStopSec=5s, KillMode=control-group. Failed состояние сохраняется
до явного stop/start; подробности остаются в журнале. Успешные transient jobs могут
выгружаться: inactive не сообщает результат прежнего задания, смотреть журнал.

Проверка 2026-10-06:

- Полный make test: 60 тестов, 58 прошли, 2 opt-in пропущены (9 новых unit-тестов).
- На хосте: запуск files, monitor_started с uid=1000/messengers, отказ второго start,
  остановка и inactive. Исправлена классификация штатного SIGINT как exit-code error.
- Text: запущен с отдельным тестовым маркером, достиг ожидания поля; status active;
  остановлен, inactive. Привязка к реальному черновику через новый launcher в этом
  опыте не проверялась, text_monitor_started не получен; прежний прямой AT-SPI опыт
  остаётся отдельным подтверждением.
- Export: искусственный пример дал ALLOW/WARN/BLOCK и summary в общем journal.
  Отсутствующий файл дал ошибку и failed status, затем тестовое состояние сброшено.
- Все запущенные нами модули после проверки остановлены.

Риски: journal может ограничивать частоту/объём и удалять старые записи, root и
пользователь имеют доступ согласно настройкам хоста; неизменность аудита не
гарантируется. Path/marker/служебные метаданные чувствительны, текст сообщений
не журналируется. Status показывает процессы, а готовность подтверждают события.
Ручные запуски вне этих unit не управляются. Смерть файлового worker — fail-open.
