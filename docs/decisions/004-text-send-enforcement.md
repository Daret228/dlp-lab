# ADR-004: запрет отправки текста

Дата: 2026-09-24. Статус: исследование завершено для выбранного AT-SPI подхода;
изменение архитектуры клиента не утверждено и не реализовано.

## Вопрос

Может ли внешний агент надёжно запретить отправку в штатном Telegram Desktop
через AT-SPI, одинаково для клавиатуры и кнопки, без глобальных keyboard hooks,
внедрения, подмены бинарников и вмешательства в шифрование?

## Установленные факты

1. В текущей установке после запуска с Qt accessibility флагом агент читает
   подготовленный editable/Text элемент. Проверен анализ секретного и обычного
   черновика. Это наблюдение, а не обязательный этап отправки.
2. AT-SPI EventListenerCB имеет тип возвращаемого значения void: это уведомление,
   а не permission request с ответом ALLOW/DENY.
3. AT-SPI Action предоставляет do_action и получение сведений о действии.
   Метод вызывает действие; он не является перехватчиком действий пользователя.
   EditableText позволяет менять содержимое, но не обеспечивает атомарную
   проверку текста и последующий запрет send.
4. В просмотренном upstream dev history_widget.cpp обработчик submit поля
   вызывает sendWithModifiers, а кнопка — sendButtonClicked. В пути отправки
   session().api().sendMessage предшествует clearFieldText. Следовательно,
   наблюдать исчезновение черновика слишком поздно для veto этого пути.

Пункт 4 — исследование upstream dev, а не доказанная идентичность установленному
бинарнику: версия/commit сборки не подтверждены. Ссылки dev изменяемы; перед
реализацией интеграции нужен фиксированный commit и проверка всех путей отправки.
Документированный внешний синхронный DLP-hook Telegram в исследованных источниках
не найден. Это ограниченный вывод, а не доказательство отсутствия всех возможных
интеграций или утверждение о других клиентах.

## Решение для текущего агента

Сохранить `enforcement=observe_only`, `send_blocked=false`. Решение политики BLOCK
в событии draft_analysis не означает блокировку отправки. Никакие сообщения
в рамках этого исследования автоматически не отправлялись и не удалялись.

| Вариант | Оценка |
|---|---|
| Чаще опрашивать поле/слушать text-changed | Улучшает реакцию, но не устраняет гонку с send |
| Стереть секретный текст через EditableText | Возможны потеря черновика и отправка до стирания; не принят |
| Перехватить Enter | Не покрывает кнопку, меню и другие пути; не принят |
| Заблокировать сеть после обнаружения | Гонка, очередь сообщений и блокировка остальных функций; не принят |
| Остановить/убить Telegram | Гонка и нарушение работы клиента; не принят |
| Штатный документированный pre-send hook | Предпочтительно, но не найден для исследованного Telegram |
| Явная интеграция в собственную сборку клиента | Потенциально даёт veto, требует отдельного решения и аудита путей отправки |
| Отдельный контролируемый клиент, например на TDLib | Потенциально даёт veto только для отправок через этот клиент |

## Что нужно для настоящего veto

```text
Запрос отправить → неизменяемый снимок сообщения → DLP → решение
                                     BLOCK/ошибка → не вызывать transport
                                     ALLOW       → передать именно этот снимок
                                     WARN        → явная политика подтверждения
```

Контроль обязан охватывать все согласованные пути: Enter, кнопку, меню,
отложенную отправку, редактирование сообщения, подписи к вложениям, повторы после
ошибки сети. Нельзя проверять снимок A, а отправлять изменённый B. Отсутствие ответа
агента/timeout должно запрещать отправку. IPC необходимо аутентифицировать,
политику и транспорт защитить от обхода в заявленной модели угроз.

TDLib — библиотека создания Telegram-клиентов, а не плагин, перехватывающий
сообщения уже работающего Telegram Desktop. Отдельное окно «проверить и отправить»
не защищает обычный Telegram, если пользователь продолжает отправлять напрямую.
Поэтому такой вариант меняет область исследования и не включается незаметно.
Исходное ограничение на изменение бинарников клиентов сохраняется: сборка
с интеграцией требует отдельного согласования этого архитектурного изменения.

Дополнительно: в upstream есть saveCloudDraft. Даже запрет send не обязательно
предотвращает передачу черновика сервису. Для утверждения «до выхода за endpoint»
нужно отдельно исследовать/контролировать синхронизацию drafts, captions и previews;
это не проверялось на пользовательском профиле.

## Критерии будущего приёмочного теста интеграции

- На BLOCK транспорт не вызывается ни для Enter, ни для кнопки.
- Быстрый ввод/вставка и немедленный send не обходят проверку.
- Изменение текста во время анализа требует нового решения.
- Недоступность DLP и timeout дают отказ, в том числе при повторной отправке.
- Все разрешённые способы отправки документированы; непокрытые явно исключены.
- Тесты на синтетических сообщениях и собственных аккаунтах, без обхода шифрования.
