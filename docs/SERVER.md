# Устройство системы и панель

Установка — [INSTALL](INSTALL.md), администрирование — [ADMIN](ADMIN.md),
модель угроз — [threat_model](threat_model.md).

## Компоненты

```text
Рабочая машина Linux
  Telegram / Signal
      ├─ открытие файла → fanotify → анализ → разрешение / отказ
      ├─ поле ввода → AT-SPI → анализ → предупреждение
      └─ локальные данные → отдельная проверка → результат
                       ↓
             журнал → отправщик и очередь
                       ↓ HTTPS
             сервер Docker → SQLite → веб-панель
```

| Источник | Получение данных | Реакция |
| --- | --- | --- |
| Файлы | fanotify, распознавание контролируемого executable | Разрешение или отказ в открытии |
| Вводимый текст | AT-SPI, доступное сфокусированное поле | Предупреждение и журнал, без запрета отправки |
| Telegram tdata | Закрытый тестовый профиль без код-пароля | Анализ поддерживаемого черновика и метаданных |
| Signal | Копия закрытой локальной базы, SQLCipher и штатный Keyring | Анализ сохранённых текстов |
| JSON-экспорт | Явно выбранный экспорт Telegram | Разовый анализ |

Анализатор BLOCK не доказывает применение запрета; файловое открытие не
доказывает сетевую отправку. Поле ввода и локальная база — разные источники.

Агент анализирует данные локально. Отправщик читает события из системного
журнала, хранит очередь на диске и передаёт минимизированную проекцию по
HTTPS с индивидуальным токеном устройства; токен администратора — только
для панели и административного API. Сервер хранит события в SQLite и
устраняет повторную доставку одного ID. Недоступность сервера не выключает
локальную защиту; успешный запуск отправщика не подтверждает доставку —
проверяйте новое событие в панели.

## Итоги файловых операций

Серия открытий одной версии файла (тот же мессенджер и пользователь,
независимо от PID) даёт одно событие `file_operation`. Пауза между
открытиями меньше 5 с сохраняет серию, максимум серии — 30 с; итог
уходит в очередь после 6 с тишины и обычно виден в панели через 15–30 с
после завершения. Незавершённый итог переживает перезапуск отправщика.

Итоговый статус: BLOCK выше WARN, WARN выше ALLOW; DENY сохраняется, если
хотя бы одно открытие было запрещено. Каждое открытие проверяется
отдельно — объединяется только отчёт; подробности остаются в системном
журнале агента. Повторная доставка не создаёт строку; позднее продолжение
обновляет тот же ID. Границы серии — эвристика, не доказательство нажатия
«Отправить»: разные файлы, версии и мессенджеры не объединяются. Старая
история не переписывается: записи с одним идентификатором группы панель
объединяет независимо от промежуточных решений. Выборка — до 200 записей.

Файловые события передают путь (до 4096 символов), идентификаторы правил,
анализаторов и причины — это отличает, например, гипотезу ML от неполной
проверки. Содержимое и совпавшие фрагменты не передаются. Имя видно в
строке, полный путь и правила — в «Подробнее»; поиск учитывает путь и
причину. Пути могут содержать персональные имена — доступ к панели и
копиям остаётся административным. В старых записях недостающие сведения
не восстанавливаются.

## Фильтр событий панели

Список «События» вместо галочки уведомлений:

- **Документы и предупреждения** (по умолчанию): файловые операции и
  проверки текста; скрыты уведомления, штатные события служб и ALLOW
  известных служебных путей. Файловые WARN/BLOCK/DENY, ошибки очереди и
  остановка проверки текста остаются видимыми. Под списком — счётчик
  скрытого и кнопка перехода в технический режим.
- **Все события**, **Файлы — все открытия**, **Текст и сообщения**,
  **Технические события**, **Уведомления** — по назначению.

Режимы сочетаются с решением, устройством, мессенджером, периодом и
поиском; «Сбросить фильтры» возвращает умолчание. Сводные карточки
отражают всю выборку, а не фильтр. Служебный путь — узкий список
(machine-id, recently-used.xbel и его временные варианты, стандартные
dot-файлы оболочки/сеанса непосредственно в `/home/USER`); это подсказка
интерфейса, не доказательство фонового действия. Неизвестные пути и
старые события без пути не скрываются. Данные не удаляются, политика
контроля не меняется.

## Канал политик

```text
Администратор → YAML + версия редактора → сервер: проверка схемы, CAS, SQLite
    ↓ явное задание apply_policy
Отправщик агента → HTTPS: своя политика → SHA256 и проверка схемы
    ↓ /run/dlp-admin-control/incoming/policy.yaml + Unix-сокет
Root-брокер → проверка схемы → резервная копия → атомарная замена policy.yaml
    ↓
Перезапуск файлового и сеансового контроля → диагностика → результат на сервер
```

Health передаёт хеш **дискового файла**, не удостоверение применённых
правил: состояние подтверждают новый `policy_loaded`, состояние сеансового
контроля и тестовое событие. Авария в середине применения может оставить
совпадающий файл и незавершённое задание — нужна диагностика и новое
задание. Изменение назначения заблокировано, пока применяется предыдущее;
выполненное задание не исполняется повторно. Брокер принимает только
фиксированные действия, не shell-команды.

## Исходники

`src/dlp/central.py` — приём, очередь, хранение; `src/dlp/central_ui.js`
и `central_page.html` — панель; `src/dlp/remote_control.py` — фиксированные
задания; `docker/entrypoint.py` — контейнер. Карта остальных каталогов —
в [DEVELOPMENT](DEVELOPMENT.md#проверка-и-ручной-запуск).
