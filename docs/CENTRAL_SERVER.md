# Центральный журнал: техническая инструкция

Для последовательной настройки с нуля используйте
[единое руководство по эксплуатации](OPERATIONS.md). Ниже сохранены также
лабораторные варианты запуска и история исправлений.

Доступно в исходниках и DEB. Для системного отправщика используйте версию
0.2.13 или новее: она включает исправления credentials, journald и диагностики.
Локальная защита запускается прежним способом. Следующие команды добавляют сбор
событий; они сами не включают анализаторы. Порты: локальная панель 8765,
центральный журнал по умолчанию 8766.

## Текущий стенд: Docker после миграции

С5ноября2026 сервер работает в двух контейнерах, агенты — в systemd.
[Текущие команды управления, регистрации, обновления и backup](DOCKER.md#текущий-стенд-после-переноса).
Панель: http://127.0.0.1:8766/; подключение удалённых агентов:
https://192.168.17.131:8767. Токен: `sudo dlp-admin-token`.
Старые central systemd units отключены; не включайте их параллельно Docker.

Разделы ниже сохраняют лабораторные и альтернативные systemd-сценарии.
Их `central init`, пути build/central-server и команды sudo -u dlp-central
не относятся к текущей базе Docker. Не выполняйте их для повторной настройки
уже перенесённого сервера. Исторические номера версий обозначают этапы реализации.

## Сервер на том же компьютере — отдельный лабораторный запуск

Из `/home/roman/dlp-lab`, однократно:

```bash
./scripts/dlp central init --state build/central-server
./scripts/dlp central add-agent --state build/central-server --name debian-test --server http://127.0.0.1:8766 --out build/central-agent.json
```

В первом терминале:

```bash
./scripts/dlp central serve --state build/central-server
```

Во втором терминале запустите отправку событий пользовательских служб DLP:

```bash
./scripts/dlp central forward --config build/central-agent.json --state build/central-queue
```

Для разового цикла добавьте `--once`. Для системной файловой службы используйте
`--system` и **другой** каталог состояния, например `build/central-system-queue`.
Нужны права чтения системного журнала. Отправщик работает каждые 15 секунд и
остаётся отдельным процессом; завершение Ctrl+C не останавливает локальную DLP.
Ошибки доставки сохраняют очередь. Все указанные данные в `build/` исключены из Git.

Откройте http://127.0.0.1:8766/. Токен администратора находится в поле `token`
локального файла `build/central-server/admin.json`. Введите его в поле страницы
и нажмите «Подключиться». Не публикуйте этот файл, конфигурацию агента и SQLite базы.
Устройство появится после регистрации; время связи заполнится после первого
успешного запроса. Даже пустая отправка обновляет время связи.

Первый сбор охватывает последние 5 минут journald. Дальше используется сохранённая
позиция. В центральной странице — последние 200 событий. BLOCK остаётся оценкой
анализатора; поле «Применение» отдельно отражает сообщённое модулем действие.
Статусы и события не доказывают отправку сообщений.

## Несколько машин

На сервере подготовьте доверенный TLS-сертификат для его DNS-имени и запустите:

```bash
./scripts/dlp central serve --state build/central-server --host 0.0.0.0 --cert /path/to/server.crt --key /path/to/server.key
./scripts/dlp central add-agent --state build/central-server --name second-linux --server https://dlp.example.org:8766 --out build/second-agent.json
```

Замените пример адреса реальным. Передайте **только конфигурацию соответствующего
агента** на его компьютер безопасным административным способом. Сохраните права
0600 и владельца пользователя отправщика. На машине должны быть исходники DLP
с этой командой. Запустите `central forward` с локальным путём конфигурации и
собственным каталогом очереди. Сертификат должен проверяться системным CA-хранилищем;
опции отключения проверки TLS нет. Автоматическая установка на удалённые машины,
раздача политик и отдельный DEB сервера пока не реализованы.

Отозвать доступ устройства (ID виден в панели):

```bash
./scripts/dlp central revoke-agent --state build/central-server --id DEVICE_ID
```

Старая конфигурация больше не сможет отправлять события, история останется.
Для новой регистрации создайте новую конфигурацию и новый каталог очереди.

Ограничения и решения: [015-central-event-collection.md](decisions/015-central-event-collection.md).

## Службы DEB 0.2.6

Один пакет содержит обе роли; включайте только нужную. При установке сервер и
отправщики не включаются автоматически. После настройки `enable --now` обеспечивает
автозапуск. Существующая файловая защита и ручные команды сохраняются.

Сервер (на серверной машине, пример только localhost):

```bash
sudo install -d -m 0755 /etc/dlp-lab
printf '%s\n' '{"host":"127.0.0.1","port":8766}' | sudo tee /etc/dlp-lab/central-server.json >/dev/null
sudo systemctl enable --now dlp-lab-central.service
```

Если на 8766 ещё работает лабораторный сервер из исходников, сначала завершите
его: `systemctl --user stop dlp-lab-central.service`. Это отдельная служба; её БД
из `build/central-server` автоматически не переносится. Новая системная служба
использует `/var/lib/dlp-central`, создаёт собственный admin.json и новую БД.
Перед регистрацией устройства дождитесь успешного запуска сервера.
Для сети укажите в JSON `host`, `port`, `cert`, `key`. Сертификат и ключ должны
быть доступны пользователю dlp-central; ключ не делайте общедоступным.

Регистрация устройства от серверной учётной записи:

```bash
sudo -u dlp-central dlp-agent central add-agent --state /var/lib/dlp-central --name linux-01 --server https://SERVER:8766 --out /var/lib/dlp-central/linux-01.json
```

Замените адрес сервера. Для опыта на одном компьютере допустим
`http://127.0.0.1:8766`. Передайте созданный файл именно на соответствующую машину.
Не используйте одинаковые учётные данные для разных компьютеров.

Отправщик системной файловой службы (на машине агента):

```bash
sudo install -o root -g root -m 0600 /path/to/linux-01.json /etc/dlp-lab/central-agent.json
sudo systemctl enable --now dlp-lab-forwarder.service
```

Служба запускается от dlp-forwarder; systemd передаёт токен через LoadCredential.
Её очередь `/var/lib/dlp-forwarder`. SupplementaryGroups=systemd-journal даёт
процессу доступ ко всему системному журналу, хотя сборщик читает только unit DLP.
Это стандартное разрешение journald, не изоляция доступа на уровне отдельных units.
Учётная запись без интерактивного входа; root-права процессу не выдаются.

Пользовательские модули (в пользовательском сеансе, без sudo):

```bash
install -d -m 0700 ~/.config/dlp-lab
install -m 0600 /path/to/linux-01.json ~/.config/dlp-lab/central-agent.json
systemctl --user daemon-reload
systemctl --user enable --now dlp-lab-forwarder-user.service
```

Та же машина может использовать свой токен в обоих отправщиках, но очереди
раздельные. User unit запускается при старте сеанса; системный — при загрузке ОС.
Временный отправщик лаборатории сначала остановите командой
`systemctl --user stop dlp-lab-forwarder.service`, чтобы не оставлять два сборщика.
Служба пользователя не включается и не перезапускается пакетными скриптами.
При обновлении пакета перезапустите её вручную.

Проверка: `systemctl status dlp-lab-central dlp-lab-forwarder` и
`systemctl --user status dlp-lab-forwarder-user`. Журналы — через соответствующий
`journalctl -u ...` или `journalctl --user -u ...`. Не запускайте лабораторный и
системный сервер одновременно на одном порту.

Удаление пакета останавливает системные службы; состояние, токены и служебные
учётные записи сохраняются даже при purge, чтобы не потерять аудит. Пользовательскую
службу перед удалением остановите через `systemctl --user disable --now ...`.
Автоматического переноса лабораторной БД, политик и ключей нет.

### Исправление credentials в 0.2.7

Используйте 0.2.7 или новее для системного отправщика. В 0.2.6 проверка владельца
обычной конфигурации ошибочно применялась к systemd LoadCredential: на стенде
системный менеджер передаёт root:root 0440 с доступом служебного пользователя.
Это приводило к ValueError ещё до сбора событий. В 0.2.7 специальный reader
применяется только пакетным entrypoint к фиксированному пути credentials службы,
проверяет владельца/тип/права и ограничивает размер; обычный CLI по-прежнему
отклоняет групповой доступ к конфигурации. Токен и регистрацию менять не нужно.
Если отправщик был остановлен для диагностики, после обновления запустите
`sudo systemctl restart dlp-lab-forwarder.service`.

### Сбор событий непривилегированного worker (0.2.8)

Для системного отправщика используйте 0.2.8 или новее. journald может помещать
записи пользовательского worker системной файловой службы в split user journal.
Поэтому системный сборщик выбирает `journalctl -u dlp-lab-files.service` без
`--system`: фильтр службы сохранён, но доступны оба типа файлов журнала.
Пользовательский отправщик по-прежнему использует `--user`. Существующая очередь
и cursor сохраняются; ручной сброс или повторная регистрация не нужны. После
обновления проверьте приём непустых пакетов: нулевой heartbeat сам по себе не
подтверждает правильность сбора.

## Дополнительный HTTPS-вход лаборатории

Для двух VM можно сохранить loopback HTTP8766 и добавить HTTPS8767 на конкретном
LAN IPv4 сервера. Оба процесса работают от dlp-central и используют одну SQLite
базу/тот же admin token; авторизация остаётся обязательной. Порт8766 не открывается
в сеть. scripts/install-central-tls.sh принимает IPv4 и каталог ca.crt/server.crt/
server.key, проверяет сертификат и соответствие ключа, устанавливает отдельную
system unit dlp-lab-central-tls. Повторная установка поверх существующей настройки
отклоняется. CA private key на серверную службу и агент не копируется.

Сертификат лаборатории нужно выпустить с IP SAN выбранного сервера. При смене
DHCP-адреса сертификат и bind адрес требуется обновить. На клиент передаётся только
CA certificate и его собственная конфигурация регистрации. Доверие CA следует
задавать только отправщику через SSL_CERT_FILE, а не всей ОС. Не обходить проверку
сертификата. Настройка firewall отдельно зависит от сети стенда; скрипт её не меняет.
Слушатель доступен тем машинам, которым доступен указанный LAN адрес и порт.
Это отдельный лабораторный unit в /etc; после обновления DLP его следует вручную
перезапустить, а перед удалением пакета — disable --now. Пакетные maintainer scripts
управляют только штатными units. Сертификат/ключ и CA — данные администратора,
не включаются в Git или DEB.

### systemd credentials на Debian 12 (0.2.10)

Debian12/systemd252 выдаёт credential-файл service-UID:root 0400 и каталог
service-UID:root 0500. Debian13 на стенде выдавал root:root 0440. С версии0.2.10
специальный reader принимает оба наблюдавшихся варианта, сохраняя фиксированный
путь службы, запрет symlink и ограничения размера. Service-owned файл с групповым
доступом или writable directory по-прежнему отклоняется. Обычный CLI config reader
не менялся. Обновлять токен, регистрацию или CA для этого исправления не нужно.


## Удалённая диагностика (0.2.12+)

Обновите сервер и системный отправщик агента до0.2.13: эта версия устраняет
ложную ошибку UID при диагностике мессенджеров, присутствовавшую в0.2.12. В таблице устройств
нажмите «Запросить диагностику», через30секунд — «Обновить». Задание ожидает
агента до15минут. Одновременно допускается одно ожидающее задание на устройство.
Агент получает задание сам по прежнему HTTPS-каналу: входящие порты и запросы
пароля на рабочем столе не нужны. Пользовательский forwarder не выполняет задания.

Результат содержит только названия фиксированных проверок и OK/ERROR/UNKNOWN/INFO.
Сырые журналы, токены, тексты и произвольные пути не передаются. «Выполнено»
означает получение отчёта, а не отсутствие ошибок; UNKNOWN означает непроверенный
аспект. Ограничения doctor сохраняются: доставка/очередь и session modules
этим заданием не проверяются. Проверки выполняются от dlp-forwarder, поэтому
недоступные ему ресурсы отражаются как UNKNOWN.

Задания доступны только администратору; агент видит и завершает только свои.
Сервер хранит время создания, срок, состояние и результат. Отчёт на агенте
сохраняется в SQLite до подтверждения сервером; повтор после потерянного ответа
не создаёт вторую запись. При сбое между проверкой и сохранением повторное
выполнение read-only проверки допустимо. Срок ограничивает начало проверки,
результат начатой проверки может прийти позже. Отдельные серверные часы должны
быть синхронизированы с агентом. UI показывает последние100 заданий, автоматическое
удаление истории ещё не реализовано. Старые агенты не исполнят запрос, срок истечёт.

Это первый этап управления. Применение политик, управление службами, обновление
DEB, одноразовая регистрация и привилегированный исполнитель пока НЕ реализованы.
Агент не исполняет shell, пути, скрипты или команды установки из ответа сервера.
Только в альтернативном systemd-развёртывании после обновления TLS listener нужно
перезапустить: sudo systemctl restart dlp-lab-central-tls.service.
