# Администрирование и обслуживание

Установка и обновление — [INSTALL](INSTALL.md). Команды ниже выполняет
администратор с sudo; остановка файловой службы кратковременно прерывает защиту.

## Консольное меню dlp-lab

Интерактивная обёртка над командами этого руководства: запустите `dlp-lab`
в терминале и выбирайте пункты цифрами; 0 — назад или выход. Меню само
определяет роль машины (сервер + агент или только агент) и скрывает
недоступные пункты. Действия, требующие root, вызывают sudo сами;
меняющие состояние (перезапуск защиты, резервная копия, обновление)
просят подтверждение.

| Пункт | Что делает |
| --- | --- |
| Статус стенда | версия пакета, состояние четырёх служб, доступность панели, контейнеры сервера |
| Диагностика агента | `dlp-agent doctor` |
| Добавить устройство | регистрация на сервере и сборка `connection.json` в `~/dlp-provision` с подсказкой следующих шагов |
| Службы агента | состояние, журналы files/forwarder, перезапуск защиты с подтверждением |
| Сервер | контейнеры, токен администратора, резервная копия, обновление стенда |

Меню не даёт новых прав: это только обёртка над теми же командами с
аргументами без shell. Источники проекта для пунктов «Добавить устройство»
и «Обновить стенд» ищутся в `DLP_LAB_REPO`, `~/dlp-lab`; без них меню
печатает команды для ручного выполнения.

Обычный пользователь агентом не управляет: `dlp-agent` отклоняет вызовы без
прав, локальной веб-панели нет, политика и службы принадлежат root.
Пользователю показываются только уведомления. Скрытие CLI — не граница
безопасности: граница — права системных файлов и служб. Пользователь с
sudo остаётся администратором ОС; процесс текстового контроля с его UID
технически может быть завершён владельцем сеанса, супервизор root его
восстановит.

## Службы

| Служба | Назначение |
| --- | --- |
| `dlp-lab-files.service` | Файловый контроль fanotify (привилегированный брокер, анализ — отдельным непривилегированным процессом) |
| `dlp-lab-session.service` | Системный супервизор текстового контроля |
| `dlp-lab-admin-control.service` | Фиксированные перезапуски и установка политики |
| `dlp-lab-forwarder.service` | Передача событий и состояния на сервер |

```bash
sudo dlp-agent doctor
sudo systemctl status dlp-lab-files.service dlp-lab-session.service dlp-lab-forwarder.service --no-pager
sudo systemctl restart dlp-lab-session.service
sudo journalctl -u dlp-lab-session.service -n 30 --no-pager
```

Не используйте `dlp-agent agent start/stop` в установленном пакете:
управление пользовательскими units запрещено. Второй файловый монитор
параллельно не запускается. Настройка процессов и каталогов —
`sudo dlp-lab-configure --wizard`.

Сеансовый супервизор ждёт активный графический сеанс настроенного
пользователя и запускает анализ с его UID, фиксированными путями и
очищенным окружением. При выходе из сеанса процесс останавливается,
при следующем входе запускается снова; упавший — перезапускается.

## Текстовый контроль

AT-SPI-монитор выбирает единственное видимое, сфокусированное
многострочное редактируемое поле внутри разрешённого процесса Telegram
или Signal. Парольные поля исключены; глобального перехвата клавиатуры
нет, маркер не нужен. При смене фокуса/чата выбор повторяется;
неоднозначное или недоступное поле не читается. Клиент должен
предоставлять AT-SPI-доступность (для Telegram администратор настраивает
запуск с `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1`); служба в уже запущенный
клиент не вмешивается.

Текст анализируется локально, в журнал уходит результат без содержимого.
При риске — уведомление. Запрет отправки текста не реализован. Локальные
базы и JSON-экспорт этой службой не сканируются.

Состояния в карточке устройства: «доступно выбранное поле» / «ожидает
доступное поле» / «недоступен» / «нет активного графического сеанса» /
«остановлен» / «восстановление». Без свежих данных более 2 минут контроль
не считается подтверждённым. Потеря связи не позволяет серверу отличить
выключенную машину от сетевой неисправности. Состояние «запущена» не
заменяет тест фактической блокировки.

## Управление с сервера

В карточке устройства: «Диагностика», «Перезапуск файловой защиты»,
«Перезапуск текстового контроля». Нужны свежая связь и работающая служба
admin-control. Панель запрашивает подтверждение — контроль кратко
прерывается. Доставка — обычно один интервал опроса (15 с), срок задания
15 минут. Результат — в разделе «Задания».

Отправщик обращается к root-сервису по Unix-сокету; сервис принимает
только фиксированные действия `restart_files/restart_session/install_policy`
— без shell, путей и пользовательских аргументов. Выполненный ID не
исполняется повторно; авария с неопределённым результатом считается
неуспехом и автоматически не повторяется. Успешный перезапуск означает
active у службы, а не доказательство блокировки или доступности поля.
Удалённая установка DEB не реализована.

## Политики

Рабочий файл агента — `/etc/dlp-lab/system/policy.yaml` (dpkg conffile;
при обновлении пакета сохраняйте изменённый через
`apt -o Dpkg::Options::="--force-confold" install ...`).

### Из панели

1. Раздел «Политики» → выберите устройство. Загрузится назначенный YAML;
   для первого назначения возьмите `config/policy.yaml` за основу.
2. Отредактируйте или загрузите файл (до 128 KiB). «Сохранить» меняет
   только назначение на сервере.
3. «Сохранить и применить» создаёт задание: нужны свежие сведения от
   агента и работающий root-брокер; файловая и сеансовая службы
   перезапускаются. Пока задание не завершено, назначение не меняется.
4. Проверьте результат задания, версию на диске и тестовое событие.

Сервер проверяет схему и конфликт версий редактора (CAS). Агент получает
только свою политику, сверяет SHA256 и схему. Обмен идёт через
`/run/dlp-admin-control/incoming/policy.yaml` (каталог root:dlp-forwarder
0770, файл 0640, симлинки и спецфайлы отклоняются). Брокер пишет только
`/etc/dlp-lab/system/policy.yaml` как root:root 0644, предыдущая версия
хранится в `/var/lib/dlp-admin-control/policy-backups/`. При ошибке
перезапуска прежний файл восстанавливается, обе службы запускаются,
задание остаётся ошибочным — проверьте восстановление. Политика не
позволяет запускать команды или ставить пакеты.

### Проверка применения

Для первого опыта примените **копию действующей** политики устройства —
правила не изменятся:

```bash
sudo install -o "$(id -un)" -g "$(id -gn)" -m 600 \
  /etc/dlp-lab/system/policy.yaml "$HOME/dlp-policy-check.yaml"
```

Загрузите копию в панели для того же устройства и примените. Затем:

```bash
stat -c '%U:%G %a' /etc/dlp-lab/system/policy.yaml
sha256sum /etc/dlp-lab/system/policy.yaml
systemctl is-active dlp-lab-files dlp-lab-session dlp-lab-admin-control dlp-lab-forwarder
sudo journalctl -u dlp-lab-admin-control.service --since '5 minutes ago' -o cat --no-pager
```

Ожидаются root:root 0644, четыре active, свежее событие `policy_loaded`
с SHA256 текущего файла и завершённое задание. Сверяйте дату с текущим
заданием, а не с прошлым перезапуском. Проверьте тестовые вложения и,
отдельно, доступность поля: `policy_loaded` не подтверждает работу
AT-SPI. Удалите копию после проверки.

Бейдж «Совпадает на диске» подтверждает только файл. При аварии между
заменой и перезапуском SHA256 может совпадать, хотя файл не загружен;
повтор прежнего ID службы не перезапускает — создайте новое задание.

### Типы файлов и изображения

Политика содержит секцию `file_types` с списками `allow` и `deny`. Тип
определяется по **сигнатуре содержимого**, а не по расширению — переименованный
файл не обходит правило. `deny` всегда сильнее `allow`; пустой `allow` означает
отсутствие белого списка.

Тип вне `allow` (при непустом списке) или входящий в `deny` → BLOCK с причиной
`file_type_denied`: содержимое не проверялось, отказ дан по типу. Так
блокируются изображения: в политике по умолчанию `allow: [text, pdf, docx]`,
поэтому PNG/JPEG запрещены.

Тип без извлечения текста (например, изображение), **явленно** добавленный
в `allow`, → ALLOW с причиной `file_type_allowed`: решение политики, содержимое
честно помечено непроверенным (OCR в этой сборке нет). Подписи этих причин
видны в панели в строке события.

**Роли:** политика назначается per-device из центральной панели — устройству
«оператор ОК» можно разрешить изображения (`allow: [text, pdf, docx, png, jpeg]`),
остальным оставить запрет. Это и есть различие допустимых операций по ролям.

### Вручную

Сначала проверьте копию, затем установите и перезапустите:

```bash
install -m 600 /etc/dlp-lab/system/policy.yaml "$HOME/dlp-policy-candidate.yaml"
sudo dlp-agent --policy "$HOME/dlp-policy-candidate.yaml" analyze --text 'коммерческая тайна'
sudo cp -a /etc/dlp-lab/system/policy.yaml /etc/dlp-lab/system/policy.yaml.previous
sudo install -o root -g root -m 644 "$HOME/dlp-policy-candidate.yaml" /etc/dlp-lab/system/policy.yaml
sudo systemctl restart dlp-lab-files.service dlp-lab-session.service
```

Откат — скопируйте `.previous` обратно и перезапустите обе службы.

## Сервер действующего стенда

Согласованная резервная копия (контейнеры останавливаются; агенты
продолжают защиту):

```bash
sudo bash <<'SH'
set -eu
backup_dir=$(mktemp -d /var/backups/dlp-central-docker.XXXXXXXX)
chmod 700 "$backup_dir"
dc() { docker compose -p dlp-central-migrated -f /etc/dlp-lab/docker/compose.json "$@"; }
trap 'dc start' EXIT
dc stop
cp -a /var/lib/dlp-central "$backup_dir/state"
cp -a /etc/dlp-lab "$backup_dir/config"
printf 'Резервная копия: %s\n' "$backup_dir"
SH
```

Копия содержит токены и ключи. Восстановление: остановите контейнеры,
сохраните текущее состояние, верните копию (UID/GID 10001, каталог 0700,
файлы 0600), запустите и проверьте устройства и новое событие. События,
принятые после копии, теряются. Токен администратора: `sudo dlp-admin-token`.

## Лабораторный сертификат

Создание самоподписанного сертификата входит в установку сервера —
[INSTALL, шаг 3](INSTALL.md#1-сервер). Здесь только эксплуатационные
правила: агентам передавайте только `central-ca.crt`, никогда `server.key`;
не перезаписывайте сертификаты действующей установки; следите за сроком
действия и перевыпускайте вместе с перезапуском контейнера.

## Остановка и удаление агента

```bash
sudo systemctl disable --now dlp-lab-files.service dlp-lab-session.service dlp-lab-forwarder.service
sudo systemctl stop dlp-lab-admin-control.service
```

Возобновление: `sudo dlp-setup`. Удаление программы: `sudo apt remove dlp-lab`;
перед `sudo apt purge dlp-lab` сохраните нужные конфигурации и журналы.

## Если не работает

- Панель не открывается: `docker compose ... ps` и `logs`, адрес и порт.
- Агент не виден: `sudo dlp-agent doctor`, журнал forwarder, CA и адрес сервера.
- `Events acknowledged: 0` само по себе не ошибка — проверьте тестовое событие.
- Текст не анализируется: служба session и доступность AT-SPI в карточке.
- `Address already in use`: найдите запущенный экземпляр, не запускайте второй.
- Файл ошибочно блокируется: проверьте причину и политику; не отключайте
  защиту всей системы ради одного документа.
