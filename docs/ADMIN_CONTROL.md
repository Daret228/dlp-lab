# Административное управление (0.2.21)

Обычный пользователь не управляет установленным агентом. `/usr/bin/dlp-agent`
отклоняет вызовы без административных прав. Локальной веб-панели нет. Политика,
конфигурация и системные службы принадлежат root. Пользователю показываются
только уведомления без действий отключения или настройки защиты.

## Службы

| Служба | Назначение |
| --- | --- |
| `dlp-lab-files.service` | Файловый контроль fanotify |
| `dlp-lab-session.service` | Системный супервизор текстового контроля |
| `dlp-lab-admin-control.service` | Выполнение двух фиксированных команд перезапуска |
| `dlp-lab-forwarder.service` | Передача событий и состояния на сервер |

Установщик включает службы. Сеансовый супервизор ждёт активный локальный
графический сеанс настроенного пользователя и запускает процесс анализа
с его UID, фиксированными путями и очищенным окружением. Пользовательский
systemd не управляет этим процессом. При выходе из сеанса процесс останавливается;
при следующем входе запускается снова. Завершившийся или зависший процесс
перезапускается системным супервизором.

Все административные команды выполняются через sudo:

```bash
sudo dlp-agent doctor
sudo systemctl status dlp-lab-files.service dlp-lab-session.service dlp-lab-forwarder.service --no-pager
sudo systemctl restart dlp-lab-session.service
sudo journalctl -u dlp-lab-session.service -n 30 --no-pager
```

Не используйте `dlp-agent agent start/stop` в установленном пакете: управление
пользовательскими units запрещено. Разработческий запуск из исходников не
предоставляет права менять системные службы и конфигурацию.

## Что именно проверяется в сеансе

AT-SPI-монитор выбирает единственное видимое, сфокусированное многострочное
редактируемое поле внутри разрешённого процесса Telegram или Signal.
Парольные поля исключены; глобального перехвата клавиатуры нет. Маркер не нужен.
При смене фокуса и чата выбор повторяется. Неоднозначное или недоступное поле
не читается. Тип поля проверяется по AT-SPI; это ещё не подтверждение универсальной
совместимости со всеми версиями клиентов или всеми их диалогами.

Текст анализируется локально; в центральный журнал передаётся результат без
содержимого сообщения. При риске выводится уведомление. Запрет отправки текста
не реализован. Локальные базы и JSON-экспорт не сканируются автоматически этой
службой; их исследовательские проверки отделены от постоянного файлового и
текстового контроля.

Клиент должен предоставлять AT-SPI-доступность. Если Telegram её не предоставляет,
администратор настраивает запуск клиента с `QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1`.
Служба не вмешивается в уже запущенный клиент и не меняет его окружение задним числом.

## Что видит администратор

Карточка устройства показывает свежесть связи, состояние файловой службы и текста:

- «доступно выбранное поле» — получено поле, подходящее по условиям AT-SPI;
- «ожидает доступное поле» — доступ к полю пока не подтверждён;
- «недоступен» — ошибка доступа, неоднозначное поле или просроченное состояние;
- «нет активного графического сеанса» — пользователь не вошёл либо сеанс неактивен;
- «остановлен» / «восстановление» — служба остановлена или процесс восстанавливается.

При отсутствии свежих данных более двух минут контроль не считается подтверждённым.
Отправщик измеряет состояние системных служб и читает root-owned состояние
супервизора. Остановка отправщика проявляется как потеря связи. Сервер не может
по отсутствию связи отличить выключенную машину от сетевой неисправности.
Состояние сервиса «запущена» не заменяет тест фактической блокировки файла.

Процесс с UID пользователя технически может быть завершён этим пользователем.
Супервизор root восстанавливает его; это не абсолютная защита сеансового процесса
от вмешательства владельца сеанса. Пользователь с sudo/root также остаётся
администратором ОС. Скрытие CLI не является границей безопасности: ею служат
права системных файлов и служб.

## Обновить действующий стенд

**Сначала сервер:** старый сервер не принимает новые события состояния.
На основной машине подготовлены пакет 0.2.22 и сценарий:

```bash
cd /home/roman/dlp-lab
sudo python3 scripts/update-managed-agent.py
```

Он собирает Docker-образ, сохраняет Compose-конфигурацию, обновляет сервер
и проверяет API, затем устанавливает локальный DEB и запускает службы.
При сбое серверного этапа возвращает предыдущие образы/конфигурацию;
при сбое установки пакета обновлённый совместимый сервер остаётся работать.
Резервная копия базы перед обновлением описана в MAINTENANCE.md.

После успешного обновления сервера, на второй машине:

```bash
cd ~/dlp-build-input
sudo apt -o Dpkg::Options::="--force-confold" install ./dlp-lab_0.2.22~deb12u1_amd64.deb
sudo systemctl enable --now dlp-lab-session.service
sudo systemctl restart dlp-lab-forwarder.service
sudo dlp-agent doctor
```

Проверка после установки: обычный пользователь не может вызвать управление;
тестовое поле с вымышленными данными даёт предупреждение; остановка сеансового
процесса отображается и вызывает восстановление; остановка службы администратором
отображается в панели. После опыта верните службу через sudo systemctl start.
Эти реальные опыты нужно выполнить после развёртывания нового пакета.

## Управление с сервера

В карточке устройства доступны «Диагностика», «Перезапустить файлы» и
«Перезапустить текст». Для перезапуска нужны сервер и агент версии 0.2.21,
свежая связь и работающая служба admin-control. Панель запрашивает подтверждение:
на время перезапуска соответствующий контроль прерывается. Результат задания
и последующая диагностика отображаются в журнале команд. Доставка обычно занимает
один интервал опроса отправщика (15 секунд); срок задания — 15 минут.

Отправщик обращается к локальному root-сервису по Unix-сокету. Сервис проверяет
UID отправителя и принимает только restart_files/restart_session, без shell,
путей и пользовательских аргументов. ID выполненной команды сохраняется до
ответа: повторная доставка не вызывает повторный перезапуск. После аварии с
неопределённым результатом команда считается неуспешной, автоматически не повторяется.

Успешный перезапуск означает active у службы, а не доказательство блокировки
или доступности поля. Проверьте состояние карточки и тестовое событие.
Удалённая установка DEB и изменение политики в этот выпуск не входят.

## Быстрое подключение нового агента (0.2.22)

После установки DEB выполните `sudo dlp-setup connection.json`.
Настройки и автозапуск служб выполняются автоматически; отдельные systemctl
команды для первого подключения не нужны. Формат и подготовка профиля описаны
в [эксплуатации](OPERATIONS.md). Для этого изменения сервер0.2.21 совместим,
пересборка Docker не требуется. На настроенных машинах достаточно обновить DEB.
