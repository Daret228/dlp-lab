# Linux Endpoint DLP Lab

Модульный исследовательский Linux DLP-агент для ВКР: контроль файлов, анализ
текстовых полей и локальных данных мессенджеров. Поддерживаются Telegram Desktop
и Signal Desktop. Анализ выполняется на рабочей машине; центральный сервер
принимает события и позволяет запросить диагностику агента.

**Состояние на 5 ноября 2026 года: версия DEB 0.2.17.** Проверен стенд из двух
машин: Debian 13 (сервер и агент) и Debian 12 (агент), связь по HTTPS.
На основном хосте установлен DEB 0.2.16; после обновления подтверждены
работа файловой защиты, отправщика и доступность панели по HTTP/HTTPS. Docker-сервер использует образ
`dlp-lab-central:0.2.15-migration1`. Это прототип, а не готовая промышленная DLP.

## С чего начать

**[Единое руководство по эксплуатации](docs/OPERATIONS.md)** — установка,
сервер и HTTPS, подключение устройств, ежедневная работа, все модули, политики,
обновление, резервные копии и устранение ошибок. В каждом разделе указано,
на какой машине выполнять команды и нужен ли `sudo`.

Токен центральной панели: `sudo dlp-admin-token` на сервере. Команда включена
в DEB 0.2.15. Для пакетов 0.2.14 и старше её можно
[установить из исходников](docs/OPERATIONS.md#31-запустить-центральный-сервер).

На текущем стенде центральный сервер уже работает в **Docker**, агенты — через
**DEB + systemd**. [Команды управления действующим сервером](docs/DOCKER.md#текущий-стенд-после-переноса).
Сервер через systemd остаётся альтернативой для других установок; на этом стенде
его старые службы отключены.

## Возможности

| Направление | Реализовано | Ограничение |
| --- | --- | --- |
| Файлы Telegram и Signal | fanotify, анализ текста, PDF/DOCX, разрешение или запрет открытия | Локальные файловые системы с исключениями; запрет открытия не доказывает перехват отправки |
| Текстовые поля | AT-SPI, анализ выбранного черновика, предупреждения и журнал | Наблюдение без запрета отправки; требуется графический сеанс и доступное поле |
| Локальные данные Telegram | Чтение исследованного подмножества локальных данных и черновиков; отдельно JSON-экспорт | Полная история сообщений из tdata не читается |
| Локальные данные Signal | Разовая проверка текстов из копии SQLCipher-базы закрытого тестового клиента | Ограниченная выборка, без вложений; штатный доступ к ключу через GNOME Keyring |
| Анализ | Словари, регулярные выражения, контекстные правила, обучаемый ML-классификатор | ML экспериментальный, в новой политике включён с WARN; OCR нет |
| Установка | DEB, systemd, мастер первоначальной настройки, ручной запуск | Для подключения нужен индивидуальный файл регистрации и CA; пользовательские модули настраиваются отдельно |
| Центральный журнал | Отдельные устройства, HTTPS, дисковая очередь отправщика | Нет обещания полноты при потере исходного journald или переполнении очереди |
| Удалённая диагностика | Запрос из панели, получение задания агентом, отчёт и история состояний | Только чтение; удалённое изменение политик, служб и обновление DEB ещё не реализованы |

`BLOCK` — решение анализатора. Фактический запрет файлового доступа отображается
отдельно как `DENY`. `WARN` разрешает открытие. Событие открытия не равно отправке.

## Устройство системы

```text
Рабочая машина                         Сервер администратора
┌───────────────────────────────┐      ┌───────────────────────────┐
│ Анализаторы и файловый контроль│      │ Общий журнал и устройства │
│ Локальные события → очередь   │ HTTPS│ Задания диагностики       │
│ Системный отправщик            │ ───► │ Веб-панель                │
│ Получение задания ← ответ     │ ◄─── │ Результаты проверок       │
└───────────────────────────────┘      └───────────────────────────┘
```

Агент сам обращается к серверу: отдельный входящий порт на рабочей машине не
нужен. Отправщик работает от непривилегированного служебного пользователя.
Через канал диагностики нельзя передать shell-команду или скрипт.
Содержимое сообщений, файлов и ключи в центральный журнал не передаются.

## Установка одним сценарием

Добавлен самостоятельный `scripts/install-dlp.py`: проверка Debian 12/13 и
зависимостей, установка локального DEB, настройка файлового контроля, HTTPS
отправщика и автозапуска. Для нового устройства нужны его JSON регистрации
и публичный CA; мессенджеры устанавливаются заранее. `--check` проверяет без
изменений, `--local-only` выбирает установку без подключения к серверу.
[Установочный комплект и команды](docs/OPERATIONS.md#быстрый-путь-единый-установщик).
### Что подготовить

- Debian 12 или 13 с systemd, Python 3 и правами администратора; проверенная архитектура — amd64.
- Установленный Telegram Desktop; Signal Desktop подключается дополнительно.
- Комплект для своей версии ОС: установщик и совместимые DEB. Для Debian 12 на стенде используется отдельная сборка SQLCipher 4.
- Для центрального журнала — адрес HTTPS сервера, индивидуальный `central-agent.json` и публичный `central-ca.crt` от администратора.

**На рабочей машине**, распакуйте полученный от администратора комплект:

```bash
tar -xzf dlp-install-0.2.17-debian13-amd64.tar.gz
cd dlp-install
# Поместите в этот каталог файлы регистрации и CA от администратора.
chmod 600 central-agent.json
sudo ./install-dlp.py --check
sudo ./install-dlp.py
```

Для Debian 12 используйте соответствующий архив. Для работы без сервера запускайте
установщик с `--local-only`; файлы регистрации тогда не нужны. При нескольких
пользователях укажите `--user ИМЯ`. `--check` ничего не устанавливает;
обычный запуск показывает план и запрашивает подтверждение.

Существующие настройки сохраняются, несовпадающая регистрация не заменяется.
При ошибке возможна частичная установка без автоматического отката. SHA256SUMS
проверяет целостность комплекта, но не является подписью издателя.

**Проверено:** запуск установщика поверх существующего агента Debian 12,
автозапуск после перезагрузки и реальный контроль тестовых файлов. Установка
на чистую ОС пока не проверена. Готовые архивы и DEB в Git не хранятся;
[как собрать комплект](docs/OPERATIONS.md#быстрый-путь-единый-установщик).

## Установка агента из DEB

Сначала соберите пакет для целевой ОС — инструкции ниже. Готовые локальные
сборки из `build/` не хранятся в Git. Перед переходом с лабораторного запуска
остановите его файловый монитор.

Для Debian 13 amd64:

```bash
sudo apt install ./build/dlp-lab_0.2.17_amd64.deb
```

Если при установке отказались от настройки, запустите мастер:

```bash
sudo dlp-lab-configure --wizard
dlp-agent doctor
```

Мастер предлагает пользователя рабочего стола, пути Telegram/Signal и автозапуск
файлового контроля. Уже существующие настройки не перезаписывает. Можно настроить
без диалога:

```bash
sudo dlp-lab-configure --user YOUR_USER \
  --telegram /usr/bin/telegram-desktop \
  --signal /opt/Signal/signal-desktop --enable
```

Если Signal не установлен, исключите аргумент `--signal`. Пути исполняемых файлов
и их родительские каталоги должны принадлежать root и быть защищены от записи
группы и остальных пользователей.

Проверьте готовность по событию `monitor_started` и затем тестовому прикреплению:

```bash
sudo systemctl status dlp-lab-files.service --no-pager
sudo journalctl -u dlp-lab-files.service -n 20 --no-pager
```

Текстовый монитор и проверки локальных баз запускаются отдельно в пользовательском
сеансе. Установка DEB сама по себе не включает все модули.

**Debian 12:** нужна нативная сборка, на стенде — `0.2.14~deb12u1`. Для Signal
требуется SQLCipher 4; штатная библиотека SQLCipher 3 не подходит. На стенде
используется локально собранный `libsqlcipher1`, а не официальный Debian backport.
[Портирование и зависимости](docs/research/debian12_port_2026-10-30.md).

## Ручное управление и диагностика

Команды выполняются **на машине агента**. Администратор может использовать SSH.

| Задача | Команда |
| --- | --- |
| Проверить конфигурацию и службы | `dlp-agent doctor` |
| Запустить файловую защиту | `sudo systemctl start dlp-lab-files.service` |
| Остановить файловую защиту | `sudo systemctl stop dlp-lab-files.service` |
| Посмотреть журнал защиты | `sudo journalctl -u dlp-lab-files.service -n 30 --no-pager` |
| Проверить отправщик | `systemctl status dlp-lab-forwarder.service --no-pager` |
| Посмотреть доставку событий | `sudo journalctl -u dlp-lab-forwarder.service -n 30 --no-pager` |
| Проверить пользовательские модули | `dlp-agent agent status` — внутри графического сеанса, без sudo |

Для ручного запуска файловой защиты вместо systemd:

```bash
dlp-agent doctor
dlp-agent doctor --json
sudo systemctl stop dlp-lab-files.service
sudo dlp-lab-run-files
# Ctrl+C завершает ручной запуск. Вернуться к службе:
sudo systemctl start dlp-lab-files.service
```

Одновременно два файловых монитора не запускайте. `doctor` проверяет политику,
пути мессенджеров и состояния системных служб без чтения токенов или сообщений.
`OK` означает успешность конкретной проверки, `INFO` — информационный пункт,
`UNKNOWN` — проверка не выполнена. Сеть, очередь и пользовательские модули
пока не входят в эту диагностику. Работающий процесс не доказывает полную защиту.

Для обновления установленного пакета достаточно `sudo apt install ./новый-пакет.deb`;
повторять мастер или заменять настройки не требуется.
[Подробности установки и миграции](packaging/README.Debian).

## Сервер и удалённая диагностика

[Пошаговая настройка сервера, TLS и регистрации устройств](docs/CENTRAL_SERVER.md).

На стенде локальная центральная панель доступна на `http://127.0.0.1:8766/`.
Это адрес на сервере. Агенты другой машины подключаются к настроенному HTTPS
адресу сервера. Для каждого агента используется отдельный токен; токен
администратора нельзя выдавать агентам.

После регистрации и запуска отправщика:

1. Откройте центральную панель, введите токен администратора и нажмите «Подключиться».
2. У нужного устройства нажмите «Запросить диагностику».
3. Через 30 секунд нажмите «Обновить»: в разделе заданий появится результат.

Задание ожидает агента до 15 минут. Статус «Выполнено» означает, что получен
отчёт, а не что все пункты имеют `OK`. На рабочей машине не требуется
подтверждение пользователя. Результат хранится до подтверждения сервером.

**Проверено на двух машинах:** доставка событий, отображение `BLOCK / DENY`,
удалённая диагностика и исправление проверки UID служебного пользователя.
Отдельный опыт разрыва связи на реальном стенде ещё предстоит; повторная доставка
и сохранение очереди проверяются автоматическими тестами.

Локальная панель `dlp-agent dashboard` (по умолчанию порт 8765) и центральная панель
8766 выполняют разные задачи. Локальная панель управляет пользовательскими
лабораторными модулями; её настройки не заменяют системную политику пакета.

## Анализ и лабораторный запуск

В установленном пакете:

```bash
dlp-agent analyze --text 'коммерческая тайна'
dlp-agent analyze --file /absolute/path/to/document.docx
```

Из корня исходников с подготовленными зависимостями:

```bash
./scripts/dlp analyze --file examples/public.txt
./scripts/dlp dashboard
./scripts/dlp agent status
./scripts/dlp agent start text --marker DLP_TEST --seconds 120
```

Перед наблюдением текста оставьте маркер в выбранном тестовом черновике.
Команда не запрещает отправку. Разовые проверки:

```bash
./scripts/dlp agent export --file examples/telegram-export-synthetic.json
# Только при полностью закрытом Signal и доступном пользовательском Keyring:
dlp-agent signal-local-check --root "$HOME/.config/Signal" \
  --journal "$HOME/dlp-signal-local.jsonl"
```

Для Signal проверяется до 100 последних текстов по умолчанию; оригинальная база
не изменяется. Это анализ сохранённых данных, не запрет отправки.
[Демонстрационный сценарий](docs/demo.md),
[исследование Telegram](docs/research/telegram_local_reader_2026-10-09.md),
[исследование Signal](docs/research/signal_storage_2026-10-26.md).

## Машинное обучение

Обучаемый классификатор обнаруживает финансовые сведения, паспортные данные и
данные доступа в тексте и извлечённом тексте документов. Его действие — `WARN`.
В исходной политике и новом пакете 0.2.15 ML включён с действием WARN. При
обновлении сохраняется политика администратора: старый выключенный режим
самостоятельно не меняется. На основном стенде ML включён; состояние второй
машины нужно проверять отдельно.

```bash
./scripts/dlp --policy config/ml-demo.yaml analyze --text 'Пароль: Reka!6831'
```

Пример содержит вымышленный пароль. Результаты на синтетической выборке не являются
независимой оценкой качества. [Обучение](docs/research/ml_linear_2026-10-19.md),
[оценка и воспроизведение](docs/research/ml_quality_2026-10-19.md).

## Разработка, сборка и тесты

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .
make test PYTHON=.venv/bin/python
make build
```

Для DEB установите Build-Depends из [debian/control](debian/control), затем:

```bash
./scripts/build-deb.sh
```

На лабораторном хосте есть `--local-deps`: тесты используют `.deps`, зависимости
в пакет не включаются. Пакет собирайте на совместимой с целевой машиной ОС.

Сборка 0.2.16 на Debian 13: **285 тестов, 282 прошли, 3 пропущены**,
включая проверки Docker-entrypoint и подготовки миграции.
Проверены lifecycle DEB и wheel вне репозитория; [повторный аудит](docs/research/audit-0.2.16.md).
Пользователь подтвердил реальный Docker smoke-test и перенос рабочего сервера;
[протокол проверки](docs/research/release-0.2.15.md).
Нативная сборка Debian 12: **269 тестов, 266 прошли, 3 пропущены**; её снимок
не включал 9 отдельных тестов установщика. После обновления пользователь
подтвердил отсутствие предупреждения `.Xauthority`, разрешение public и запрет secret.
Тесты включают анализаторы, очередь, TLS, авторизацию и изоляцию заданий.
Обычные тесты не заменяют kernel/fanotify опыт; привилегированные проверки
запускаются отдельно и явно. [Правила доступа](docs/privileged-access.md).

## Если что-то не работает

| Симптом | Что проверить |
| --- | --- |
| Страница на 8765/8766 не открывается | Это локальные адреса соответствующей машины; проверьте нужную панель/службу, не запускайте второй экземпляр на том же порту |
| Служба active, но файл не блокируется | Событие `monitor_started`, UID пользователя, путь клиента и исключения; затем тестовое прикрепление |
| `Events acknowledged: 0` | Это число подтверждённых событий в цикле, а не ошибка само по себе; создайте тестовое событие и сопоставьте его с центральным журналом |
| В диагностике `INFO` или `UNKNOWN` | Необязательный компонент или проверка не выполнена; это не равнозначно отказу |
| Предупреждение о `.Xauthority` при старте Telegram | Обновите агент до 0.2.14 и перезапустите файловую службу; исключение ограничено приватным файлом в домашнем каталоге |
| Отправщик не работает | Его журнал, индивидуальная регистрация, HTTPS адрес и доверенный CA; не удаляйте очередь для устранения ошибки |

[Подробное устранение ошибок, обновление и удаление](docs/OPERATIONS.md).

## Ограничения и дальнейшая работа

- Исключённые каталоги и служебные файлы не анализируются. В 0.2.14 добавлено
  исключение для приватного `<home>/.Xauthority` с проверкой владельца, прав,
  типа, числа ссылок и совпадения открытого файла. Документ, намеренно помещённый
  по этому пути, тоже не анализируется. [Границы исключений](docs/OPERATIONS.md#6-правила-и-исключения).
- Полная локальная история Telegram не читается, отправка текста не блокируется.
- Мессенджеры, версии, графическая доступность, форматы и файловые системы требуют
  проверки на конкретном хосте; универсальность для любого клиента не заявляется.
- Управление политиками и службами, подписанные обновления DEB с сервера и
  регистрация одноразовым кодом пока не реализованы.
- Роли нескольких администраторов, ограничение хранения и промышленная защита
  сервера от перегрузки остаются дальнейшей работой.
- Проект используется на собственных тестовых системах: без глобального
  keylogging, MITM, внедрения в клиенты или обхода их шифрования.
