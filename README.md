# Linux Endpoint DLP Lab

Актуальные требования, состояние и следующие задачи:
[контекст проекта](docs/PROJECT_CONTEXT.md). Здесь зафиксировано видение научного
руководителя: локальные данные сообщений, файлы и текстовые поля; расширяемая,
свободно распространяемая система под управлением администратора.
Ниже также сохранены инструкции и результаты отдельных этапов разработки.

Исследовательский прототип для ВКР на собственном Linux-стенде: файловый контроль
Telegram через fanotify, наблюдение одного текстового поля AT-SPI, анализ JSON-экспорта
и экспериментальное чтение локального черновика из копии tdata закрытого Telegram.
Последнее проверено на одном собственном тестовом черновике с разрешённой обработкой
локального ключа. Полная история и запрет отправки текста не реализованы.
eXpress пока не исследован. Это ещё не промышленная DLP.

Прямое чтение черновика, запуск и ограничения:
[протокол 2026-10-09](docs/research/telegram_local_reader_2026-10-09.md).

## Что работает

- TextContent/FileContent → Dictionary/Regex/Context → AnalysisResult + ALLOW/WARN/BLOCK.
- YAML-политика с порогами, весами, лимитами и стратегией ошибок.
- JSONL-аудит без содержимого сообщений; ML и messenger adapters имеют интерфейсы.
- C helper для fanotify setup со сбросом привилегий и Python worker для анализа.
- Фильтр процессов Telegram, корреляция повторных open, выбранное поле AT-SPI.
- Нормализация и аудит JSON-экспорта одного чата.
- Управление модулями через пользовательский systemd и общий журнал.
- Unit/protocol tests и отдельный opt-in kernel integration test.

**Проверка среды:** Debian 13, Python 3.13, GCC; Telegram найден, eXpress UNKNOWN.
Реальные FAN_OPEN_PERM/FAN_DENY проверены через ограниченный gateway, в том числе
при выборе файлов в Telegram. Тесты протокола не заменяют kernel integration.

## Управление агентом на текущем стенде

Из `/home/roman/dlp-lab`, без sudo перед scripts/dlp:

```bash
./scripts/dlp agent status
./scripts/dlp agent start files
./scripts/dlp agent logs --follow
./scripts/dlp agent stop
```

`logs --follow` занимает терминал; Ctrl+C прекращает просмотр, монитор продолжает
работать. `stop` выполнять после выхода из просмотра либо во втором терминале.
Для текста сначала подготовить поле с маркером, затем:

```bash
./scripts/dlp agent start text --marker DLP_TEST --seconds 120
```

Разовая проверка с сохранением результата в общем журнале:

```bash
./scripts/dlp agent export --file examples/telegram-export-synthetic.json
./scripts/dlp agent logs --lines 15
```

Status показывает только управляемые процессы. Готовность проверять по новым
событиям monitor_started/text_monitor_started. Текст наблюдается без send veto;
экспорт проверяется разово. Автозапуска нет, повторный start работающего модуля
отклоняется. Файловый start использует существующий фиксированный sudo gateway.
Права/хранение/ротация журнала определяются journald хоста; это не защищённый аудит.
Прямые CLI-команды ниже выводят результат только в терминал.
Полная последовательность: [демонстрация для ВКР](docs/demo.md).

## Установка и автономный запуск

На обычном Linux с python3-venv/pip и GCC:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/python -m dlp.cli --policy config/policy.yaml analyze --text 'коммерческая тайна'
.venv/bin/python -m dlp.cli analyze --file examples/public.txt
make test PYTHON=.venv/bin/python
make build
```

В текущем workspace PyYAML уже установлен локально в `.deps`; работают:

```bash
make test
make demo
PYTHONPATH=src:.deps python3 -m dlp.cli analyze --file examples/secret.txt
```

Результат JSON содержит decision. Код выхода 0 означает завершённый анализ,
в том числе BLOCK; 2 — ошибку конфигурации или неполный анализ. Не трактовать
exit 0 как ALLOW. Проверяются UTF-8 текст и извлечённый текст PDF/DOCX (ограничения ниже); ошибки/превышение лимитов
по умолчанию BLOCK с complete=false. WARN в PoC разрешает открытие и пишет аудит.

## fanotify: ручной эксперимент на тестовом host

Нужен CAP_SYS_ADMIN (обычно запуск helper через sudo), поддержка permission events
ядром/файловой системой и доступ worker к файлам. Не запускать Python под root.
Не устанавливать setuid/capabilities на helper. Он наблюдает только непосредственных
детей отдельного каталога и не модифицирует файлы мессенджеров.

Ниже низкоуровневый опыт с отдельной сборкой helper, не обычный запуск агента.
Не запускать одновременно с agent start files. Пример cat работает в режиме all;
в текущем messengers cat пропускается. Для повседневного опыта использовать
установленный gateway и [сценарий демонстрации](docs/demo.md).
Сначала загрузить/проверить policy командой analyze. Затем, из корня проекта:

```bash
make build
mkdir -p build/watch
chmod 700 build/watch
cp examples/public.txt examples/secret.txt build/watch/
umask 077
sudo ./build/fanotify-launcher "$PWD/build/watch" "$(id -u)" "$(id -g)" \
  /usr/bin/env "PYTHONPATH=$PWD/src:$PWD/.deps" \
  /usr/bin/python3 -m dlp.cli --policy "$PWD/config/policy.yaml" monitor \
  > build/events.jsonl
```

В другой консоли того же пользователя:

```bash
cat build/watch/public.txt   # ожидается успех
cat build/watch/secret.txt   # ожидается Operation not permitted
```

Остановить Ctrl+C. После остановки защита каталога прекращается. Для установки
через venv заменить Python в команде на абсолютный путь к `.venv/bin/python`.
Лог обязательно держать за пределами watch. Метки не рекурсивны.

Полный автоматический kernel test на собственном стенде:

```bash
sudo env DLP_RUN_PRIVILEGED=1 DLP_TEST_UID="$(id -u)" DLP_TEST_GID="$(id -g)" \
  PYTHONPATH="$PWD/src:$PWD/.deps" /usr/bin/python3 -m unittest discover -s tests -p test_kernel.py -v
```

Harness запускается root исключительно для создания тестового каталога, запуска
helper и проверки его сброса привилегий. Проверяются ALLOW, WARN→ALLOW, DENY,
аудит и освобождение после завершения worker. Тест пропускается без явного флага.
Обычный `make test` не запрашивает sudo.

## Структура и ограничения

```text
src/dlp/        модели, контракты, анализ, policy, CLI, аудит, fanotify worker
native/         минимальный привилегированный setup
config/         YAML-политики
examples/       синтетические файлы
 tests/         unit/protocol и opt-in kernel test
 docs/          архитектура, модель угроз, исследование среды и клиентов
```

Событие open журналируется как file_access_attempt с send_confirmed=false.
Связь с реальной отправкой не доказана. Process filter реализован, текущий режим
— messengers: Telegram включён, eXpress отключён. Нет кеша решений, блокировки буфера обмена, TLS MITM,
перехвата клавиатуры, расшифровки профилей или чтения чужих аккаунтов.
Смерть worker приводит к fail-open; запись лога может задержать следующие события;
SIGALRM не заменяет внешний watchdog для зависшего kernel IO.

См. [архитектуру](docs/architecture.md), [модель угроз](docs/threat_model.md),
[результаты исследования среды](docs/research/environment.md).
Следующие этапы: оценка качества/задержек, расширение покрытия, тестовая среда
eXpress и защищённое администраторское управление. Границы каждого модуля
и проверенные результаты приведены в контексте проекта.

## Проверка текста в поле Telegram (эксперимент)

В проверенной сборке доступ к полю появился после полного выхода из Telegram
и запуска из обычного терминала:

```bash
QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1 /usr/bin/telegram-desktop
```

Открыть собственный тестовый чат и ввести `DLP_TEST коммерческая тайна`, не отправляя.
Затем из корня проекта запустить без sudo:

```bash
PYTHONPATH=src:.deps python3 -m dlp.cli text-monitor --marker DLP_TEST --seconds 120
```

Агент привяжется к найденному полю и будет проверять изменения 120 секунд.
После старта маркер можно удалить и вводить обычный текст, email или секретную фразу.
Результаты — в терминале; WARN/BLOCK дополнительно вызывают desktop notification,
если notify-send и служба уведомлений доступны. `--no-notify` отключает уведомления.
Ctrl+C останавливает наблюдение. Root не требуется.

**Отправка текста не блокируется.** BLOCK в результате — решение политики,
`enforcement=observe_only` означает только наблюдение/предупреждение. Не отправляйте
реальные секреты, рассчитывая на veto. Проверка реального тестового черновика
успешна, но контроль всех полей/окон/режимов Telegram ещё не подтверждён.

### Политика форматов файлов

В `config/policy.yaml` добавлен необязательный раздел `file_types`:

```yaml
file_types:
  allow: [text, pdf, docx]
  deny: [elf, dos_pe, script, zip, gzip, 7z, rar]
```

Тип определяется по сигнатуре содержимого или проверке UTF-8, без доверия
расширению. Поддержанные категории: `text`, `elf`, `dos_pe` (заголовок MZ),
`script` (начальный `#!`), `zip`, `gzip`, `7z`, `rar`, `pdf`, `docx`, `png`, `jpeg`, `ole`.
Это ограниченный классификатор сигнатур, не полная проверка структуры формата,
не антивирус и не детектор всех исполняемых файлов, скриптов или полиглотов.
Повреждённый файл с известной сигнатурой также получает соответствующую категорию.

Непустой `allow` ограничивает набор допустимых категорий; пустой отключает
белый список. `deny` явно запрещает категории. Пересечения и неизвестные имена
при загрузке политики отклоняются. Неизвестный тип даёт `unknown_file_type`,
`complete=false` и решение `on_error` (на стенде BLOCK).

Запрет формата возвращает BLOCK с `reason=file_type_denied`, `score=0`:
это прямое правило формата, а не текстовый балл. `complete=true` в этом случае
означает завершённое решение о запрете; `metadata.content_checked=false` явно
указывает, что содержимое не анализировалось. В метаданных сохраняется категория,
но не байты файла. Разрешённый формат не означает автоматически безопасное
содержимое: UTF-8 текст и извлечённый текст PDF/DOCX проходят обычные правила;
для остальных возвращается `unsupported_content_type`, `complete=false`, решение `on_error`.

DOCX отличается от ZIP по обязательным частям контейнера, затем проверяется
при извлечении. Произвольные архивы не распаковываются. Лимит размера и проверка
изменений файла сохранены. Слишком большой файл получает неполный результат
до классификации. Fanotify использует исходный FD события, а не повторное
открытие пути; область контроля остаётся прежней. Запущенный агент нужно
перезапустить для чтения новой политики.

Проверка без запуска мониторинга:

```bash
./scripts/dlp analyze --file /usr/bin/true
./scripts/dlp analyze --file examples/public.txt
./scripts/dlp analyze --file examples/secret.txt
```

На стенде ожидаются соответственно запрет ELF по формату, ALLOW и словарный BLOCK.
Эти команды сами по себе не запрещают открытие файла другими приложениями.


### Извлечение текста документов

TXT должен содержать UTF-8 (BOM допускается). DOCX обрабатывается стандартной
библиотекой Python: основной текст, таблицы, колонтитулы, сноски и комментарии.
Фраза, разделённая форматированием на несколько фрагментов, остаётся связной.
PDF обрабатывают `/usr/bin/pdfinfo` и `/usr/bin/pdftotext` из `poppler-utils`.
На текущем стенде они установлены; при отсутствии будет неполный результат
`pdf_dependency_missing`. Дополнительные Python-пакеты для извлечения не нужны.

```bash
./scripts/dlp analyze --file /полный/путь/документ.pdf
./scripts/dlp analyze --file /полный/путь/документ.docx
```

В результате есть `metadata.file_type`, область проверки `scope`, признак `ocr=false`
и статус анализа извлечённого текста. Текст документа в журнал не записывается.
Координаты находок относятся к извлечённому тексту, а не к странице документа.
`complete=true` означает завершение проверки в указанной области, а не всех
возможных данных внутри файла.

OCR нет: картинки, сканы, вложения PDF и текст внутри изображений не анализируются.
Смешанный PDF с текстом и изображениями может дать `complete=true` только для
извлечённого текста. PDF без текста или с пустыми текстовыми страницами даёт
неполный результат. DOCX с изображениями, вложенными объектами или другими
распознанными неподдерживаемыми частями также даёт `complete=false`.
Зашифрованные, повреждённые и превышающие лимиты документы не считаются проверенными.
Применяется `on_error` (сейчас BLOCK); уже найденный BLOCK при частичном разборе
не снижается. Макросы не исполняются, внешние ссылки не загружаются.

Парсер работает отдельным процессом с ограничениями времени, памяти и вывода.
Лимит входа задаёт `max_bytes` (сейчас 1 МиБ), извлечённого текста — меньший из
`max_bytes` и 4 МиБ. DOCX: до 256 записей, 8 МиБ распакованных данных и отношения
распаковки 200:1; PDF: до 200 страниц. Это ограничения прототипа, а не полная
изоляция от уязвимостей парсеров. Временные файлы удаляются при обычном завершении
и тайм-ауте; гарантированное стирание с носителя не реализовано.

Проверено на синтетических документах и через CLI; отдельный реальный опыт
прикрепления PDF/DOCX в Telegram ещё не выполнен. Архитектура и ограничения:
[решение об извлечении документов](docs/decisions/008-document-extraction.md).


### Экспериментальная проверка новых чувствительных категорий

Для финансовых данных, паспортных реквизитов и секретов доступа подготовлены
новые правила и локальный ML baseline. Доступна отдельная offline-команда:

```sh
printf '%s' 'Пароль: сиреневыйлес' | PYTHONPATH=src:.deps python3 scripts/predict-sensitive.py --stdin
PYTHONPATH=src:.deps python3 scripts/predict-sensitive.py --file /путь/к/файлу.docx
```

По умолчанию гибрид использует локальную модель build/ml/hybrid-v3/model.json.
В чистой копии её создаёт `PYTHONPATH=src:.deps python3 scripts/evaluate-ml-hybrid.py fit`.
Режим `--mode rules` работает без модели; `--mode ml` позволяет сравнить ML отдельно.
Новые категории **не подключены к рабочей политике агента**, автоматических
блокировок этой командой нет. Лимит текста 16 КиБ, OCR отсутствует.

На дополнительной синтетической проверке v4: 58/60 точных результатов, 0/12 ложных
тревог обычных текстов. Правила дали тот же результат, ML отдельно существенно хуже;
самостоятельная польза ML пока не доказана. Это не оценка надёжности на реальных
документах. [Методика, ограничения и воспроизведение](docs/research/ml_hybrid_2026-10-14.md).

### Новые категории в агенте: предупреждения

В `config/policy.yaml` включён раздел:

```yaml
sensitive_alerts:
  enabled: true
  mode: rules
  action: WARN
```

Финансовые/паспортные данные и секреты доступа проверяются общим анализатором
для текста, извлечённого содержимого файлов, экспортов и локального черновика.
Используются правила v4; самостоятельный ML не показал достаточного качества.
Раздел необязательный (старые политики работают как раньше), `enabled: false`
отключает новые категории. На этом этапе допустимы только mode=rules и action=WARN.

Находки `sensitive_advisory` не добавляют балл к старым правилам и повышают только
ALLOW до WARN. Несколько новых категорий одновременно не превращаются в BLOCK.
Если старое правило или ошибка основного извлечения требует BLOCK, он сохраняется.
Расположение находки обозначает весь проверенный текст, а не точный фрагмент секрета.

При превышении лимита новых правил 16 КиБ или их тайм-ауте результат неполный,
`metadata.sensitive_alerts.complete=false`, WARN (либо прежний BLOCK). Текст
не усекается и не считается полностью проверенным. Это отдельная реакция от
`on_error` основного чтения/извлечения, которое сохраняет прежнюю политику.

AT-SPI и локальный черновик используют существующие уведомления и журнал.
CLI analyze и проверка экспорта журналируют результат, но сами не показывают
уведомлений. Файловый монитор при новом WARN разрешает открытие, затем ставит
предупреждение в ограниченную фоновую очередь. Не чаще одного за 10 секунд;
подавленные повторы и статус доставки тоже журналируются. Блокировка старым
правилом не сопровождается новым предупреждением «отправка не заблокирована».
Фоновая доставка не задерживает fanotify-ответ текущему или следующим открытиям.

Gateway очищает окружение: после сброса привилегий Python использует стандартную
D-Bus-сессию своего UID, если адрес отсутствует. Root-настройки не расширялись.
`accepted` означает принятие уведомления службой рабочего стола, а не доказанный
показ человеку. Содержание документа/пароля в уведомление или журнал не включается.

Быстрая проверка через обычный интерфейс агента:

```sh
./scripts/dlp analyze --text 'Пароль: сиреневыйлес'
./scripts/dlp analyze --file build/sensitive-demo/credentials.docx
```

Ожидается WARN, score=0, category=credentials. Второй файл — локальный тестовый
артефакт, в чистой копии репозитория его нет. Для мониторинга используются прежние
`agent start files` и `agent start text --marker DLP_TEST --seconds 120`.
Уже запущенные процессы нужно перезапустить, чтобы они прочитали новую политику.

### Локальная веб-панель

```sh
cd /home/roman/dlp-lab
./scripts/dlp dashboard
```

Команда печатает полную ссылку с ключом текущей сессии. Откройте её в браузере.
Панель слушает только `127.0.0.1:8765`; другой порт: `--port 8766`. Запускайте
из обычного пользовательского сеанса, без sudo. Ctrl+C останавливает панель,
не меняя состояния модулей агента. При новом запуске ключ меняется; старая
вкладка потребует открыть новую ссылку. Ключ не нужно записывать в Git или отчёты.

Панель показывает состояние управляемых модулей, события и фильтры по периоду
(1/7/30 дней), категории, решению и источнику. Автообновление раз в 10 секунд,
кеш сервера — 5 секунд. Загружается не более 1000 последних записей journald
для фиксированных user-units агента; фильтрация и счётчики работают по этой
выборке. При достижении лимита есть предупреждение. Повторные открытия — отдельные
события, не отдельные доказанные утечки. WARN/BLOCK в сводке считаются по анализам,
без дополнительных строк доставки уведомлений. DENY — именно отказ открытия.

Раздел «Политика анализа» позволяет менять пороги WARN/BLOCK, реакцию на ошибки
и включать проверку новых категорий. Нажмите «Загрузить настройки», измените поля,
затем «Проверить изменения» и «Сохранить политику». Перед записью создаётся копия
в `build/policy-backups/` (права 0600); конфликт с внешним изменением отклоняется.
Пустое изменение не записывает файл. При сохранении YAML форматируется заново,
комментарии остаются в резервной копии. Для отката остановите нужные модули,
восстановите выбранную копию в `config/policy.yaml` и запустите модули заново.
Настройки вступают в силу при следующем запуске модуля; автоматического
перезапуска после сохранения нет. Для применения остановите и заново запустите модуль. История не копируется в отдельную базу, срок хранения определяется journald.
Ручные процессы, вывод CLI в терминал и посторонние user-units не включены.
На странице и в API нет исходных сообщений, содержимого файлов или путей профилей.
Выводятся только ограниченные поля событий. `complete=true` для PDF/DOCX относится
к поддерживаемому извлечённому тексту; OCR отсутствует. `accepted` у уведомления
означает приём службой, не доказанный показ пользователю.

API требует случайный ключ, проверяет Host/Origin; браузер получает ключ из
фрагмента ссылки и хранит его только в sessionStorage текущей вкладки. Сторонние
ресурсы не загружаются, содержимое событий выводится текстом. Это локальный
прототип, не многопользовательский сервер: сетевой доступ, роли администратора,
TLS, централизованный сбор и устойчивое хранение ещё не реализованы.


### Управление модулями через панель

На странице «Управление» выберите карточку «Проверка файлов» или «Текст в Telegram».
Нажмите «Проверять файлы» / «Проверять текст», прочитайте описание и подтвердите
запуск. Для остановки используйте кнопку «Остановить» в той же карточке.
«Отмена» закрывает подтверждение без команды. Журнал и настройки вынесены
в отдельные страницы бокового меню. При недоступном состоянии кнопки отключены.
Надпись «Проверка работает» требует события готовности текущего запуска;
одного состояния active для неё недостаточно.
Прежний установленный gateway контролирует только прямые дочерние файлы `/var/lib/dlp-lab/watch`
с установленным фильтром мессенджеров. Текстовый модуль наблюдает только выбранное
видимое поле Telegram с маркером `DLP_TEST`, в течение 120 секунд.
Отправка текста не блокируется. Изменение выбора отменяет подготовленное действие.

Остановка снимает контроль выбранного модуля. Закрытие панели не останавливает
агент. Запущенный процесс ещё не означает готовность: ищите `monitor_started`
или `text_monitor_started` в журнале. Версия политики в ответе запуска относится
к файлу на момент запроса. Карточка работающего модуля отдельно показывает
подтверждённую событием `policy_loaded` версию его текущего запуска и совпадение
с файлом на диске. При отличии нужен перезапуск. Если событие отсутствует
в выборке журнала, версия показывается как неподтверждённая. Это не доказательство
готовности контроля: события готовности проверяются отдельно.
При ошибке или тайм-ауте сначала обновите статус и проверьте журнал, затем повторяйте.
Экспорт и локальное хранилище пока запускаются через CLI с нужными параметрами.


## Обучаемый ML-классификатор (эксперимент)

Добавлена отдельная обученная модель: финансовые сведения, паспортные данные,
данные доступа. Она анализирует текст и извлечённый текст документов локально,
даёт WARN и не запрещает отправку. В основной политике выключена из-за ложных
тревог. В панели: «Настройки анализа» → «Загрузить настройки» →
«ML-классификатор» → «Включён» → проверка изменений → сохранение;
затем перезапустите нужный модуль. До 16 КиБ текста, без OCR.

Проверка только ML без изменения основной политики, из корня проекта:

```sh
./scripts/dlp --policy config/ml-demo.yaml analyze --text 'Пароль: Reka!6831'
```

Ожидается WARN с analyzer=ml. Это вымышленный тестовый пароль.
Обучение, результаты и ограничения: [отчёт ML](docs/research/ml_linear_2026-10-19.md).
Обновление качества: на одном диагностическом наборе ложные тревоги снижены
с 10/20 до 3/20, пропуски — с 3/24 до 2/24. Выборка синтетическая и раскрытая;
независимая оценка ещё необходима. [Сравнение и воспроизведение](docs/research/ml_quality_2026-10-19.md).

### Расширенный файловый контроль (2026-10-19)

Подготовлен новый gateway с FAN_MARK_FILESYSTEM: вложенные папки поддерживаемых
локальных файловых систем, без обязательного размещения документов в watch.
На текущем стенде новый gateway установлен 2026-10-19, запуск проверен на реальном ядре. Для обновления других прежних установок
остановить files и выполнить в своём терминале:

```bash
sudo /usr/bin/env -i PATH=/usr/sbin:/usr/bin:/sbin:/bin /bin/bash /home/roman/dlp-lab/scripts/update-fanotify-access.sh
```

Затем `make privileged-test` и запуск files из панели. Область «Локальные файловые
системы» подтверждается событием текущего запуска; старый gateway остаётся видимым
как «Тестовый каталог». Python получает только события фиксированного Telegram,
сам широкий fanotify FD остаётся у native broker. Анализ текста/PDF/DOCX сохранён.
Служебные каталоги исключены; новые диски требуют перезапуска, FUSE/сетевые
файловые системы не охвачены. Реальный опыт блокировки Telegram вне watch ещё предстоит.
Подробности и шаги проверки: [ADR-012](docs/decisions/012-filesystem-scope.md).
